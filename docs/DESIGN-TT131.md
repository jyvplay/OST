# TT131 engineering report

## Contract, model and evidence threshold

The admissible deliverable is independently written production code in this single-PWA repository, its real tests and honest documentation. It must preserve existing behavior and the stated privacy/lightweight boundaries. Access consists of the original local specifications, source and history, an isolated server/database, permitted public references and the tools listed below—not access to all browsers, devices, users or future schedules. Resources include two available CPUs, wall time, CPU, memory, storage, network traffic and test fidelity; milliseconds, bytes, image pixels and WCAG rule severities are kept separate.

The requested universal success predicate is: for **every** admissible prior state, supported platform, user interaction, failure and resource budget, **there exists** a correct execution that preserves all existing good features, meets all original specifications and privacy constraints, makes every feature Class A (including at least 20 additional completed ones), and passes all mandatory checks. The original merge precondition additionally required the changed repository to be no worse than `main` on every relevant dimension and strictly better on at least one; the later explicit override is recorded below. A finite sample is evidence only for its own fixtures; changing the order to “there exists a passing execution for each chosen fixture” would be a different, much weaker claim.

**H+** remains plausible for the bounded improvements observed below. **H−** remains open for the entire requested system; the tests do not establish a general impossibility theorem. Specific stronger claims are false: a frozen or closed browser page cannot be treated as an assured exact alarm, and a focusable element alone did not reliably pan in our measured Chromium sequence. **H∂** includes page lifecycle, storage availability, assistive technology, browser implementation, device scale, content/state, operating-system behavior and the comparison baseline. The original whole-repository Pareto merge condition is not established; after this was disclosed, the user explicitly authorized merging despite that gap. The override is not evidence of Pareto superiority.

Adjacent but non-equivalent problems: a canvas that passes axe versus one that pans by keyboard; an accessible name versus a visually discoverable tool; a focused region versus keyboard operation; controlled-clock in-page alarms versus native alarms; a passing module case versus preservation of all workflows; a local faster wall-time sample versus less CPU/memory/energy and no regressions; same test names versus the same assertions; audited initial views versus every application state; and successful compilation versus a production-ready OS.

Actually used: Git and GitHub CLI; Node 22, Next.js/React, TypeScript and ESLint; two available CPUs; real Chromium 137/Playwright and axe-core 4.14; a locally initialized disposable PostgreSQL 17.5 instance, production HTTP server and real VFS/API; Python `cryptography`, `argon2-cffi`, Pillow, Shapely/GEOS and NumPy; test-only ical.js and Temporal; Chromium/Skia's canvas compositor as an independent comparison; and controlled clock, storage/Notification fault injection and temporary DOM/result mutations. Tests using doubles say so. No independent agent, theorem prover, other browser, physical device or OS-alarm service was used. This is not a formal proof of the universal predicate.

## False-solution shapes and the modal shortcut

The modal shortcut treats the usual observed state as if it quantified over all states. Its failure is concrete: an ordinary fit-to-window axe run passed while the controlled 800% canvas revealed a serious unfocusable scroll region; the targeted test forces that boundary and a temporary removed-tab-stop mutation makes the detector report the defect. Likewise, a normal storage read passed while a deliberately throwing getter allowed a test write to the host before repair.

These are not success: (1) one passing build; (2) a clean linter for only changed files; (3) one initial screenshot; (4) a screenshot of all apps at one state; (5) pretty icons without names; (6) an accessible name without discoverability; (7) `tabIndex=0` without working panning; (8) axe without keyboard behavior; (9) a function that pans programmatically without a user path; (10) fit zoom without overflow; (11) one engine implying cross-browser support; (12) a test double presented as an OS notification; (13) an in-page timer presented as a closed-app alarm; (14) a snooze arithmetic helper presented as a snooze UI; (15) encryption round trips alone proving no host leakage; (16) a browser guard without an independent host SQL check; (17) a faster mean proving lower CPU and energy; (18) same test names implying identical assertions; (19) one successful run after a repair proving all schedules; (20) a previous build's gate proving current source; (21) a register label proving Class A; (22) a local subset outperforming a prior branch proving the whole repository Pareto-superior to `main`.

## Research and imported hypotheses

MDN recommends a focusable, appropriately named scroll container when keyboard access is otherwise unavailable [1](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/overflow); this does not itself prove that every browser or assistive technology pans as intended. Deque's rule checks keyboard access to a scrollable region [1](https://dequeuniversity.com/rules/axe/4.0/scrollable-region-focusable); a pass is narrower than a complete usability audit. WAI-ARIA defines accessible names, including author-provided names for buttons [1](https://www.w3.org/TR/wai-aria-1.2/); an accessible name does not automatically give a sighted touch user a visible label. The specific SVGs and implementation here were written in this repository rather than copied from those sources.
