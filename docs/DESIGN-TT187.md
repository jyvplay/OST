# TT187 — bounded token revocation uncertainty

## Model, resources and runtime
One coding agent used the source repository, Bash, Node 22/Next/TypeScript production compiler, ESLint, Git/GitHub CLI, web research, a real Chromium 143 and disposable PostgreSQL. External Python and Node oracle packages were available for the gate. No independent agent, theorem prover or simulator was used. Browser network faults below are deliberate test interception, not actual network outages; side effects and authorization are checked against the real server/database. The environment has two CPUs; browser suites that mutate the shared disposable DB run sequentially.

Admissible objects: a Routines automation token ID and DELETE request against the existing token endpoint. Access: client sees response, an unconfirmed error, and later a separately requested list; server can commit before or after the client loses the response. Counted resource: event-loop time in milliseconds, with a 12,000 ms abort deadline followed by a separate 8,000 ms list deadline. Success for the exercised cases: while the request is outstanding a token's synchronous lock prevents duplicate activation; if the abortable DELETE or its body hangs and the event loop runs, show revocation unconfirmed and refresh the list; do not claim rollback; after refresh/failure release the lock for a deliberate retry. A real commit may complete after the refresh and the list can therefore be stale. A retry on the same ID uses the server's existing serialized, idempotent-revocation contract. No guarantee is made for page suspension, server rollback, non-abortable transports, concurrent clients, actual security revocation before confirmation, or global Class-A functionality.

H+: liveness with explicit uncertainty and retained recovery is achievable under an abort-aware fetch and running event loop. H−: the client cannot conclude from timeout alone whether server work committed or rolled back. H∂: outcomes depend on whether and when server receives/commits, response/body delivery, event-loop scheduling, and list availability. Threshold: a prepatch held-request failure, production build, two distinct server-state attacks plus failed-refresh attack, carried mutation and token suites, and documented gate result. These are not universal proofs or the user's 10a Class-A requirement.

## Frontier and candidates
[MDN Fetch](https://developer.mozilla.org/en-US/docs/Web/API/Fetch_API/Using_Fetch) describes HTTP failure as a response requiring status checking and abortable fetch/body consumption. Client cancellation is not a transactional rollback; inspect the existing endpoint's DB transaction and row lock for its actual behavior, not a generic idempotency claim. The open interface is a DELETE that may commit after the refreshed list snapshot, and concurrency/suspension beyond this bounded browser test.

1. **Client abort + unconfirmed warning + reload (implemented):** concrete code in `Routines.tsx`; three browser/DB tests. Attacker holds request before delivery or holds a real committed response, then checks authorization and refresh. Gap: delayed commit after refresh and event-loop suspension, local distributed-systems ambiguity.
2. **Promise race alone:** causal model: UI releases at deadline but unbounded fetch can later resolve or reject, requiring epoch protection and cleanup. Attack: release the older response after retry; no implementation adopted. Gap local stale-completion handling.
3. **Unconditionally declare failure and rollback:** counterexample: test commits the actual DELETE before holding its response; bearer authorization returns 401 despite timeout. Not a solution.
4. **Unconditionally declare revoked:** counterexample: test holds DELETE before it reaches server and bearer authorization remains 200. Not a solution.
5. **Automatically retry mutation:** design would resend ID on timeout; current endpoint serializes and reports already revoked, but a refresh may race with late commit and retry policies change audit/traffic. Attack: hold original then count duplicates. Not adopted; gap local timing, not entire OS task.
6. **Server-side operation status / cancellation:** design requires operation identity, persistent transition records, authentication and a cancellation protocol; client abort alone cannot implement it. Cheapest attack: commit just before cancellation. No artifact beyond causal model and inspected endpoint; gap is the exact distributed mutation interface, not the entire OS.

## Misleading shapes
A 200 response is not a consumed valid body; client abort is not rollback; timeout is not proof of failure; timeout is not proof of success; a list refreshed once is not future linearizability; a disabled button is not a synchronous double-click lock; a lock is not distributed mutual exclusion; a retried operation is not guaranteed delivered; one Chromium is not all browsers; local DB is not production network; a passing unit test is not real authorization; a build is not a functional proof; fixture interception is not an actual outage; an existing register label is not a Class-A promotion; more tests are not demonstrated faster tests. Modal shortcut: claiming either failure or revocation from silence. The held-before-delivery and held-after-commit tests detect both wrong conclusions against actual authorization.
