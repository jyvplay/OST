# TT231 — guarded duplicate trash

## Contract and evidence threshold

Admissible objects: two distinct live VFS files listed in a Storage duplicate group, identified by canonical path, id, version, and SHA-256 of stored content. In one guarded transaction, **for every** attempted target, if either the target or its designated retained peer no longer has the listed identity and stored-content digest, the request must not trash the target; otherwise it may trash the target while the peer remains live at the transaction boundary. The user may explicitly trash the other copy later. This is not permanent backup, a global deduplication proof, an atomic batch, byte-for-byte comparison beyond SHA-256, or protection from arbitrary privileged writers and older servers that bypass the cooperative lock. Lost acknowledgement is not proof of failure.

H+: a cooperative transaction can enforce this limited check. Evidence threshold: real Chromium/HTTP/PostgreSQL pre-patch counterexample, production build, fresh browser and concurrency/error attacks, affected regression gate. H−: without cooperative mutations or a common atomic check, a prior report cannot guarantee a later destructive action's preconditions; this is a local impossibility under that access model, not a statement that every deployment is safe or unsafe. H∂: hashes, locks, prior identities, sidecars, and later actions set boundaries. PostgreSQL documents transaction-scoped shared/exclusive advisory locks and their lifetime ([documentation](https://www.postgresql.org/docs/current/functions-admin.html)); the application must voluntarily use the same lock. The report query and each action are separate operations, and no claim is made that the entire report is an atomic snapshot with subsequent actions.

## Implementation and evidence

The Storage API adds ordered identity metadata to its existing duplicate groups without removing existing `paths`. Storage sends the chosen target and a designated retained peer to a dedicated guarded operation, not the offline queue. The existing VFS transaction acquires its exclusive cooperative gate and row locks, then checks target and peer id, version, digest, live file type, distinct path and digest of stored content. It refuses stale or malformed inputs. The old general-purpose Trash operation remains available to its callers. Older servers without identity metadata show an explanation and disable this specific duplicate action. A rejected or lost response says that the outcome was not confirmed; it does not claim rollback.

Real Chromium, HTTP, and PostgreSQL baseline: **0/2**; changed target was trashed, and changed retained copy allowed the last matching file to be trashed. After repair, **7/7** passed: both stale cases; ordinary success; concurrent reciprocal requests with exactly one success and one conflict; response lost after actual commit with an uncertain UI; malformed guards; and old-server identity absence. The lost-response test deliberately interrupts the real reply after the server operation, not a simulated commit. A subsequent eighth attack held the cooperative shared lock while changing the peer and observed the guarded request wait and then return 409; the expanded suite passed **8/8**. Production build passed. ESLint passed for both API routes and VFS; Storage's pre-existing `react-hooks/set-state-in-effect` error and cleanup-ref warning remain. Tests ran on an exclusive disposable database.

Limitations: the cooperative advisory gate excludes old servers/raw SQL and other nonparticipating paths. Guarding the primary file does **not** atomically guard the independently followed photo sidecar, which is still handled by the existing post-transaction helper; a partial sidecar failure is reported. A later user operation can remove the retained peer. If the response is lost, durable request-id/result lookup and safe automatic retry are absent. Reports can be stale, in which case the action refuses rather than silently refreshing into a new destructive choice. The report's grouping relies on stored digests, while this action recomputes the digest of both stored content strings before trashing. Identical file content with differing metadata is not a complete semantic equivalence guarantee.

## Candidate mechanisms and adversaries

| Candidate / artifact | Proven portion | Adversary and gap |
|---|---|---|
| Guarded target and retained peer, real implementation | 8/8 bounded tests above | noncooperative writer, separate sidecar, hash collision; local correctness gap under broader model. |
| Target-only identity check, existing VFS primitive | protects against changed target | retained peer changes first: baseline demonstrates last-copy loss. |
| Re-read before unguarded Trash, design | could warn on stale state | writer races between re-read and Trash; local TOCTOU remains. |
| Confirmation dialog, design | confirms user intention | confirms obsolete report, not concurrent identity; original race remains. |
| Never allow duplicate Trash, design | avoids this action's deletion | fails to preserve useful functionality; not accepted. |
| Immutable versions or a durable deduplication snapshot, design | potentially stronger historical recovery | restore policy, storage costs and concurrent writes require a separate end-to-end implementation; larger gap. |

Reject the following as substitutes: a success toast, a DOM click, a prior duplicate count, same name, same size, matching stale digest, a single matching copy, a majority/modal safe case, a confirmation dialog, an HTTP 200 with an unverified body, response absence as proof of noncommit, a mocked deletion as proof of a real one, a local-only mutex, a raw SQL writer assumed cooperative, a green lint, a screenshot, a past full gate, or a feature-register label. The changed-peer baseline is the modal counterexample: a usually safe duplicate group can lose its only remaining matching file when one rare peer changes. The real browser test detects this particular case, not every concurrent history.

The requested entire OS scope, ten Class-A promotions, all-app visual review, and significant Pareto speedups are not established. No independent agents, simulators, theorem provers, or expert reviewers were used. The cooperating-writer lock test passed as described above. The next high-information test is concurrent sidecar replacement; it needs a separately designed atomic companion policy before making a stronger safety claim.
