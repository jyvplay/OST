# TT159 — automation settlement race

## Scope, model and hypotheses
Admissible objects are PostgreSQL automation run rows whose initial status is `queued`; independently arriving HTTP settlement reports carry a positive run ID, a boolean and a bounded result. The system is the existing Node/Next server and PostgreSQL database, with an exclusive disposable database for experiments. Resource: terminal transitions and corresponding audit records per run (count, not time). For each queued row, for every finite set of concurrent settlement reports, at most one queued→terminal transition commits; when it does, exactly one matching audit insert commits in the same transaction. Competing and later successful HTTP responses must report the committed terminal row. A nonexistent row returns 404; failed audit insertion leaves the row queued. This is a bounded claim about settlement, not execution.

H+: a conditional row update plus an atomic audit transaction can satisfy the above under PostgreSQL's concurrency semantics. H−: exactly-once real-world action execution is not established by atomic settlement; without coordinating action execution and failures, two shells may perform the same work. H∂: multiple processes, lost responses, browser crashes, unauthorized settlement and database failure require additional protocol or security assumptions. Relevant [PostgreSQL Read Committed documentation](https://www.postgresql.org/docs/current/transaction-iso.html) says a competing updater waits and re-evaluates its WHERE predicate against the updated row; it applies to this one-row conditional update and does not prove an external side effect occurred once.

Evidence threshold: fail an adversarial real HTTP/PostgreSQL test on the old implementation, then pass that test and a distinct audit-write rollback attack on the production build, as well as the affected HTTP and browser suites. A clean whole-project gate is separately necessary for merge. No theorem prover, independent agents, simulator or external expert review was used. Actual tools: TypeScript/Next production compiler, Node, Playwright/Chromium, PostgreSQL, Git and web documentation search.

## Six constructions, artifacts and strongest attackers
1. **Conditional update + audit transaction (implemented):** `src/app/api/automation/route.ts`. Concurrent real reports are forced to contend on a real DB row; only one wins, both report the terminal value, and one audit exists. Attack: audit insertion raises a database exception; the row stays queued (real trigger fault injection). Gap: no guarantee of single browser execution or authorization; global to the broader feature.
2. **Read then unconditional update (previous behavior):** reproducible counterexample `scripts/tt159-settle-race.mts` held a row lock, let both HTTP requests read queued, then released it; old code returned two wins. Gap local to terminal-state atomicity.
3. **Per-process JavaScript mutex (not used):** causal counterexample is two Next processes with separate heaps. Cheapest falsification is two independent server processes settling the same row. Global across server replicas.
4. **Row lock transaction then check (alternative):** could serialize the read and update, but longer-held locks and audit rollback must be tested. Attack: lock-holder crash or long transaction; verify rollback and contender behavior. Local alternative, not implemented.
5. **Serializable transactions (alternative):** may abort concurrent conflicts and need retries; returning a serialization error without a defined retry is not equivalent to a terminal reply. Attack: simultaneous conflicts plus bounded retries. Local for database transition, not side effects.
6. **Pre-execution claim/lease (not implemented):** may stop concurrent shell dispatch, but a crash after a side effect and before settlement creates an ambiguous outcome. Attack: kill claimant after action, before acknowledgement. This is a global execution/recovery problem, not solved by settlement.

## Fifteen misleading results
1. One terminal DB row does not prove one execution. 2. One response does not prove the loser agrees. 3. Serial tests do not prove concurrency. 4. A race that did not happen is not a passing attack. 5. Locking only in one process is not cross-process coordination. 6. Conditional update without atomic audit can lose the audit. 7. A failed transaction is not a failed action. 8. A missing audit is not proof that no action occurred. 9. A browser toast is not durable evidence. 10. Duplicate effects are not fixed by deduplicating reports. 11. A bearer token is not an authorized shell settlement. 12. A 200 response after a timeout is not guaranteed. 13. Rate limiting by a stale read is not concurrency-safe. 14. A conditional row update does not enforce a global queue bound. 15. A disposable DB run is not an installed-PWA or multi-device security test. 16. Passing focused tests is not a passing full gate.

## Actual tests and next gap
The lock-barrier attack failed on the old production server (both calls claimed success) and passed after the repair. A second real PostgreSQL trigger-induced audit failure verified rollback. Existing `tt146-http` 4/4 and `e2e-tt146` 5/5 passed sequentially after repairing the HTTP suite's cleanup: the suite previously left its own 31 real queued commands, which the next browser shell executed, covering the Devices window. Cleanup now deletes only its own still-queued fixtures on an explicitly disposable database, with no claim those actions were executed. The full project gate must be reported separately.

Important remaining risks: queue retrieval still does not claim work, so two shells may execute it twice; settlement is currently unauthenticated, and rate-limit/queue-cap updates have concurrency gaps. The highest-information next test is two real independent browser contexts executing the same queued action, then a crash between side effect and settlement, followed by a separately designed authenticated claim/recovery protocol. No Class-A promotion, all-app visual audit, original artwork, or measured test-speed improvement is claimed.
