# TT171 — Backup copy density and safety

## Model and threshold
Admissible object: the Backup module in the existing real PWA against an exclusive disposable PostgreSQL database. Access: repository, git/gh, public documentation, Chromium, Node/Next/TypeScript and PostgreSQL. Count: default-view words under the existing TT119/120 metric and real workflow assertions; no CPU or speed improvement is asserted. For every tested build and given disposable data state, default Backup must retain its primary operations and visible safety limits and be at or below the unchanged 440-word gate; existing backup/recovery and density suites must run without weakening them. This is not a universal bound over arbitrary file names, datasets, viewports or open disclosures, and is not a claim of complete OS functionality. Local commit threshold: observed old counterexample, successful build, new browser attack for safety messages and primary controls, affected regressions. PR must disclose any failed or unavailable gates.

H+: precise independent rewriting may reduce fixed copy while preserving essential caveats. H−: the previous data state exceeded the existing bound; this is not a proof the broader task is impossible. H∂: measured words change with saved inventory and UI state; lowering the metric is not equivalent to usability, nor does an empty data state prove growing-list behavior.

Runtime: npm-installed dependencies, embedded real PostgreSQL, Playwright with real Chromium and external test tools in a disposable workspace; no independent agent, simulator, theorem prover, expert review or assistive-technology system. Public research: GOV.UK advises details only for information not needed by most users, with clear descriptive labels and acknowledged voice-access caveats (https://design-system.service.gov.uk/components/details/). This is guidance, not evidence that hiding backup risk warnings is safe. No best-known global optimality or impossibility result is established; the interface remains preserving understandable risk boundaries while bounding dynamic content and the complete OS contract.

## Portfolio and adversaries
Each candidate is a falsifiable design contract, not a claim that all were implemented or formally proved; all gaps are local except a whole-app design policy.
1. **Raise cap**: hypothetical altered bound. Artifact: 459 ≤ 460, a numeric observation. Attacker: unchanged text and UX; this weakens an acceptance contract. Not implemented; gap is original UX, not arithmetic.
2. **Hide all warnings**: hypothetical removal. Artifact: risk information unavailable; security/restore-boundary presence assertions attack it. Gap is safety, local but unacceptable.
3. **Native disclosure of secondary material**: hypothetical named details. Artifact: open/close keyboard workflow. Attacker: essential safety info hidden from users; compare visible key-custody, scope and rollback warnings. Not implemented; local UX/accessibility gap.
4. **Inventory pagination**: hypothetical bounded rows and navigation. Artifact: pagination contract for all saved entries. Attacker: prune targets hidden or newest order changes; test every page and prune plan. Unimplemented; local dynamic-data gap.
5. **Independent copy editing**: preserve operations and risk semantics, shorten duplicate prose. Artifact: changed component and real-browser suite. Attacker: secret custody, preview conditions, rollback/erasure and drill scope; probe text and actual config creation plus existing encryption and drill suites. Verified only for tested fixtures; dynamic lists and comprehension remain unproved.
6. **Virtualization**: hypothetical viewport-bounded entries. Artifact: keyboard focus/scroll identity contract. Attacker: recycled rows lose focus or omit data, especially assistive technology. Not implemented; local accessibility gap.
7. **Whole-app systematic content model**: audit and rewrite every surface against explicit risk/function contracts. Artifact: app-by-app checklist and screenshots. Attacker: hidden warnings, omissions and altered functionality. Not implemented; this remains essentially the broader original task.

Misleading result shapes and probes: (1) fewer words vs retained warnings (text assertions); (2) hidden warnings vs visible warnings (innerText); (3) controls in DOM vs visible (visibility checks); (4) one viewport vs accessibility (additional real devices/AT required); (5) open button vs working action (real config build); (6) build vs verified bundle (checksum status); (7) plain checksum vs authentication (retain source caveat); (8) encryption vs key custody (retain either-secret and loss warning); (9) database rollback vs erasure (retain disk warning); (10) sample drill vs full restore (retain sample limits); (11) preview vs commit (existing preview/restore suite); (12) fresh database vs arbitrary inventory (large-data test remains open); (13) test count vs all schedules; (14) failed dependency vs application failure (install missing oracle and rerun); (15) targeted green vs full gate; (16) one word-count improvement vs measured script performance. The modal shortcut is making a panel shorter by hiding or deleting safety copy; new tests require visible caveats and primary controls, plus build a real snapshot.

## Experiments so far
Old production on a newly bootstrapped disposable database: 459/440, test failed. After rewrite: 429/440, a 30-word reduction in that exact default state; no arbitrary dataset guarantee. Final production build passed and the new real-browser suite passed 2/2. TT87 backup passed 6/6. TT88 initially failed 2/6 because the independent Python cryptography package was missing; after installing it, TT88 passed 6/6. TT89 drill passed 9/9. These are functional checks, not proof of user comprehension or all-app quality. A full gate is running; its result must not be inferred from the targeted suites.
