# TT153 — cron correctness and regression triage

## Scope and evidence threshold

The cron engine is a pure, minute-granularity parser and occurrence calculator. It does not schedule or execute jobs. Within its documented Vixie-style day-field dialect, matching is the intersection of the two expanded day sets when either field begins with a wildcard, and the union when neither does. `?` is this project's extension, treated like a leading wildcard. Success means the resulting instants are strictly after the cursor, selected dates obey those rules, descriptions do not hide the conjunction, and the browser uses no network for the calculation. A finite corpus cannot prove this for all expressions, zones or dates.

The local threshold was TypeScript, regression tests that fail before each repair, unchanged RFC/HMAC and DST cases, independently generated UTC examples, and an adversarial boundary test for the optimization. A full production regression gate remains necessary before merge.

## Independent evidence and repairs

* Vixie/ISC cron's historical leading-asterisk behavior is documented at https://crontab.guru/cron-bug.html and can be inspected in the cronie source at https://github.com/cronie-crond/cronie. It differs from a naive “only a literal star is unrestricted” implementation. The previous code incorrectly unioned `0 0 */2 * 1`, firing on odd dates **or** Mondays. We now intersect when either day field begins with a wildcard. The other branch continues to union restricted fields.
* The previous impossibility check rejected `0 0 30 2 1` even though the OR weekday branch matches Mondays in February. It is now accepted; an impossible February day with an unrestricted weekday is still refused. Separate test assertions list the February 2025 Mondays because croniter 6.0.0 refuses this particular expression before evaluating its OR branch.
* The pinned `docs/test-fixtures/cron-vixie.json` was generated by `scripts/oracle/cron_oracle.py` using external `croniter==6.0.0` (MIT), with `implement_cron_bug=True`. The test checks six schedules and five future UTC instants each. The oracle package is test-only, not shipped in the app. Regenerate using a Python environment with that exact version: `python scripts/oracle/cron_oracle.py > docs/test-fixtures/cron-vixie.json`.
* Invalid long names such as `mondayish` and unsafe numeric steps are refused rather than silently interpreted. Valid three-letter and full names remain supported. A spring-forward gap earlier on the cursor's civil day is no longer returned as a future skipped occurrence. Targeted tests first failed on the prior behavior, then passed on the repair.
* UTC occurrence search now avoids resolving candidate minutes on the cursor day that are necessarily at or before the cursor. Other zones keep the original resolver. Dense schedules, seconds within a minute, midnight, and the existing DST tests exercise the boundary. An alternating local benchmark of 20 calls at 23:55:30 UTC reported before 883/1010/1200 ms versus after 37/15/19 ms (`scripts/tt153-cron-bench.mts`). This is one workload under variable shared CPU load, not evidence of universal speedup or a full test-gate improvement.
* Beam's empty QR input now displays an original QR glyph and neutral prompt rather than a blank white block and red error. Nonempty overflow is still refused; Chromium checks both paths. The empty-state screenshot was inspected locally.

## Regression triage and limits

A production build before the cron/QR changes passed the previously failing vector (12/12), TT81 (7/7), TT49 Writer (6/6), TT73 Writer (4/4), and TT130 privacy tests. TT134's GitHub check initially returned `unknown`: the Node server could not verify the sandbox's certificate. Restarting the same server with `NODE_OPTIONS=--use-system-ca` (without disabling verification) produced a real HTTP 200 and `X-Frame-Options: deny`; the suite then passed 8/8. The first concurrent density/UI attempt was invalid because both changed the same desktop; its density receipts were restored and the affected UI suite rerun exclusively.

This work does not establish every feature as Class A, does not provide a cron routine trigger or persistent OTP entries, and does not include a visual inspection of every app. The exclusive production density runs left five recorded failures: Monitor exceeds the TT119 and TT120 700-word ceilings and the TT124 520-word ceiling, Routines exceeds the TT124 300-word ceiling, and the TT124 Writer screenshot interaction was intercepted by the shelf. TT118 passed. These are not resolved by relabeling the limits. The full production gate still needs to pass without weakening assertions. No new register rows or feature-grade promotions are claimed.

## Extended gate and follow-up

The production gate was interrupted after roughly 28 minutes, after several failures and while the accessibility browser suite was running; it is **not a complete or passing gate**. Its receipts additionally recorded spreadsheet header resize (138 → 138 pixels), a stale Clock edit conflict timeout, and shelf interception of Terminal and Writer controls in several window layouts. The accessibility suite also recorded the resize failure and two subsequent timeouts. Those failures need independent investigation; do not infer that the timeouts have the same cause. The gate's TT126 Vault and two TT127 Vault race cases hit an ambiguous exact “Add” button name introduced by the OTP panel. The OTP action is now labeled “Add code”; without changing the assertions, exclusive development-server reruns and a subsequent rebuilt production-server rerun passed TT126 4/4, TT127 Vault 3/3, and TT151 2/2. The rebuilt production ledger checks passed 5/5. These reruns are not a replacement for a full production gate. The size of the existing register and earlier successful suites are not proof of 20 additional Class-A promotions.
