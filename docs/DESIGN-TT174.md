# TT174 — guard a Backup prune target against replacement

## Model and evidence threshold
Admissible objects: the existing Backup inventory and per-file Trash request, the real VFS HTTP endpoint and exclusive disposable PostgreSQL. Access: source, git/gh, public research, Next/TypeScript, actual Chromium and HTTP/PostgreSQL; independent test input is a concurrent real VFS write. Count: tested requests, database identities/versions, statuses and UI outcomes, not a throughput improvement. For each tested schedule, if the file at the target path is replaced or rewritten after the panel lists it and before the guarded Trash request locks it, the changed file must remain live and the client must show an unconfirmed operation, stop the batch and refresh. Existing unguarded Trash calls must retain their semantics. This does not guarantee an atomic batch, a stable list of the two newest, protection from direct writers ignoring version semantics, immutable backup files, or client acknowledgment of commits. A local commit needs a pre-patch actual counterexample, final build, adversarial tests and affected regressions; report full gate result. Follow user request to review main and assess merge only after testing.

H+: a per-target identity/version/hash precondition checked in the same DB transaction as Trash can prevent the tested replacement. H−: existing unguarded implementation acts on whatever is currently at that path; this is a real counterexample, not a whole-OS impossibility proof. H∂: raw writes that bypass maintained versions, deletion/recreation, other clients and missing rows affect guarantees. Available and used: shell/git/gh, web research, Node, TypeScript/Next, Chromium/Playwright, exclusive disposable PostgreSQL. No independent agent, theorem prover, simulator, human expert or assistive-technology system.

Frontier: PostgreSQL's row-level locks prevent competing writers from modifying a selected row until the locking transaction ends (https://www.postgresql.org/docs/current/explicit-locking.html); a missing row cannot be locked this way and cooperative advisory locks do not constrain raw clients. Transactions provide atomicity for their participating statements, not HTTP response delivery (https://www.postgresql.org/docs/current/tutorial-transactions.html). No global best or impossibility theorem for the full OS is known. Open interface: whole-batch snapshot/retention invariants and confirmation after network failure.

## Experiment and results
The pre-patch Chromium test intercepted a real prune POST, rewrote the selected file through the real API, and then forwarded the POST. The rewritten file was trashed (assertion `true !== false`). After the change, the same browser/HTTP/PostgreSQL schedule passed. The client sends the listed id, version and hash for each target; the server validates them and checks the locked row inside the Trash transaction. Missing metadata fails closed in this client; omitted guard remains the existing unconditional API. An empty hash is accepted for legacy rows; id/version remain essential. Malformed guards return 400, mismatched/deleted/trashed files return 409. A direct HTTP test covered malformed guards, purge/recreate with a new id, and a valid guarded Trash. TT174: 2/2; TT173: 4/4 including lost response; TT172: 4/4; TT171: 2/2, 430/440 words. Production build passed with DATABASE_URL. Earlier build without DATABASE_URL failed during page-data collection. Tests use exclusive disposable DB, not user data.

The cross-client rewrite was issued from an independent HTTP client while a browser request was held, not from a second browser tab. No cross-tab UI test or simultaneous batch-insertion retention test was run. A sequential batch can partially complete, a response can be lost, and other files may be added, so no atomic batch or newest-two invariant is claimed. Existing generic callers without a guard are unchanged. Raw DB writers bypassing VFS conventions are outside this guarantee. No all-app visual review, 20 Class-A promotions, measured script speedup, or independent OS-wide audit was completed this turn. Prior full gate (TT173) failed density limits in Routines, Files and Beam; no full gate was run on this change.
