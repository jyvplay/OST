# TT177 — distinguish unknown Remote Playback availability

## Bounded contract, model and evidence threshold
Admissible objects: Beam's actual React UI, browser Remote Playback API and availability callback/error/cleanup, relevant capability status and existing density gate. Inputs: callback true/false, API absent, watch promise rejected or pending. Browser/HTTP and disposable PostgreSQL are observable; no receiver hardware or privileged platform API is available. Count: displayed words, tested observable labels/callbacks and regressions, not Class-A promotions or speed. For the tested real-browser false callback, the displayed status must be scoped to Remote Playback; for the pure mapping test, null must be unknown and true and false must remain distinct. No capability, trust prompt, action, warning or other transport may be removed. We do not claim actual external receiver connectivity, accessibility conformance, global browser support, or a bound independent of session history. Threshold before commit: counterexample on existing production, passing build, new browser attack(s), affected existing tests and honest gate report. Explicitly user requests merging PR at end; do not conflate merge with complete success.

H+: scope/status wording can distinguish unknown from unavailable while retaining all controls. H−: current text overstates an unknown value (tested); this is not an impossibility theorem for the OS. H∂: the API may be missing, monitoring may fail, callbacks can race cleanup, and other casting methods behave differently. Open interface: device-specific actual receiver discovery/connection, and reliable status after API changes or permission failure. Resources actually available: shell/git/gh, web documentation, Node/TypeScript/Next, Playwright real Chromium and disposable PostgreSQL; no independent agents, simulator, theorem prover, human expert, accessibility tester or receiver hardware. No speed experiment implied by adding tests.

## Research frontier and candidate portfolio
MDN documents that `watchAvailability` provides a boolean for the corresponding media element, and may reject if continuous monitoring is unsupported (https://developer.mozilla.org/en-US/docs/Web/API/RemotePlayback/watchAvailability). The Remote Playback specification allows false when continuous monitoring is disabled and rejects monitoring under other conditions (https://w3c.github.io/remote-playback/). Thus false is a report by this particular monitor, not proof of absence of every possible receiver; no assertion about a complete hardware network follows. No global achievability/optimality/impossibility theorem for the OS is established. Six distinct designs, artifacts and strongest cheap attacks follow; all gaps local unless noted:
1. **Existing generic receivers label**: the old real Chromium output `receivers: none reported` is the counterexample. Attacker: other transports remain available while Remote Playback says none. The target does not specify which monitor produced the status; local semantic failure.
2. **Hide the badge**: a proposal retaining cards but suppressing availability. Attacker: a user cannot distinguish pending from false or true. Test: callback states and keyboard navigation. Not implemented; local loss of useful feedback.
3. **Scoped three-state text**: implemented label and pure mapping; old/new actual browser tests exercise false with real monitoring. Attacker: promise rejects, callback true, and late unmount. Pure tests cover label mapping, not real hardware, promise rejection or cleanup; local monitoring gaps remain.
4. **Mark null as unsupported**: design maps missing/pending/rejected to unsupported. Attacker: delayed watch or monitoring rejection while manual prompt works. Test with a real browser where monitoring rejects but prompting is available. Not implemented; local semantic failure.
5. **Query each transport independently**: design reports per-transport hardware discovery only when a genuine API exposes it. Attacker: unavailable or permission-gated APIs and inconsistent device identities; test across genuine hardware and browser permission states. Not implemented; device/provider interface gap beyond this local change.
6. **Aggregate availability**: design combines monitored transport observations. Attacker: one transport false and another unknown or available; boolean OR treats unknown as false and makes an invalid universal claim. Test full three-valued truth table and hardware observations. Not implemented; aggregation evidence gap.
7. **Trust actual connection outcomes**: design only shows verified established sessions. Attacker: failure or disconnection after a successful connection; test actual receiver disconnect. Not implemented; real-device availability gap.

## Misleading result shapes and attacks
DOM present versus visible; one browser versus all; API property exists versus watch works; false callback versus no possible device; unavailable monitoring versus unsupported connection; available API versus actual receiver; reported receiver versus successful connection; remote playback versus Presentation; permission refused versus no device; callback state versus current hardware after disconnect; session logged versus transport genuinely active; top-bar text versus enforced privacy; words counted versus comprehensible layout; one viewport versus all; historical coverage tags versus production-grade functionality; a screenshot versus an accessibility audit; targeted tests versus full gate; clean git versus correct software; faster wall time alone versus Pareto improvement; source docs versus observed hardware. Modal shortcut is a bare `receivers: none reported` derived solely from Remote Playback: a user can read it as a universal statement while other transport cards are present. The new browser test demands a scoped label and checks all 11 existing transport labels and trust/file/filter/copy controls. It failed on the old build and passed on the patched build. The initial pre-patch attempt assumed Chromium had no Remote Playback API and failed that assumption; a direct real-browser inspection showed it does have the API and reported false, so the test was corrected to check the actual environment rather than faking an absent API.
