# TT192 — rehydration after a cross-tab handshake

## Runtime and model
One coding agent used Bash, Git/gh, web search, Node 22, the Next/TypeScript production compiler, ESLint, actual Chromium 143 through Playwright, and disposable PostgreSQL. No independent agent, theorem prover, simulator, external expert, or actual assistive technology was used. Test interception deliberately delays a real list response and injects a Storage exception; token creation, row locking, DELETE, list and bearer checks use the real app/server/database. Two CPUs were available; browser suites sharing the DB run sequentially. Application changes are independently written and add no dependency.

Admissible objects: existing eight-character automation token IDs, monotone uncertainty snapshots in an open document, sessionStorage markers, list responses, and advisory same-origin/same-partition BroadcastChannel messages. The client cannot see an uncommitted transaction or predict when it will commit. An adversary may order the real row lock, DELETE, browser reload, list delivery, another tab's handshake, storage denial and transaction release. Counted resources: token IDs retained per document/tab and transmitted in chunks of at most 100; an entire successful list rehydration can send ceil(n/100) messages, where n is the number of marked listed IDs. No throughput/CPU/latency bound or speedup has been measured. Existing deadlines are 12,000 ms for DELETE and 8,000 ms for list, with event-loop and transport limitations. A marker is advisory, not authorization or a server operation journal.

Success, with quantifier order: for each tested ID and ordering, given a first tab has retained its marker, a second tab has subscribed and requested replay while the first is waiting to read an actual list, the first eventually rehydrates before its request deadline, and the broadcast is delivered, the second's corresponding last-seen-live row becomes uncertain without marking an unrelated token; this should still happen if the second tab's marker storage is denied. Failure is an unqualified live row in this exercised schedule, an unrelated affected token, or incorrect real bearer results. These finite runs are not a proof for every ordering or browser. Missing peers, closed pages, unavailable channel, delayed/dropped messages, unlisted IDs, lost storage, other devices, hostile same-origin scripts, exactly-once operations and whole-OS Class-A certification are distinct problems.

H+: the exercised rehydration ordering can be repaired with an advisory announcement after rehydration plus announcement on channel installation. H−: absent a knowledgeable active peer or durable shared record, a client with an early live snapshot cannot distinguish a never-delivered revoke from one that will commit later. H∂: lifecycle, delivery, data storage, list membership and deadlines change the result. Threshold for the narrow change: real DB prepatch counterexample; production build; same ordering after repair and a patch-directed storage-denial attack; related regression suites and an honestly reported full gate. The full user task succeeds only with its broader acceptance criteria, not this narrower threshold.

## Frontier and competing mechanisms
[MDN BroadcastChannel](https://developer.mozilla.org/en-US/docs/Web/API/Broadcast_Channel_API) describes communication among matching origin/storage partitions and explicit closing; a channel is not a history or transaction log. [MDN sessionStorage](https://developer.mozilla.org/en-US/docs/Web/API/Window/sessionStorage) specifies per-tab page sessions, possible opener copies, reload survival and policy exceptions. [PostgreSQL READ COMMITTED](https://www.postgresql.org/docs/current/transaction-iso.html) specifies that an ordinary SELECT sees committed data at statement start, not a concurrent later commit. These conditional facts do not verify app-level delivery or imply cross-device guarantees.

1. **Rehydration and channel-install announcements (implemented):** broadcast only ID markers in bounded chunks both when a successful list restores session markers and when a channel is installed, avoiding the two possible initialization orderings. Real blocked-DELETE reload/handshake test and denied-storage receiver attack. Attacker blocks list forever, closes channel, removes storage or reorders beyond delivery; gap local advisory lifecycle and the larger server outcome ambiguity. Next cheapest test: list failure or timeout followed by a successful manual retry while a peer remains open.
2. **Request-only handshake (TT191 baseline):** concrete real-DB counterexample: peer receives request before its delayed list restores markers and never sends later; prepatch 0/1. Gap local rehydration ordering.
3. **Periodic retries of request:** causal design; later request can succeed with active peers, but fixed intervals burn resources and cannot prove success for a permanently unavailable peer. Attack freeze the sender across all polls or block transport. Gap local liveness under unbounded failures; not implemented.
4. **Shared origin-wide localStorage event plus persistent IDs:** could support late readers when storage succeeds, but extends metadata retention and cannot guarantee persistence under denial or eviction. Attack storage clear and private partition. Gap local privacy/lifetime plus original server ambiguity; design only.
5. **Broadcast every received marker:** naive fanout risks ping-pong storms because both peers retransmit the same ID. Causal cycle A→B→A, with no termination condition. Attack two listeners and count messages; not implemented. Our receiver does not rebroadcast received messages.
6. **Poll token list:** repeated live reads can all precede a held transaction's commit. The lock/list/401 experiment is an executable counterexample. Gap equivalent to outcome identification with only precommit observations; not adopted as a guarantee.
7. **Server-side durable operation record:** design operation identity, authenticated state, idempotency and retention before mutation, with explicit delivery and cancellation semantics. Attacker delivers an original DELETE after a status read or expiry. This is a new protocol, gap local to the protocol rather than proof of all OS functionality; not implemented.

## Misleading outcomes and modal shortcut
Client abort is not rollback; timeout is not failure; timeout is not success; a list snapshot is not future liveness; a marker is not authorization; a broadcast is not confirmed delivery; same origin is not sufficient across storage partitions; a tab session is not cross-device persistence; a handshake is not a durable log; sending after rehydration does not cover failed rehydration; a UI warning is not transaction cancellation; an unrelated token staying live in one run is not isolation proof for every schedule; a storage exception injection is not a real-world policy survey; a single browser is not cross-browser verification; a build is not behavioral proof; role markup is not screen-reader verification; one screenshot is not an all-app review; new test coverage is not a speedup; ledger counts are not Class-A certification. Modal shortcut: treating an early live list as evidence of current or future bearer authorization. The real held-row test captures an early list, observes the request at the reloading peer before rehydration, and after delivering the captured list releases the row lock and checks actual bearer 401. The receiver-denied-storage variation attacks a repair that depends only on shared persistent storage.
