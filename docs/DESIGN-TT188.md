# TT188 — late revocation after a list refresh

## Model and boundary
One coding agent used repository inspection, web research, Node/Next production build, ESLint, shell, Git/GitHub, Chromium 143 and a disposable PostgreSQL server on a two-CPU machine. No independent agents, theorem prover, simulation, or real accessibility technology were used. Admissible objects are authenticated automation token IDs, an actual DELETE and independent list/authorization requests. The attacker can lock a token row in PostgreSQL, delay the server transaction beyond the client timeout and refresh, then release it. The browser can dismiss the warning or deliberately retry. The property exercised is that a live row previously subject to a revoke is labeled as uncertain, including after a warning is dismissed and an early list refresh; unrelated rows are not marked. This is an in-memory, mounted-component property, not a global guarantee. Timer progress assumes an active event loop and abort-aware transport. Other clients, reload/unmount, and arbitrarily delayed list responses are outside the demonstrated boundary.

H+: a conservative local marker prevents a stale list read from being presented as unqualified live in the exercised sequence. H−: timeout and an earlier live snapshot cannot determine whether the server will subsequently commit. H∂: visible state depends on list arrival, server commit ordering, component lifetime, and other clients. Success threshold: a prepatch counterexample, production build, actual browser/database late-commit attack with authorization checks and idempotent retry, related regressions and an honestly reported full gate. This is not a universal proof or evidence of ten Class-A features.

## Frontier and candidate portfolio
[MDN Fetch](https://developer.mozilla.org/en-US/docs/Web/API/Fetch_API/Using_Fetch) documents aborting requests and body consumption; that does not establish rollback. [PostgreSQL isolation](https://www.postgresql.org/docs/current/transaction-iso.html) describes transaction snapshots and concurrent effects; a list snapshot is not evidence about a future commit. The actual endpoint and database behavior were examined and exercised, rather than assuming a generic retry contract.

1. **Per-ID local uncertainty (implemented):** `Routines.tsx` marks a token as soon as revoke is initiated; live observations remain qualified even if the warning is dismissed. A revoked observation is displayed revoked. Attack: hold row lock through timeout and refresh, then commit. Gap: state disappears with unmount/reload, and status is a last observation, not durable synchronization.
2. **Warning only (prepatch):** TT188 real-DB test fails when dismissal leaves an unqualified live row; no durable marker.
3. **Clear marker on one successful list:** a list can run before a delayed commit. The locked-row experiment is a counterexample; not implemented.
4. **Declare revoked at timeout:** held-before-delivery TT187 test shows bearer still authorized; not implemented.
5. **Automatically retry:** server's tested same-ID retry is idempotent in the exercised transaction, but automatic retries change traffic and still need a bounded operation protocol. Attack with held original and concurrent retry; not implemented.
6. **Persisted operation identity/status:** would require authenticated server-side durable records, retry semantics and retention, plus a protocol for indefinite in-flight operations. Attack commit immediately after a status read or cancellation. Design only; no server protocol or proof implemented.

## Misleading result shapes and modal shortcut
Timeout is not rollback; timeout is not commit; abort is not server cancellation; an early list is not a future-state guarantee; a warning dismissal is not resolution; an observed revoke is not a guarantee about other clients or future mutations; a badge is not authorization; UI disabling is not a distributed lock; a local lock is not a server transaction; one idempotent retry is not universal exactly-once delivery; a database test is not a production network; network interception is not a real outage; one browser is not cross-browser proof; one screenshot is not an all-app review; a build is not functional correctness; a prior ledger label is not a Class-A proof; additional tests do not demonstrate speedup. The modal shortcut would infer either success or failure from silence, or infer future liveness from a past snapshot. The held-row/actual bearer test specifically attacks those inferences.
