# TT168 — explicit token-revocation outcome

## Scope and declared threshold
Scope is the existing Routines token list's DELETE interaction with the real API and disposable PostgreSQL, not authentication, exactly-once execution or the complete OS. Resource: HTTP outcomes, DB state, list and warning state, and per-token pending actions. A passing tested schedule must never treat an HTTP error or a lost response as confirmed revocation; it must refresh the list and explicitly communicate ambiguity, while retaining a way to retry. A local commit requires pre-patch counterexamples, successful build and affected regressions, and a patch-targeted adversarial browser test. Merge requires the full gate on the exact build and main review. H+: scoped reporting and refresh are achievable. H−: the complete requested OS might be impossible under the constraints, not established. H∂: a lost response can occur before or after commit; concurrent clients and failed refreshes affect what can be known.

Available and actually used: local git/gh and shell, web search, Node, TypeScript/Next, Chromium/Playwright, HTTP and exclusive disposable PostgreSQL. No independent agent, simulator, proof assistant, human expert or assistive-technology system. Test-only PG trigger failures and transport aborts exercise actual server/database outcomes; a delayed or dropped real response is fault injection, not a simulated production implementation. MDN notes fetch resolves for HTTP error statuses and consumers must check `Response.ok` (https://developer.mozilla.org/en-US/docs/Web/API/Window/fetch). This does not establish whether a server committed before a network failure. No global best-known result or impossibility proof for the complete OS is claimed.

## Evidence and frontier
Old production failed both initial adversarial cases: no warning following a real PostgreSQL audit-trigger 500 and none following a dropped successful DELETE response. The modified build passed four Chromium cases: rollback plus retry and bearer authentication, committed response loss plus revoked listing and authentication, two synchronous activations while a DELETE is held (one request), and committed response loss plus failed list refresh followed by retry and explicit dismissal. Faults are injected into actual requests or PostgreSQL, not a replacement service. The build passed with DATABASE_URL configured; the first build attempt without it failed at page-data collection. Quantifiers: for each of the four tested schedules and their created tokens, the listed observable assertions held. This is not a proof for every execution, browser, tab, network failure, row or deployment. The warning remains until dismissal or another attempt for that token; a refresh can fail and leave the earlier row visible alongside a list-staleness warning. The local lock is neither cross-tab nor durable. A successful response and a later list read can race other clients. Warning dismissal and another attempt do not prove the outcome of the earlier operation. List refresh can be superseded by another load; no linearizability claim.

## Six mechanism-distinct candidates
These are design alternatives considered, not six implemented or independently benchmarked solutions.
1. Ignore DELETE response (old artifact): cheap, but HTTP error or transport loss hides outcome; the two pre-patch tests defeat it.
2. Check HTTP status only: addresses non-2xx; attacker drops a committed response and list may remain stale. Lost-response test distinguishes it.
3. Remove row optimistically: quick feedback but rollback or unauthorized response makes a live token appear revoked; trigger-failure test attacks it.
4. Auto-retry DELETE: repeat-safe server transition helps, but cannot determine initial response or prevent repeated requests and hidden failures; hold and count requests plus lost-response test expose the boundary.
5. Server-side operation IDs/durable idempotency: potentially recoverable state across clients, but needs schema, retention, authentication and lifecycle semantics; not implemented or proven here.
6. Status validation, explicit ambiguity, unconditional refresh and local per-token lock (implemented): tested as above, but failed refresh, unmount, and other clients still constrain knowledge.

## Misleading shapes and their probes
A green build (browser fault tests); a 200 response (check body); a 500 (check real DB/auth); a rejected fetch (drop after server commit); a revoked badge (check bearer); a live badge (fail refresh after commit); successful refresh (also assert warning); a warning (assert exact token and retry); a disabled button (dispatch synchronous clicks and count requests); a single tab (cross-tab remains untested); a retry (check DB and warning independently); empty list (search exact ID); normal audit (trigger rollback); test cleanup (delete own IDs and trigger in finally); a passing targeted suite (run full gate). The modal shortcut is to test only the normal successful click: the trigger and dropped-real-response cases directly challenge it.
