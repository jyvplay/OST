# TT195 — type-ahead interaction boundaries

## Model and evidence threshold
Objects: a Files pane with a finite rendered, sorted/filtered list or grid, its keyboard prefix buffer and real browser DOM focus. Inputs: browser pointer-down, focus transitions, and keyboard events; access is the app's own UI and disposable VFS through its real API. Resource: one in-memory buffer per pane, 700 ms prefix lifetime; success is behavioral correctness, not a measured performance claim. For every relevant event sequence in a specified environment, pointer interaction or focus leaving the listing must end the old prefix, while focus transfers *within* the listing must not end a keyboard sequence. The specific acceptance experiment is a finite Chromium fixture, not a proof of that universal claim. A green build, real prepatch counterexample, postpatch browser regression and affected gates are the threshold for accepting the limited implemented claim; Class A would additionally require broader platform, AT and product evidence, which is absent.

H+: scoped resets can preserve list keyboard prefixes while preventing stale prefixes after external interaction. H−: if browser focus transitions or input events cannot distinguish these boundaries, this mechanism cannot ensure the property. H∂: focus reparenting, null related targets, touch/pen, alternate views, IME, and other browsers need separate evidence. No substitution of static source inspection for event behavior, synthetic events for a real IME, test fixture results for global compatibility, or accessibility recommendations for assistive technology testing.

## Frontier and portfolio
The [W3C APG listbox pattern](https://www.w3.org/WAI/ARIA/apg/patterns/listbox/) recommends single- and multiple-character type-ahead, especially over seven options, and distinguishes focus from selection; it does not specify this buffer boundary or prove actual screen-reader support. The remaining interface is how actual pointer and focus transitions interact with an application-local prefix without breaking multi-selection, drag, or normal focus movement.

1. **No reset:** prior production build and new browser test provide the counterexample: b, click alpha, c still searches `bc` and does not focus Charlie. Local failure, falsified by the test.
2. **Reset on every option blur:** construction would discard prefixes when type-ahead itself focuses another option. The existing `b` then `r` test is the cheapest attacker. Rejected without implementation; gap is local.
3. **Reset only on timeout:** existing 700 ms already bounds staleness; quick pointer attack still fails. Existing baseline is the artifact. Local failure.
4. **Reset on selection change:** focus-only type-ahead and modifier selections make selection a poor proxy for pointer intent; a click on an already selected option may be semantically unchanged. This is a causal counterexample, not an executed candidate. Local unresolved interface is event provenance.
5. **Capture pointer-down plus reset on focus leaving listing:** implemented, with containment check so keyboard focus movement within listing is retained. Real prepatch attack failed and postpatch tests pass. Remaining gaps include cross-browser/touch/AT behavior and pointer-cancel semantics. Local patch, not complete accessibility proof.
6. **Explicit interaction sessions driven by a separate state machine:** could distinguish programmatic, pointer, keyboard and focus events, but increases complexity and needs an independently tested event model. No implementation; cheapest falsification is the same browser attack plus keyboard continuation. Gap is broader interaction compatibility, not equivalent to the entire OS task.

The modal shortcut would reset on every blur because blur appears correlated with leaving the listing; it fails because moving from Beta to Bravo also emits blur inside the listing. The pre-existing rapid `b`, `r` test detects it. Other misleading shapes are enumerated in TT194; additional ones include pointer reset only after click (too late for canceled clicks), stopping propagation and breaking marquee, resetting only on mouse (missing pointer devices), applying one pane's reset to another, treating selection as focus, and counting a successful synthetic composition event as IME coverage.

## Reproduction and limits
Available and used: Node/TypeScript compiler via production Next build, ESLint, real Chromium 143, PostgreSQL disposable fixture, git/gh, web search and shell. No independent agents, theorem prover, expert review, or simulator was used. Actual browser baseline: TT194 2/3 with new pointer attack failing at Charlie; patched production build: 3/3 including rapid prefix preservation, pointer reset and listing exit/refocus. The tests use a mouse and programmatic focus for the exit boundary, not touch or real screen readers. No claim of ten Class-A promotions, all-app review, or a measured test speedup follows.
