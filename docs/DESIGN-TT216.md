# TT216: preset refresh and late completion

## Scope, model, and evidence threshold

The object is the Routines preset-list read after a create, in a browser connected to one app server and one disposable PostgreSQL database. Requests and responses can be delayed, fail, or arrive out of order; client timeouts do not cancel database work. Count wall-clock milliseconds, network reads/writes and persisted preset rows, not OS-feature grades. For each completed list read of the current generation, the UI may replace the prior list only if its response has the expected array/field shape and the client has not aborted; a failed current read must visibly mark the list as potentially stale, retain prior displayed rows, and expose retry. Older refreshes must not replace a newer one. If both reads used by `load` honor AbortSignal, the save lock is released after the 12,000 ms timer plus event-loop scheduling and response cleanup; this is not a hard real-time bound, and a frozen browser or noncompliant fetch is outside the model. Empty, loading, stale and successful list states must not be conflated. This does not establish restore fidelity, offline operation, safe retry, authorization, or correctness against legacy writers.

**H+**: conditional stale-result suppression and timeout handling are feasible in one mounted component, with actual examples verified below. **H−**: a client receiving no create response cannot deduce from an initially absent list that the create will not commit later: the experiment demonstrates precisely such an execution. **H∂**: stronger reconciliation needs persistent operation identity, a matching payload rule, atomic effect/result storage, retention and compatible writers. Last turn's `docs/DESIGN-TT215.md` gives the related seven mechanisms and 17 misleading result shapes; those are scoped conceptual alternatives, not implemented alternatives or proof of OS completeness.

Decision threshold for this patch: production build succeeds; a pre-patch browser attack demonstrates the hang; new hang/recovery, malformed data, and reordered-response attacks pass after repair; TT214, TT215 and TT157 affected suites pass; full gate result is recorded rather than presumed. This is evidence for the exercised cases, not a universal proof.

## Mechanisms, alternatives and attacks

1. **Generation counter (implemented):** only the latest read writes list state. Artifact: `loadSequence` in `Routines.tsx`; a held older real response released after a newer successful read did not clobber it. Attacker: an older response arrives last, or component unmounts and remounts; the latter was not tested. Gap: local component lifecycle, not the whole OS.
2. **AbortSignal deadline (implemented):** shared read controller bounds compliant browser fetches; hanging list test exercises the 12 s deadline and retry. Attacker: browser event loop freezes or fetch implementation ignores abort; no hard real-time guarantee. Cheapest test: stall both reads and measure under load. Local liveness gap.
3. **Response shape validation (implemented):** a successful HTTP response with non-array `rows` is rejected and shown as stale. Attacker: array entries individually malformed or large; simple field checks cover some, not all semantic constraints. Cheapest test: adversarial row corpus and length limits. Local validation gap.
4. **Serialize all reads (alternative, not implemented):** an explicit FIFO prevents reordered completion; a stalled head can block newer refreshes. Attacker: hold the first response forever. Falsify liveness with two real held requests. Local scheduling gap.
5. **Server snapshot/version token (alternative, not implemented):** monotonic revision on an inventory transaction allows comparing returned snapshots across clients. Attacker: deletions and legacy writers that fail to increment it, or counter rollback on restore. Test simultaneous legacy mutation. Gap spans writer interoperability.
6. **Durable idempotency record (alternative, not implemented):** bind operation ID and request fingerprint to creation and result in one database transaction, replay matching attempts. Attacker: same key different payload, expired key, deletion/recreation, or old clients. Test concurrent duplicate/mismatch and crash boundaries against real DB. Gap is operation identity, retention and deployment compatibility, not all OS features.
7. **Read after timeout as proof (rejected):** directly falsified by the TT216 late-commit experiment. A transaction holds an uncommitted conflicting insert; the UI's actual server insert waits; the client times out; a real list response and direct read both omit the preset; rolling back the blocker lets the original insert commit. This does not imply that retry is safe.

The PostgreSQL [Read Committed documentation](https://www.postgresql.org/docs/18/transaction-iso.html) describes statement snapshots and invisible conflicts with `INSERT ... ON CONFLICT DO NOTHING`; the [INSERT documentation](https://www.postgresql.org/docs/18/sql-insert.html) describes conflict arbitration. These are conditional database semantics, not proof of end-to-end acknowledgement. The experiment queries `pg_stat_activity` for a lock-waiting insert before timeout, rather than inferring blocking from elapsed time alone.

## Executed verification

Available and used: Node, Next production build/TypeScript, PostgreSQL disposable database, Chromium 143, Playwright and HTTP interception, shell commands, ESLint, web search, and test-only independent oracle packages. No independent agent, theorem prover, expert review or other browser was used. Test interception holds or modifies responses for fault injection; the persisted writes and database locking in the late-commit test are real, not a simulated database.

On the previous build the refresh-hang attack failed 0/1. On the final production build: TT216 refresh **3/3** (held list response, explicit retry recovery, malformed HTTP 200 list, out-of-order responses); late-commit **1/1**; TT215 **4/4**; TT214 **5/5**; TT157 **2/2**. The TT215 modal test positively opens the launcher without a modal then focuses behind the open dialog and attempts Meta+A: merely stopping propagation inside the dialog would miss that event. This is one shortcut/browser and not a comprehensive modality audit. Fixture uses exclusive disposable state; the late-commit test uses a PostgreSQL lock and rollback, then cleans its preset.

Earlier, before the final validation-only change, individual density suites on a fresh disposable database passed TT124 23/23, TT125 3/3, TT123 23/23 (Files 255/260 in TT125). That is not a repair of the previous full-gate failures: fixtures and accumulated state differ, and the full-gate Beam 12040 anomaly remains unexplained. No visual audit of all apps is claimed.

## Open boundaries

A list can become stale immediately after a successful read. Timeout and retry do not reconcile an in-flight creation; no idempotent retry protocol was implemented. Older writers, other tabs, a reset generation after remount, synchronous event-loop stalls, accessibility beyond the tests, and all restore state variants remain open. Existing Routines ESLint has a separate set-state-in-effect error. No ten Class-A promotions, original graphics, all-app visual review, or measured Pareto improvement was demonstrated; newly added tests increase gate work. Historical feature counts are not an independent estimate of modern OS parity. The next high-information test is a durable operation-ID design exercised across a late commit, retry with identical and different payloads, server restart, deletion/recreation and retention expiry.
