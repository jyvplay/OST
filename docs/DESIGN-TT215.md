# TT215: preset acknowledgement and restore boundaries

## Scope and verification model

This is a narrow investigation of preset creation, **not** a proof of an OS or a claim that any feature is Class A. Admissible requests are names and JSON desktop states sent by a browser to the same app/server and PostgreSQL database, with a unique `desktop_state.id`. The create-only client and server are from this branch; older clients, direct SQL writers, deletions and existing PUT are outside the concurrency guarantee. A save is confirmed only if a non-aborted HTTP success contains `{ok:true, revision:1}`. A 409 refuses a name; any other error, malformed success or timeout is unconfirmed. User-facing uncertainty does not assert rollback. Time is milliseconds; the client abort threshold is 12,000 ms and scheduling may delay it. No worst-case response bound is claimed for the subsequent list refresh.

A scoped safety target is: for each pair of overlapping new-operation creates for an absent identical key, assuming one shared functioning database and no concurrent delete/legacy write, at most one insert succeeds, and the loser cannot overwrite the winner; if no confirmed response reaches the client, it must not claim a save. The test provides examples, not a universal proof; PostgreSQL's unique-key enforcement is the mechanism underlying the conditional argument. Liveness (eventual save or bounded completion under arbitrary network/database failure) is a different target and is not established. Restore success in one case is not full layout/props fidelity, cross-device synchronization, offline durability, multiwriter linearizability, or OS completeness.

**H+**: under the stated shared-database, create-only and no-conflicting-delete assumptions, the design is achievable; the test observes one winner and one 409. **H−**: with an indefinitely lost response, the client cannot infer from silence alone whether the server committed: the same observation is compatible with commit and no commit. No universal eventual response bound can be guaranteed against an indefinitely stalled dependency. **H∂**: a durable request identifier and server-side result retention could support safe reconciliation/replay, under additional assumptions about retention, atomicity and access. A refresh alone cannot settle an in-flight request.

External reference: PostgreSQL [transaction isolation](https://www.postgresql.org/docs/18/transaction-iso.html), Read Committed: `INSERT ... ON CONFLICT DO NOTHING` may decline insertion due to a concurrent transaction not visible in the command snapshot. This implementation does not require returning the conflicting row or treating it as visible in that statement. PostgreSQL [INSERT](https://www.postgresql.org/docs/18/sql-insert.html) describes conflict targets and `RETURNING`; the primary key is the arbiter. These are imported database guarantees, not independent proof of application-wide semantics. Exact open interface: shared-DB create arbitration does not protect against legacy PUT, delete, arbitrary SQL, lost acknowledgements, or later restoration of malformed state.

## Competing mechanisms and adversaries

These are candidate constructions, not six implemented alternatives or proofs. Their cheapest falsifications are concrete next experiments; no result is implied unless listed above.

1. **Atomic unique-key insertion** (implemented): `ON CONFLICT DO NOTHING RETURNING` makes collision arbitration part of the insert. Evidence: two concurrent HTTP creates, 200/409. Attacker: concurrent delete followed by legacy PUT; outside the scoped guarantee. Falsify with coordinated transactions and that writer; gap local to writer interoperability.
2. **Check then write**: executable existing `PUT` path illustrates this different design; two sessions can both see absence or stale state. Attacker holds both reads before writes; cheapest test is a DB barrier-controlled two-client race. Gap is local atomicity, not proof of a complete OS; not selected for new creates.
3. **Per-key advisory lock**: executable SQL design `pg_advisory_xact_lock` followed by read/write. It serializes only cooperating writers sharing the lock scheme, not arbitrary SQL; attacker issues an unlocked PUT. A two-connection lock test falsifies broader protection. Local interoperability gap.
4. **Serializable transaction and retry**: execute a read/write transaction at SERIALIZABLE and retry serialization failures; attacker forces repeated conflict or an uncooperative write outside transaction. Cheapest test is concurrent isolation-level transactions and bounded retries. Ordering is conditional on successful transactions and does not solve response loss; local retry/liveness gap.
5. **Durable idempotency key**: persist request ID, operation result and mutation atomically; duplicate requests return the saved result. Artifact is this transaction design, not implemented. Attacker reuses IDs with different payloads, or retries after record expiry; test both against a real store. Gap is local operation identity/retention and protocol evolution, not the entire original OS task.
6. **Timeout plus honest uncertainty** (implemented): abort the browser request after 12 seconds, do not retry, warn that completion remains possible. A held response after real commit tests it. Attacker delays commit until after a list refresh; neither timeout nor refresh proves rollback. Cheapest test releases a blocked server-side transaction after the warning; unresolved reconciliation is local but essential for safe retry.
7. **Explicit overwrite with compare-and-swap**: conditional `UPDATE ... WHERE id=? AND revision=? RETURNING`, with a separate create-only path. Attacker changes or deletes/recreates the row between confirmation and update; generation identity or sufficiently robust version semantics are needed to address ABA. Test a delete/recreate barrier race. This alternative is not implemented; overwrite remains unavailable.

## Fifteen misleading result shapes

1. HTTP 200 with no valid acknowledgement; 2. a toast after a failed PUT; 3. a list refresh before an in-flight commit; 4. abort interpreted as server rollback; 5. an automatic retry after a lost response; 6. two concurrent writers passing separate existence checks; 7. equal revisions interpreted as ownership; 8. timestamps truncated to fit int4 but not monotonically ordered; 9. a 409 presented as a successful overwrite; 10. a modal visually covering the page while global shortcuts still fire; 11. an intercepted fake response presented as a real network incident; 12. one restored window presented as full props and multi-workspace fidelity; 13. same-version create safety generalized to older clients; 14. unit-only success presented as browser/database verification; 15. a faster setup phase presented as a faster complete gate; 16. a density cap passed by hiding working actions; 17. a green targeted suite presented as full OS readiness.

## Remaining gaps and next test

Test delayed server commit *after* the timeout and the first refresh, then design explicit reconciliation with durable operation identity before claiming safe retries. Test restoration of multiple windows, props, workspaces and reload, plus delete/recreate ABA, legacy writers and simultaneous tabs. The create action has no overwrite UI and list refresh itself can hang. All-app visual review, original graphics, ten production-ready Class-A promotions and a significant measured Pareto improvement were not completed. Historical self-assessed ledger numbers do not establish a meaningful distance to modern OS parity; an independently reviewed per-feature acceptance matrix and real platform capability tests are needed. Full-gate outcome is reported separately after the run completes.
