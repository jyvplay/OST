# TT196 — retain Files keyboard focus when clearing selection

## Formal scope and evidence threshold
Admissible objects are real Files panes, their current visible ordered options, a selection set, an anchor, a logical focus and the browser's active element. Access is through a production Next app, real Chromium keyboard input and a disposable PostgreSQL-backed filesystem; no production dependency or external code is added. Counted resources: one existing focus path and O(n) membership check on Escape; no runtime performance improvement is claimed. For each tested scenario, after Escape clears a nonempty selection while a visible option owns DOM focus, selection must be empty and focus remain on that option; subsequent Space, arrows and Enter must operate on that option. When focus belongs to the background, Escape must not invent an option. This is a finite browser test, not a proof for all event sequences, browsers, assistive technologies, or arbitrary dynamic changes. Acceptance threshold for this bounded change: real prepatch counterexample, production compile, patch-specific attacks, affected browser tests, and transparent full-gate results. Passing these does not establish Class A.

H+: retaining the actual focused visible path separately from selection repairs these sequences. H−: if the DOM option is detached or order has changed between keydown and render, the path may not identify a viable option; a one-event state update cannot prove focus behavior in all asynchronous environments. H∂: background, other panes, column buttons, IME, dynamically removed files, alternate keyboard shortcuts and AT need separate treatment. Adjacent but different questions include selecting a focused item, maintaining selection on arrow movement, type-ahead matching, restoring focus after unmount, and operating-system accessibility conformance.

## Prior guidance and boundary
[W3C listbox guidance](https://www.w3.org/WAI/ARIA/apg/patterns/listbox/) distinguishes DOM focus from selection and describes multi-selection models. This recommendation is relevant but does not mandate Escape semantics, prove this implementation, or substitute for real assistive-technology testing. No third-party implementation was copied. The open interface is the app-specific coordination of logical focus, DOM focus, selection, filtering, view changes and browser events.

## Portfolio and strongest attackers
1. **Existing `emptySel()`**: actual baseline is 0/3: beta remains DOM-focused but has tabindex -1 and Enter does not open a focused folder. Attacker presses Escape then Space/Enter. Fails locally.
2. **Clear selection and restore the previous selected path**: causal counterexample: Ctrl+Arrow moves focus independently of the selection. New test explicitly selects alpha, Ctrl+Arrow to beta, clears and selects beta. Local gap: focus is not selection; unimplemented.
3. **Clear selection and keep previous logical focus unconditionally**: causal counterexample: focus is on the listing background or a column control rather than an option; it would invent an active option. Background attack checks that Space does not select beta. Local gap; unimplemented.
4. **Keep DOM focus but derive only Enter/Space from DOM**: baseline already retains DOM focus, but roving tabindex is wrong and arrows use selection focus. The beta tabindex and arrow tests falsify this partial approach. Local gap; unimplemented.
5. **Retain the path of the event's actual visible option**: implemented; membership guards background/stale paths. Real postpatch tests exercise list, grid, selection different from focus, background and Enter on a folder. Remaining interfaces include dynamic unmounts, cross-browser and AT; this is local, not a solution for the whole OS.
6. **Redesign as aria-activedescendant container**: a different focus mechanism that could centralize DOM focus, but would require revalidating scrolling, drag, multi-pane, context menus and AT. No implementation; cheapest attack is the same Escape/Enter regression plus drag and screen reader tests. Global widget integration gap, not equivalent to the whole OS.

Modal shortcut: preserving `selNow.focus` unconditionally is tempting because it tracks focus normally, but becomes stale when the background owns focus; the background test detects invented focus. A separate stale-selection attack rejects preserving the selected item instead of focus.

## Negative space
Misleading results include: DOM focus retained but logical focus lost; correct Enter but broken Space; correct Space but broken arrows; correct selection but wrong tabindex; first selected row mistaken for current focus; multi-selection accidentally retained; anchor incorrectly retained; background given a phantom current option; stale filtered-out path accepted; grid omitted; folder opening not tested; only synthetic events; relying on ARIA attributes without real keyboard input; a green build without runtime test; type-ahead test substituted for Escape test; keyboard test substituted for screen reader verification; Ctrl+Space collision overlooked; a single Chromium fixture treated as all browsers; ignoring the full gate; counting the repair as ten features. These are possible false positives, not claims all were independently tested.

## Experiments and limitations
Tools actually used: shell, git/gh, web search, Node/TypeScript production build, ESLint, real Chromium 143 and disposable PostgreSQL, with independent gate oracles where the gate invokes them. No independent agents, theorem prover, expert review, or simulator was used. Prepatch test: 0/3 (list and grid wrong tabindex; folder Enter fails). First postpatch run 3/4 because an exploratory Ctrl+Space attack opened the existing shell command palette and intercepted the following click; this exposed a shortcut collision, not a clean test of the fix. The test was changed to unmodified Space, retaining the Ctrl+Arrow focus-only attack. Ctrl+Space conflict is unresolved, not claimed fixed. Postpatch 4/4 before adding the separate background attack. Real IME, AT and other browsers remain unverified. No broad visual review, original artwork, ten Class-A promotions or test speedup was established.
