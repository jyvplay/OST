# TT158 — local automation planner token honesty

## Scope and model
The object is one in-memory local planner token, containing 96 bits generated by the browser CSPRNG, a routine identifier, exclusive expiry in milliseconds and a used flag. Input is a pasted JSON request and an explicitly user-selected routine in one mounted Routines component. No request origin in that JSON is authenticated. For every valid issued token and ordered sequence of local checks, a missing/wrong secret, wrong routine, used token or expired/non-finite expiry must refuse without granting success; at most one matching check before expiry succeeds, and invalid checks do not consume it. Execution is out of scope: Plan never runs actions. This is not authentication for `/api/automation`, browser-origin security, persistence across reload, multi-tab coordination or constant-time server authentication.

H+: the bounded single-component planner can check a supplied token and consume it. H−: it cannot authenticate a remote origin from user-supplied JSON or serve as a server security boundary. H∂: cross-origin request security requires a separate trust boundary, real HTTP headers, credentials and threat model. OWASP's [CSRF guidance](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html) describes server verification of browser-set Origin/Referer and its caveats; it does not validate this local planner or prove the server API secure. No external implementation was copied.

## Six mechanisms and attacks
1. **Local compare and consume**: `src/lib/automation-entry.ts` checks secret, routine, expiry and used state, then marks the same object used. Pure test exercises wrong secret, wrong routine, replay, expiry boundary and non-finite expiry. Real Chromium checks missing/wrong secret, success, replay, and no execution. Gap: same JavaScript object in one component only; global security remains open.
2. **Metadata-only check** (old code): wrong presented secret and replay are counterexamples, since neither was checked or consumed. The new pure test fails against the old signature and the UI regression requires actual selectable tokens. Gap is local; eliminated for the bounded model, not for server security.
3. **Server-side atomic token redemption** (not implemented): a conditional database update could serialize requests, but requires actual authenticated ingress, hash comparison and transaction semantics. Attacker concurrently redeems from two processes or loses acknowledgement. Cheapest falsification: two real simultaneous HTTP requests and DB observation. Global gap for a real remote entry mechanism.
4. **Trusted server Origin/header checks** (not implemented here): compare browser-provided request metadata against configured canonical origins with proxy-aware policy; a pasted field is not evidence. Attack missing/null Origin, non-browser requests, untrusted proxy and CSRF. Cheapest falsification: real cross-origin browser requests. This is a separate server security design, not the planner's fix.
5. **Signed capability** (not implemented): signed scoped expiry may make a capability verifiable without storing each secret, but signatures alone do not prevent replay. Attacker reuses a valid signature. Cheapest falsification: duplicate delivery. Global gap requires replay storage and protected key.
6. **Disable cross-origin automation** (not adopted): denying all remote calls minimizes attack surface but removes existing functionality. Attacker is a legitimate user with a valid external workflow; cheapest test is a real bearer-token enqueue and drain. Preserving that workflow requires testing the separate API rather than deleting it.

## Misleading result shapes
1. A plan is not execution. 2. A supplied origin is not browser-verified origin. 3. A token's presence is not matching its secret. 4. A used flag is not enforcement unless updated. 5. A first success is not replay prevention. 6. A routine name is not a unique identifier. 7. A local token is not the API bearer token. 8. A UI check is not server authorization. 9. Expiry after the boundary is not expiry at it. 10. NaN is not a valid expiry. 11. A CSPRNG token does not prevent XSS. 12. Hiding a token from an abbreviated display does not make it unusable safely. 13. One tab's state does not coordinate other tabs. 14. A green pure suite is not end-to-end proof. 15. An end-to-end pass is not a full project gate. 16. A historical ledger is not release acceptance.

## Evidence and exact gaps
Before patch, `tt158-entry-token` failed against the previous function and the browser attack failed waiting for a routine selector absent in the previous UI; these are not claims that the old UI's full attack path was measured. After patch, pure 1/1 and production Chromium 1/1 passed; production TT157 browser 2/2, TT141 browser 8/8 and TT146 5/5 passed on the first revision. The finite-expiry hardening was followed by a fresh build and pure rerun; the final gate result must be consulted separately. TypeScript and production builds passed. No independent agents, simulator, theorem prover or expert review were used. Node, Next/TypeScript, Chromium, PostgreSQL and external documentation were used.

Scope boundaries: the local token is shown in the page and can be read by scripts in that origin; it is not a protective authorization boundary. The separate actual bearer API was not modified or independently security audited here. Its queue/settlement multi-window races and external-origin protections remain open; test two simultaneous real browser shells and hostile cross-origin HTTP requests before asserting stronger security. No 20 Class-A promotions, all-app visual review, original graphics or measured test-speed gain are claimed.
