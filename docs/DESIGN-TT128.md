# TT128 — honest calendar, photo and PWA boundaries

## Full turn report and decision

This turn strengthens existing behavior rather than certifying a complete OS. It contains many discrete repairs, but **does not deliver or certify 20 independent new Class A features**, does not establish that every existing feature is Class A, and does not make a browser into Android or a fully offline OS. The original Android specification has privileged and hardware-dependent requirements a PWA cannot implement. Existing register/ledger counts are historical, author-written classifications, not independent proofs. No feature was promoted on the strength of this turn's test tags.

The work was done on `arena/f945505b-ost`, starting from `03839e1`. Changes span Photos, iCalendar/Planner, Clock, the service worker, decorative empty states and repeatable tests. The detailed results and limits below are the evidence for this turn, not a retroactive claim about earlier runs.

## Formal target, frontier and hypotheses

Let E be an environment consisting of the current Next.js server, one PostgreSQL database, a same-origin service worker and browser, and the current cooperating application code. Let inputs include VFS photo rows/reads, calendar content and task imports, time-zone/date inputs, service-worker network/storage faults, and interleavings of writes. The intended invariants are quantified over **all** inputs and interleavings satisfying the stated preconditions, not just the fixtures below:

- If a Photos viewer is opened on a shown sequence S, navigation stays in the surviving paths of S for that viewing session, even if EXIF indexing changes the library's later order. A failed or stale identity read must not be recorded as proof of absent metadata.
- For an import UID U, if all concurrent importers run the new cooperating server against the same database, at most one importer adds a previously absent U; other importers observe and skip it. Empty UIDs are not deduplicated. A multi-event import is **not** one all-or-nothing transaction.
- For a conditional file write with a previously observed identity, if a cooperating ordinary write commits first, the stale conditional write refuses. Nothing prevents a later unconditional write from replacing a conditional winner.
- An update with a failed precache must not replace the active worker, and an installed update waits for user action. `/api/` fetches are network-only; cache contents are limited by the worker policy. A browser with no usable cached app/data is not claimed to operate offline.
- For a supported local wall time, the converter returns an instant only if it maps back to that wall time; a gap refuses and an overlap requires an explicit choice. Date calculations refer to calendar labels rather than fixed 24-hour durations where implemented.

These are design goals with finite tests, **not universal proofs**. Resource bounds include the VFS normal write cap of 8 MiB, a 20,000-row media query cap (including sidecars), the recurrence cap of 512 returned occurrences and bounded iteration, and 17 offset samples across a 96-hour window per conversion. The benchmark host exposed two CPUs; no hard resource bound on all app work is proven. Dependencies, availability and scope also matter: the real database and test browser were local and disposable, not an untrusted server or actual mobile device.

- **H+ (still open in general):** identity guards, row locks, a UID-scoped advisory lock, and readiness checks can preserve the named local invariants. The targeted races and negative tests support specific cases; they do not prove every execution.
- **H− (supported boundary):** cache entries, test tags or UI controls cannot create native Android privileges, an offline database, exactly-once distributed writes, physical-device validation, or a security audit. Real tests also demonstrate that a later ordinary writer may replace the earlier conditional result.
- **H∂ (unresolved frontier):** old/noncooperating servers, raw SQL, commit-acknowledgement loss, browser/cache quota policy, old private caches, timezone data and historical transitions, recurrence interoperability, initial-install offline use and deployed security/authentication remain decisive. A transition from H∂ to a universal or Class A claim needs independent review, representative devices/browsers, failure/recovery tests and all original success predicates—not a higher test count.

The adjacent problems are not equivalent: mutually cooperating writers versus all possible writers; desktop cache versus offline VFS; screenshots versus all interactive states or accessibility review; a date-time converter versus an alarm scheduler; an RRULE preview versus interoperable recurring events; and browser/PWA behavior versus Android APIs.

## False-solution result shapes rejected

The modal shortcut is **counting visible controls or green tags instead of checking outcomes**: Photos already had sorting/navigation controls, yet asynchronous EXIF could reorder a viewer underneath Next. The forced delayed-real-read regression distinguishes a working control from that failure. Additional non-equivalent result shapes are:

1. A page rendered, therefore every button works (rendering alone is not the interaction).
2. Twenty labels/tests, therefore twenty independently completed features (explicitly not claimed).
3. A passing self-round-trip, therefore an interoperable ICS file (cross-checked with `ical.js`, still partial).
4. Seventy-five JavaScript characters, therefore at most 75 UTF-8 octets (multibyte counterexample tested).
5. Replacing every `\\n` twice, therefore literal backslashes survive (TEXT round-trip counterexample tested).
6. A nested alarm SUMMARY is the parent event title (nested component case tested).
7. The final property wins, therefore a VTODO due date is correct (both property orders tested).
8. `NOT-COMPLETED` contains `COMPLETED`, therefore the task is done (exact status test).
9. Parse any RRULE and ignore unsupported keys, therefore preview is faithful (unsupported rules now refuse).
10. A floating/UTC timestamp is a preserved TZID and recurring wall time (known unresolved mismatch).
11. A monthly clamped preview equals RFC invalid-date skipping (explicitly disclosed mismatch).
12. A single UTC offset works for every local wall time (gaps/overlaps cross-checked with Temporal).
13. A 24-hour duration is the next local calendar day (Santiago counterexample in real Chromium).
14. A cache entry named `date` is necessarily a capture date (legacy file-date counterexample tested).
15. A failed photo read proves no EXIF (network-abort and retry test).
16. A matching stored hash proves independently recomputed image bytes (not established).
17. One winning conditional writer prevents a later unconditional overwrite (real PostgreSQL counterexample).
18. A UID existence check followed by insert is automatically atomic (real forced race and lock-removal mutation).
19. A successful worker installation with a swallowed precache error preserves the old shell (real failed-upgrade test).
20. A cached desktop page means server data are offline (API intentionally returns 503; cold root remains unproven).
21. A cache quota error means the network resource is unavailable (VM cache-failure attack).
22. An update can reload immediately without risking an edit (browser verifies user-controlled waiting).
23. Screenshots or one axe run establish human accessibility and visual quality (neither is claimed).
24. Two successful timing runs prove a global CPU/wall Pareto frontier (not claimed).
25. A correct insertion function guarantees a user's selection will still be current after a delayed UI callback (real browser counterexample and repair).

## Timing and repeatability

At benchmark time, the same four-case `e2e-tt120.mts` was run with a real Chromium and the same disposable dev server/database on a two-CPU host. Baseline wall times were **30.877, 28.357 s** (mean 29.617 s); the readiness version was **24.679, 23.117 s** (mean 23.898 s), approximately 19.3% lower wall time in this small sample. CPU timings varied substantially, including baseline user times 16.828 and 40.069 s; no CPU or global Pareto superiority is asserted. Runs were not randomized or pinned to isolated CPUs, and the complete gate now includes additional tests. The assertions were not removed, and the Clock heading readiness was added. After those measurements, the navigation check was further strengthened to match the exact position label (so `11 of …` cannot masquerade as `1 of …`); that later test change was not part of the speed comparison.

Reproduce on a disposable database/server with `BASE=... DATABASE_URL=... JOBS=2 bash scripts/run-gate.sh`. `scripts/run-fast.sh` still runs the network-dependent `oracle-ai` separately in its no-argument default; the explicit gate list deliberately does not include it. The optional independent `tt128-oracle.mts` requires test-only `ical.js@2.2.1` and `@js-temporal/polyfill@0.5.1` installed under `TOOLS_DIR` (default `/home/user/tools`); absence fails rather than silently skips. `tt128-visual.mts` captures review PNGs under `VISUAL_OUT` or `/home/user/.cache/ost-tt128-visual`; it changes default desktop state temporarily, so it too requires an exclusive disposable server and database.
