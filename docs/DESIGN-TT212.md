# TT212 — recheck the clock between backup Trash requests

## Model and evidence threshold
Objects: Backup UI, its captured list of file names and guards, a valid/invalid browser clock, real guarded `/api/fs` Trash requests and an exclusive disposable PostgreSQL-backed application. For each sequential batch started from an eligible captured list, before each next request the client samples its clock. If the sampled time is invalid or makes any dated name in that list future, no subsequent request in that batch is intentionally sent; any earlier successful requests stay moved to Trash and the existing partial/uncertain warning is shown. This is a point-in-time client condition, not a guarantee against a clock change after the check or an independently modified inventory. Dates are local calendar filenames with minute precision; any strictly future timestamp is treated as uncertain. Counted resources: scans of the captured names before each request, extra browser test time and DB/API operations. It does not provide atomic batches, rollback, trusted real time, real creation order, continuous monitoring, a persistent future-date history, escaped/unobserved changes, all-browser accessibility, Class A, or PWA-wide completion.

H+: a per-request recheck can prevent later requests after an observed clock reversal. H−: without a transaction spanning the inventory and all destructive writes or a trusted generation order, this client cannot guarantee correctness under every concurrent update and clock schedule. H∂: failures depend on precisely when the clock changes relative to the check/request and on visibility of the captured inventory. Threshold: a failing real-browser prepatch attack that actually commits the first Trash, patched regression, independent existing save/inventory/prune/conflict checks, production build, lint reporting and full-gate report. This evidence supports only the specified observed behavior.

## Frontier and mechanisms
PostgreSQL [Read Committed documentation](https://www.postgresql.org/docs/current/transaction-iso.html) states a nonlocking SELECT sees a snapshot committed before the statement began, not a snapshot frozen across independent client requests; stronger isolation has different semantics and may require transaction retry. A client-side preflight list followed by separate Trash requests is not a serializable batch. We independently wrote the patch; no outside code was copied.

1. **Single pre-confirm check**: baseline actual attack sends two Trash operations after the clock reverses during the first. Local counterexample and local gap.
2. **Post-confirm check only**: TT211 did this. Real attack holds the first response after an actual DB commit, changes the browser clock, then releases the response; baseline sent two requests. Local gap.
3. **Check before each Trash**: implemented. Attacker changes time after the check but before or during the request, or creates an unseen future-dated file. These remain; the patch only stops subsequent requests once the state is observed. Requires server-side protocol for broader guarantees.
4. **Refresh inventory before each Trash**: could detect some intervening changes but another writer can modify it immediately after the refresh; partial batches and failed lists complicate behavior. Not implemented. Cheapest attack: create a future file between list response and Trash. Cross-layer gap.
5. **Server-side atomic batch with verified inventory generation**: could compare identities and apply a batch in one transaction if all relevant writers participate and conflict/ack semantics are defined. Attacker inserts a matching file via an uncoordinated writer. Not implemented; cross-layer architecture gap.
6. **Persistent monotonic generations**: could order new backups independently of wall clock, but migration, legacy files, imports, storage failure and multi-writer allocation need an explicit protocol. Attacker imports legacy names or clock-skewed historical files. Not implemented; cross-layer gap.
7. **Disable all pruning**: avoids this failure but removes useful ordinary retention; normal prune regression is a counterexample to acceptance. Not implemented.

Rejected misleading shapes: first request cancelled after actual commit; successful response assumed all targets moved; warning suppressed after partial batch; clock checked only before confirmation; mocked database represented as real; rechecking unchanged names described as refreshing inventory; `Date.now` considered trusted wall time; old guards proving all inventory unchanged; total batch called atomic; changed clock after last request retroactively rolled back; future dates permanently remembered; browser clock control called a real device clock adjustment; one Chrome run claimed cross-browser; density cap raised to pass; stale response ignored without testing; failure while saving called rollback; speedup claimed from smaller test; test runner feature counted as ten Class-A app features; partial suite called full gate; an open PR called merged.

## Actual observations and limitations
Available and used: git/gh, shell, Node 22, production Next/TypeScript build, ESLint, Chromium 143 via Playwright, real disposable PostgreSQL, and web search. No independent agents, theorem prover, simulator, or outside expert participated. The controlled browser clock is not an OS clock change. Test interception uses `route.fetch()` to execute a real Trash request before changing the page's clock and releasing the real response. Before the patch TT211 browser suite 1/2: the new attack observed 2 requests rather than 1. The first patched run caught a mistaken test expectation about deletion order; the actual prune plan deletes the 2025-01-01 copy before 2024-12-31. Corrected test passes 2/2, with exactly one committed Trash, the next target still live and the partial warning present. Existing real browser TT172 4/4, TT173 4/4, TT174 2/2, TT175 2/2, TT176 7/7; production build passed. The full-gate outcome is appended below.

I visually inspected only Backup at 1150px wide (local Chromium screenshot); its export toolbar wraps and explanatory copy is text-heavy. No all-app visual audit, redesigned graphics or Class-A promotion is claimed. The extra per-request check adds work, and no script-speed or Pareto improvement has been measured. TT211's note that no mid-batch check existed is historical; clock changes between an individual check and the request, mid-request commits, stale inventory, cross-tab concurrency and a clock later catching up remain unresolved. Highest-information next test is an adversary inserting a new future-dated file after listing but before a guarded Trash, followed by design of an atomic server-side batch/inventory contract rather than falsely calling another client fetch atomic.

## Full gate and stronger attacker
Full gate `.cache/gate/20261121T070650Z/run-114493-n9e1s0` exited 1: TT211 browser 2/2, TT173 4/4, TT174 2/2, TT175 2/2, TT176 7/7, Find/Notes TT133 27/27 and e2e-a11y 9/9 passed. TT134 review repairs 6/8 (GitHub framing was unknown instead of deny), TT124 Routines 332/300, TT125 Files 375/260, and TT123 Files 375/320 failed. These failures also occurred in previous full runs. TT133 passing this time does not explain or erase the two TT211 failures of the regex paint assertion. No thresholds were relaxed.

The next attacker was actually executed after the gate in a disposable DB: `scripts/tt212-backup-stale-attack.mts` opened Backup with four past-dated copies, inserted a future-dated copy through the real API after the UI list loaded, then clicked prune. The UI moved two past copies to Trash despite the now-future-dated new copy. The script printed `COUNTEREXAMPLE`, checked all five actual database states and purged only its own fixtures. It intentionally demonstrates a known gap; it is not included in the passing gate and must not be read as a safety guarantee. A proper repair needs a verified atomic server-side inventory/Trash contract, accounting for uncooperative writers and unknown commit outcomes; repeating client-side checks alone cannot eliminate the race.

## TT213 follow-up
A guarded server operation now rejects the observed stale-inventory schedule for participating VFS writers; `docs/DESIGN-TT213.md` describes its model, real tests and boundaries. The historical counterexample above was observed before that repair; its script now verifies refusal in that same schedule. This is not a whole-batch or uncooperative-writer guarantee.
