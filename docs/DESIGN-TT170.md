# TT170 — early Fusion launcher activation

## Formal scope and evidence threshold
Admissible object: Fusion-layout server-rendered launcher button in the real PWA and the TT130 amnesic privacy regression. Information: repo and public documentation; exclusive disposable PostgreSQL, real HTTP, real Chromium and delayed JS responses through Playwright. Resources: test verdicts and wall time; no throughput improvement is asserted. For each tested schedule, before boot the Fusion launcher must be disabled, after boot it must respond to activation, including an injected bootstrap failure; the TT130 privacy test must still verify a 423 and no database write. Browser timeouts are finite test bounds, not service-level guarantees. Success is limited to the particular tested build and schedules, not all browsers and every action. Local commit requires a pre-repair counterexample, production build, new attack on the repair, affected regression tests, and documented remaining gaps; merge requires the full gate plus review of main. Do not substitute a disabled button for entire-app readiness, a passing isolated regression for a clean gate, or a synthetic delay for proof of the previous intermittent failure's cause.

H+: this bounded guard can prevent premature launcher activation. H−: the old build exposes an enabled server-rendered launcher before scripts run; no global impossibility result is established. H∂: JS-disabled behavior, bootstrap failure, layout changes and React hydration affect the answer. Available and used: git/gh, shell, web search, Node, Next/TypeScript, Playwright/Chromium, disposable PostgreSQL. No independent agents, theorem provers, simulators, human reviewers or assistive-technology testing were used.

## Frontier and hypotheses
Playwright documents that apparent actionable controls may precede hydration and recommends fixing readiness in the application (https://playwright.dev/docs/navigations#hydration). This guidance assumes the site renders static controls before their handlers are attached; it does not prove what caused TT169's Launcher timeout. React documents effect cleanup on unmount and changed dependencies (https://react.dev/reference/react/useEffect); it does not certify shell bootstrap. No global optimality or impossibility theorem is known here. Open interface: distinguishing actual TT130 intermittent failure causes, plus the remaining unguarded controls and layouts.

## Candidate mechanisms and attacks
Each is a falsifiable design artifact, not a claim of implementation or proof. All gaps are local except whole-shell readiness which spans the original broader task.
1. Ignore early actions (old markup): actual browser with held scripts shows enabled button before boot; gap is false affordance. Attack: activate with JS delayed.
2. Fixed sleep before click: executable design sleep then click; arbitrary slowness exceeds any chosen wait; attack with delayed script beyond it. Gap: deterministic readiness.
3. Retry clicks until dialog appears: executable design repeated click; toggle may close an already-open dialog. Attack delayed state update. Gap: avoiding repeated side effects.
4. Wait for shell-ready only in tests: deterministic test signal, but user still sees enabled nonworking button. Attack real click before hydration. Gap is product usability.
5. Queue and replay early events: design needs trusted event buffering, timing and duplicate suppression; attack click on control later removed or native behavior already performed. Not implemented; whole-shell safety gap.
6. Disable Fusion launcher until shell-ready (implemented): native disabled property in server HTML, enable after boot, preserves same launcher. Attack no JS, failed bootstrap, keyboard, switching layouts; tested cases and limitations recorded below. Gap is remaining controls/layouts and universal scheduling.
7. Client-only shell: removes SSR interaction window but sacrifices rendering/availability; attack JS-disabled and offline startup. Not implemented; whole-shell gap.

Misleading shapes and probes: 1 HTML presence vs handlers (hold JS); 2 visible vs enabled (inspect disabled); 3 enabled vs responding (open actual dialog); 4 one click vs repeat toggle (do not retry); 5 hydration vs bootstrap (check shell-ready); 6 boot success vs failed service (abort bootstrap); 7 mouse vs keyboard (Enter); 8 visible warning vs privacy isolation (real 423 and DB count); 9 test page vs live backend (real HTTP); 10 isolated pass vs full gate; 11 Fusion vs Art/Business; 12 a button vs all controls; 13 timeouts vs causes; 14 error response vs no commit; 15 one viewport vs accessibility; 16 wall time vs Pareto proof. The modal shortcut of clicking as soon as HTML is visible is attacked by delaying actual application JavaScript; old production demonstrably leaves the button enabled in that condition.
