# TT211 — future-dated backups and clock uncertainty

## Scope, model and evidence threshold
Objects: local dated backup filenames, browser-local last-built timestamp, current device clock, and guarded Trash requests through the actual Backup module and `/api/fs`. A filename is dated only if the existing strict local-calendar parser accepts it. A clock is uncertain for retention if it is invalid or any parsed filename resolves strictly after the current time (zero skew allowance). In this bounded model, for any inventory and time: a future timestamp must not be labelled fresh; no plan can select a Trash target when the inventory contains a future-dated copy or the current time is invalid. When inputs are known and not future, existing sorted keep-N behavior remains. Prune rechecks the same inventory after the confirmation returns. Last-built timestamps and filenames have different precision (milliseconds versus minutes). One millisecond ahead is uncertain; equality is not. This is a fail-closed availability tradeoff, not proof the device clock is correct.

Access/resources: browser clock and observed list, process memory, API responses, bounded tests on a two-CPU machine. No trusted real time, durable sequence, atomic whole-inventory check, or information about offline downloads is assumed. A competing tab can change the inventory after the list was read; guarded Trash protects the target identity but does not establish a globally atomic inventory snapshot. Distinct problems: archive integrity, restore success, offline persistence, always knowing the real chronological order, exactly-once create, timezone-independent names, monotonicity across clock resets, and full OS/Class-A completeness.

H+: refusal while a future timestamp is observed avoids the demonstrated false-fresh and wrong-retention cases. H−: with no independent clock or durable trustworthy ordering, a system cannot infer true backup chronology from wall-clock strings alone when the clock has been corrected. H∂: outcomes depend on timezone/DST, the timestamp crossing into the past, independently modified inventory, stored state, and clock validity. Declared threshold for this narrow patch: a prepatch counterexample, unit boundary and correction attacks, a real Chromium/PostgreSQL check that no Trash request is sent, existing guarded-delete and save regressions, production build, and clear full-gate reporting. This threshold is not a Class-A certification.

## Frontier and alternatives
A documented real-world issue shows clock correction can make timestamp retention delete a newer backup ([issue](https://github.com/b-relay/rig/issues/565)); it is an example, not a theorem about this implementation. A separate review explains that merely classifying an observed future timestamp as unknown does not preserve that uncertainty once the clock catches up ([issue](https://github.com/coe0718/diaktoros/issues/1905)). No third-party code was copied. The exact open interface is durable, trustworthy generation ordering across clock corrections, restarts, imports and concurrent writers, together with an atomic inventory policy; filenames alone cannot supply it.

1. **Clamp negative age to zero**: original code labelled the future as fresh; baseline test fails. Attacker sets clock backward. Local false-positive gap.
2. **Ignore only future files while retaining older ones**: preserves future files but can still delete an older valid copy when relative creation order is unknown. Counterexample: two post-correction copies and multiple pre-correction future files. Local retention gap.
3. **Refuse the complete plan for a future filename**: implemented; unit baseline future scenario would trash two older entries, patched plan returns none; real browser sends zero Trash requests. Attacker: new future copy appears after listing, or clock catches up later. Those require a stronger inventory/identity contract; broader cross-layer gap.
4. **Arbitrary skew tolerance**: tolerating small future times would still certify a timestamp that is not yet known to have occurred; cheapest attack is timestamp one millisecond ahead. No tolerance is used. Local epistemic gap.
5. **Use server timestamps**: creation time from the same or another wall clock may also be wrong or rewound. Attacker changes server clock or imports an old file. Requires a trusted-clock model; broader gap.
6. **Durable transactional generation sequence**: could establish an application-controlled order for operations in one store, but imports, concurrent allocation and legacy backups need rules and transaction tests. Not implemented; broader interface.
7. **Remember observed future dates durably**: can avoid later treating an already-observed future timestamp as fresh, but storage failure, identifiers, cross-device state and first observation need defined semantics. Not implemented; local-to-cross-layer gap.
8. **Disable all pruning**: trivially protects copies but removes legitimate retention functionality. Counterexample: ordinary dated past backups; unacceptable feature regression.

Misleading result shapes: future called today; invalid clock called fresh; warning but still sending Trash; one future file excluded but still counting it among kept copies; missing date parsed as valid; false empty-list success; stale list treated as current; failed guard interpreted as deletion; response lost assumed rollback; two-tab race ignored; time corrected during confirm ignored; clock catching up claimed trustworthy; future checks applied only to UI not planner; timezone/DST assumed universal; real browser replaced by pure tests; fixed fixture clock mistaken for system-clock test; timeout swallowed; increase cap to pass density; single app fix promoted to ten Class-A features; performance claimed without benchmarking.

## Actual execution and limitations
Tools actually used: Node 22, TypeScript/Next production build, ESLint, Bash, git/gh, real Chromium 143 through Playwright, real disposable PostgreSQL, and web search. No independent agents, theorem prover or independent expert were used; browser clock manipulation is a controlled test, not an external trusted clock. Baseline TT211 unit 1/5, with future-age, invalid-now, future-retention, and invalid-now-retention failures. Patched UTC and America/New_York unit runs passed the initial 5/5; an additional backward-correction attack is included. Strict date regression 3/3 in New York, core suites TT120 10/10 and TT123 18/18 passed. Real browser TT211 1/1 checked a future copy and browser-local last-built timestamp are unknown, zero real Trash requests are made, and all four database files remain live. Real TT172 4/4, TT173 4/4, TT174 2/2, TT175 2/2, TT176 7/7 passed. Existing TT173/174 fixture filenames intentionally use years 2302/2303: first patched run failed because those dates are now correctly future and TT173's unbounded wait hung; the fixture clock is now fixed to 2304 and the held-request wait is bounded. The hung test and browser were terminated and only its explicitly owned disposable fixtures removed.

An attempted actual-dialog clock-change attack could not update Playwright's clock while the native modal blocked the command; it timed out and caused a rejected command after context closure. The attempted test was removed; the after-confirmation recheck has a unit-level backward-clock attack, not a successful real-modal clock-correction test. This remains a gap. Once time catches up to a future date, this stateless implementation may call it fresh again; the attack in the cited issue is not fixed. The stored snapshot may become obsolete during confirmation or a prune batch. Invalid/unparseable names remain unpruned as before, and timezone shifts may conservatively block valid files. No elapsed-time or CPU improvement is claimed; extra tests increase work but strengthen recurring verification.

The production build passed. ESLint passed for the changed libraries and test files; `Backup.tsx` has the same pre-existing set-state-in-effect and unescaped-entity errors plus a warning recorded in TT209. The full-gate result is recorded below when known. Ten Class-A promotions, all-app visual review, graphics, and a quantified OS-completion percentage are not claimed.

Additional boundary: the displayed age is recomputed on React renders, not continuously; changing the clock without a rerender can leave the previous label visible. The post-confirm check is not repeated before each individual Trash in a batch, and inventory changes after listing are not transactionally excluded. These are not covered by the successful browser test and prevent a general destructive-safety or Class-A claim.
