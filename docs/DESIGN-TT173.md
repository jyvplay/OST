# TT173 — working, honest Backup pruning

## Scope, quantifiers and threshold
Object: the existing Backup panel's prune action on dated /Backups files, actual VFS HTTP server and exclusive disposable PostgreSQL. Observables: HTTP requests and responses, stored node trash flags, inventory and visible status. For each explicitly tested schedule: after confirmation, only the older selected copies move to Trash and the two newest stay; on an error or lost response the UI must say the outcome is unconfirmed, stop the batch and refresh the inventory, without reporting all succeeded. A per-panel guard must prevent repeated pending activation from starting a second batch. This is not atomic batch deletion, cross-tab exclusion, guarded replacement, secure erasure, guaranteed recovery after lost responses or a complete OS. Default resource bounds: existing 440-word Backup density gate and browser timeouts, not a latency promise. Commit threshold: old-build real-browser/DB counterexample, successful build, patch-specific fault and concurrency attacks, related backup tests; full gate must be reported. Keep PR open.

H+: a real reversible operation and honest uncertain-result handling can satisfy these bounded tests. H−: old code's nonexistent `rm` operation is rejected by the current server; this is not a general impossibility proof. H∂: concurrent replacement, response loss, failure at operation k, multiple tabs and failed list refresh change what is knowable. Actual tools: git/gh, shell, web research, Next/TypeScript, Playwright/Chromium, HTTP and disposable PostgreSQL. No agents, theorem prover, simulator, independent human or AT reviewer. MDN states fetch fulfills on HTTP errors and consumers must check status (https://developer.mozilla.org/en-US/docs/Web/API/Window/fetch); PostgreSQL documents transactions as all-or-nothing for participating statements (https://www.postgresql.org/docs/current/tutorial-transactions.html), which neither guarantees delivery of an HTTP response nor spans independent requests. No global optimality or impossibility theorem has been established.

## Mechanisms and adversaries
These are independently stated candidates, not six implemented/proved solutions. Gaps are local unless noted.
1. **Old `rm` request:** concrete server route returns unknown operation; real browser/DB pre-patch test failed. Attacker: confirmed prune of four actual copies; none are moved. Local contract failure.
2. **Direct permanent purge:** artifact is the existing purge API. Attacker: a replaced file or bad plan destroys an unintended version. Probe concurrent overwrite immediately before request and inspect versions. Not implemented; irreversible local data-loss gap.
3. **Reversible sequential Trash with checked responses and unknown-state warning:** implemented artifact; tests use live VFS, drop a real committed response, inject a 500 after one successful move and fail refresh, and count held-request duplicate activations. Gap: non-atomic batch, stale identities, cross-tab or unmount; not a full distributed solution.
4. **Blind retry:** design repeat failed operation; attacker replaces the same filename after uncertain response, so retry moves the replacement. Probe lost response, replace path, then retry. Not implemented; gap is identity and concurrency.
5. **Atomic server batch with conditional per-file identities:** design is a single transaction locking planned rows and checking versions, then moving all or none. Attacker: new file or path replacement races the plan; compare full snapshot and affected rows under concurrent requests. Not implemented; substantially wider server/API gap.
6. **Durable operation ID and results:** design records a unique operation, request fingerprint and outcome transactionally. Attacker: retry with altered payload or lost response after commit. Probe key reuse and recorded-result lookup. Not implemented; distributed recovery interface, beyond local warning.
7. **Manual one-file operation:** design requires each selection and confirmation individually. Attacker: user loses visibility of ordering/retention or operations are interrupted; test expected ordering and count. Not implemented; local usability gap.

Misleading shapes and probes: 1 control rendered vs actual server supports op (real prune); 2 HTTP 200 vs valid body (check ok); 3 failed fetch vs operation absent (drop after real commit); 4 first success vs entire batch success (second request failure); 5 list refresh requested vs successful (fail GET); 6 stale list vs safely prunable (disabled on refresh failure); 7 disabled button vs synchronous double activation (held first request and count); 8 irreversible purge vs reversible Trash (check node flags); 9 selected names vs identity-safe replacement (concurrent replacement remains open); 10 one panel vs other tabs (cross-tab remains open); 11 Trash vs secure erasure (do not claim erasure); 12 success text vs all copies always preserved (concurrent writers not tested); 13 DOM vs accessible disclosure (actual keyboard/AT evaluation still needed); 14 targeted tests vs full gate; 15 word count vs comprehension; 16 adding tests vs faster tests. Modal shortcut is asserting that a rendered prune control works: the real browser/HTTP/DB test failed on old production because `rm` is not an API operation.

## Evidence and limits
Old production failed its real four-copy prune case; the server does not implement `rm`. Patched build passed. On the initial patched build TT173 passed 4/4: correct two older files moved to Trash; real second commit with response dropped; two synchronous activations while first request held produce only the two intended requests; second-request 500 and failed refresh produce both warnings and leave a genuine partial result. TT172 passed 4/4, TT171 2/2 at 430/440, TT87 6/6, TT88 6/6 and TT89 9/9. Tests own checked-unoccupied fixtures only; they purge those fixtures after each case.
