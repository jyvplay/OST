# TT222 — conservative framing-policy probe

## Scope and runtime
One agent used Node 22, Next production build, PostgreSQL disposable database, curl, ESLint, Playwright Chromium 143 and web search. No separate agents, theorem prover, independent reviewer, CI service or simulated endpoint was used. The test fixture is an actual local HTTP origin with controlled response headers, not a third-party site or a production allowlist. Its server process alone was started with `FUSION_WP_TEST_LOOPBACK_PORTS=4043` and `FUSION_WP_OS_PROXY=0`; this SSRF exception is test-only and must never be enabled in a deployment. The ordinary gate server had no loopback exception. The fixture test must run separately on an exclusive disposable setup with `TT222_LOOPBACK_FIXTURE=1`, `TT89_DISPOSABLE_DATABASE=1`, `DATABASE_URL` and `BASE` targeting that specially configured server.

## Narrow formal model
Input is one completed public-URL HTTP response's enforced CSP header (including a comma-joined policy list) and XFO, on the existing server-side probe path. Count one classification per response, not bytes, user actions or OS features. For the checked subset, each policy is split into directives, the first directive named frame-ancestors exactly is used, and the result is conservative: no directive or all effective values exactly `*` preserves the existing embeddable classification; any other effective value reports csp-restricted, unless existing XFO handling decides first. A named subdomain wildcard is not a global wildcard. A restricted result is advice to offer handoff, not a claim that a particular ancestor is definitively blocked. Parameter boundaries include the existing redirect, SSRF and fetch limits, the current request's observed headers, and the 1 MiB response limit; no finite-time guarantee is made for all networks. Success on the finite fixture set requires each real HTTP response and its route output to match the specified result, including fresh attacks after repair. Failure is any mismatch, network failure or fabricated success.

H+: the finite directive-extraction and conservative classification contract is achievable. H−: a header-only request cannot guarantee whether future navigations, changed policy, cookies, nested ancestor chain, JavaScript or other browsers will allow embedding. H∂: actual results depend on origin, request, browser, network, cache and policy; even `*` cannot guarantee the frame will render. This does not substitute header classification for actual browser enforcement, complete CSP evaluation, accessibility review, a benchmark, modern-OS parity, or full product acceptance.

W3C CSP3 specifies policy directive parsing, ignores duplicate directive names in one policy, and gives enforced frame-ancestors precedence over XFO in compliant modern engines: https://www.w3.org/TR/CSP3/ . Its policy-list discussion distinguishes multiple enforced policies, and its frame-ancestors algorithm applies to ancestor contexts. This implementation does not implement that full algorithm, nor correctly resolve the CSP/XFO precedence; it maintains the old XFO-first decision and therefore can conservatively refuse embedding that a conforming browser permits. The source list parser here classifies, not matches a parent origin. No arbitrary-header or cross-browser conformance proof is claimed.

## Counterexamples and repair
With the old production build and real local HTTP origin, the five-case suite passed 1/5: `https://*.trusted.example`, `*, frame-ancestors 'none'`, an empty directive and an unrelated `not-frame-ancestors` directive were misclassified. Route extraction now requires the exact directive name, respects first duplicate within each comma-separated policy, and only treats the exact standalone `*` source list as unrestricted. After rebuilding, the five original cases plus three new attacks (duplicate allow-first, duplicate deny-first, uppercase subdomain wildcard) passed 8/8. This is an actual HTTP integration test of the probe and origin; it does not independently show iframe rendering. Existing real GitHub/DNS UI suite passed 8/8, TT221 Browser suite 2/2, TT220 identity 2/2, build and route lint passed.

TT221 lifecycle follow-up delays the actual request before continuing it to the actual endpoint, closes the initiating tab, and checks a second tab after the old response and its own retry. This tests one close-while-pending ordering; it does not assert cancellation or cover every remount, restore, tab-ID reuse or stalled connection.

## Candidate portfolio and residual attacks
1. Old substring match (counterexample: fixture baseline 1/5); false positives on unrelated directive and false negatives on subdomain wildcard. Local gap demonstrated.
2. Exact parsing with conservative classification (implemented route and fixture 8/8); attacker supplies XFO conflicting with CSP or a source list matching the actual parent; remaining gap is local/full CSP semantics, not verified browser conformance.
3. Reuse `embed-policy.ts` (artifact: code inspection): it merges separate policies and mishandles obsolete ALLOW-FROM, so the cheapest attack is conflicting policy lists. Gap is a local parser rewrite and independent conformance testing.
4. Full CSP source matcher including every ancestor (design: parse policy list and intersect each policy's matching result): attacker chooses nested origins, schemes, ports, duplicate headers and redirects. Requires parent chain and browser compatibility, approaching full policy engine rather than this narrow fix.
5. Embed and inspect (design: attempt actual navigation in a sandboxed frame): attacker uses cross-origin isolation, script-generated refusal or a changed response. Cross-origin observation is limited and load signals alone do not prove successful rendering; gap is the original real-world verification problem.
6. Handoff every URL (design: never embed): easiest falsifier is an actually embeddable origin. Avoids some false-allow classifications but removes a useful existing capability and violates the preservation requirement.

Misleading shapes: (1) test response invented instead of real HTTP; (2) only header presence tested; (3) `*` substring mistaken for global allow; (4) policy names matched as substrings; (5) empty directive treated as absent; (6) only the first policy considered; (7) duplicate directives merged; (8) report-only policy enforced as a response header; (9) a known failing URL treated as universal; (10) failed TLS called site denial; (11) a handoff recommendation called confirmed browser block; (12) server response claimed to predict later browser request; (13) stale probe used as current permission; (14) unit test claimed as independent browser conformance; (15) hidden or clipped text removed to make density green; (16) accepting a modal described as completion. A modal only records an interaction; this fixture asserts the real HTTP response status and classification, so acceptance without the network response cannot pass it. Neither this nor the Browser lifecycle test is a universal proof.

## Density investigation
An exploratory Chromium DOM audit on the accumulated disposable database found that the existing metric counts laid-out text even outside clipped scroll regions: Files 375 total versus 279 with an experimental ancestor-clip intersection, and Routines 423 versus 131. Those numbers were gathered in one view and the experimental counter does not prove pixel-perfect visibility or stable asynchronous content. Files' exploratory result still exceeded its strictest 260 cap. No thresholds, content, or metric were changed. A defensible fix needs an explicit initial-viewport versus entire-scrollable-content contract, independently validated visibility accounting and a separate full-content/accessibility preservation test; making red results green alone is not evidence.

Ten Class-A promotions, a comprehensive app visual review, original graphics, Pareto speed gains and modern OS parity are not established here. The next high-information verification is an actual Chromium parent/child frame test covering controlled wildcard, multiple policies and XFO/CSP conflict, paired with the route response; a separate held-response test for tab-ID reuse and remount remains open.
