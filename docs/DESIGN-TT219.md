# TT219: generation rotation across legacy writers

## Model and evidence threshold

Scope: `desktop_state` preset rows in one PostgreSQL database, the new guarded-delete endpoint and ordinary inserts/updates with database triggers enabled. An existing old application server may issue ordinary PUT-style SQL without knowing about `generation`. For each such insert/update, the BEFORE row trigger assigns a fresh random UUID; a guarded delete is one SQL statement requiring ID, generation and the expected enabled trigger metadata. If migration or the trigger is absent/disabled for the delete session, the statement affects zero rows and returns 409. The migration also rotates all existing preset generations, invalidating views taken before installation. Returned tokens are not secrets or authorization.

Conditional safety target: for each guarded DELETE based on a token issued before a committed insert/update to that ID, it must not remove the changed row, assuming the writer's trigger actually fires, no later actor alters the assigned token, no UUID collision or database restore reuses the token, and PostgreSQL's transaction semantics hold. Units are one row, one random UUID and database statements; no bounded completion time is promised. The API deliberately returns the same 409 for absent/mismatched rows and missing guard, so it does not distinguish them. Lost acknowledgements, durable replay, legacy unguarded DELETE, authorization, uncooperative administrative writes, whole-desktop optimistic concurrency and OS completeness are different targets.

**H+**: the scoped conditional protection is implementable with database-enforced generation and was exercised by HTTP/database tests. **H−**: a token cannot protect a name-only legacy unconditional DELETE; absent the necessary identity information an intervening replacement is indistinguishable, as TT217's counterexample demonstrates. **H∂**: if a writer runs with triggers disabled, a non-origin replication role, a later trigger modifies the generation, a backup restores old tokens, or an administrator alters the function/schema, the assumptions fail. Checking the trigger at delete time does not prove it fired for all prior writes. UUID uniqueness is probabilistic. This is not a security boundary against a privileged database actor.

Evidence threshold: observe old-generation reuse against the actual prior server; exercise pre-install stale-token behavior; test migration and explicit/legacy writes on PostgreSQL, fail closed when the trigger is disabled, run production build and affected real-browser/HTTP suites. Report full-gate result separately. No universal theorem or Class-A claim follows from finite tests.

PostgreSQL's [trigger function documentation](https://www.postgresql.org/docs/16/plpgsql-trigger.html) says a row-level BEFORE INSERT/UPDATE trigger can alter and return `NEW`; [CREATE TRIGGER](https://www.postgresql.org/docs/15/sql-createtrigger.html) notes that INSERT ON CONFLICT UPDATE can fire both kinds of trigger. [Read Committed](https://www.postgresql.org/docs/18/transaction-iso.html) documents conditional DELETE rechecking an updated row after waiting. These statements assume their documented PostgreSQL settings and enabled trigger behavior; they do not prove network acknowledgement or compatibility with disabled triggers. The implementation is independently written; no cited source code was copied.

## Deployment and limitations

For existing databases: back up, schedule maintenance, run `src/db/migrations/tt218-desktop-generation.sql` first and then `src/db/migrations/tt219-preset-generation-trigger.sql`, before deploying this server. PostgreSQL 13+ and privileges to alter table/create trigger/function are required. Both scripts set lock and statement timeouts. TT218 can rewrite the table; TT219 locks the table and updates every preset row, so production duration, WAL, space and contention require measurement. TT219 deliberately rotates all preset generations **on every execution**: user content/revision remains, but outstanding guarded deletes become stale. Do not call this token-idempotent. `drizzle-kit push` alone does not create the trigger; disposable `scripts/sandbox/bootstrap.sh` now installs it, and its helper requires explicit disposable opt-in. The guard queries PostgreSQL catalog metadata inside its DELETE; the check proves a named enabled trigger with expected event bits/function identity for the deleting session, not its function body or historical enforcement in other sessions.

No server-generated migration is automatically run on production startup. Old servers still permit unconditional DELETE; old PUT-style writes normally rotate via the trigger, but disabled triggers, replication mode and restore bypass remain. The legacy DELETE route remains for compatibility. New UI cannot use guarded delete on an older server and missing guard fails closed on a new server. No automatic retry or durable unknown-outcome reconciliation was added.

## Mechanisms, artifacts and attackers

1. **BEFORE row trigger plus catalog-gated conditional DELETE (implemented):** migration SQL and endpoint are artifacts. Legacy SQL UPDATE and explicit reused-token INSERT were rejected by stale delete in 3/3 TT219 cases, including disabled-trigger refusal. Attacker: privileged actor disables trigger, modifies data and reenables it before a delete; metadata at delete time cannot prove history. Cheapest test: real two-session bypass/re-enable. Cross-writer administrative boundary remains.
2. **Application-only UUID rotation (TT218):** prepatch TT219 baseline showed unchanged token for legacy-style UPDATE and explicitly reused generation on INSERT. Attacker: older app or direct SQL. Cheapest falsification is the reproduced 0/3 suite; local deployment compatibility gap.
3. **Conditional DELETE by generation alone (TT218):** stale recreate/update and row-lock tests 4/4 under cooperating writers; attacker deletes/recreates with an explicitly reused UUID. Cheapest falsification is TT219's second case. Gap is generation lifecycle, not OS completeness.
4. **Strict advisory-lock protocol (not implemented):** requires every writer to use the same lock and check identity in its transaction. Attacker: unlocked old SQL; test two independent DB connections. Gap is global writer cooperation.
5. **Database permissions and stored procedure-only writes (not implemented):** revoke direct writes and allow only a controlled operation. Attacker: privileged connection or owner bypass; test role grants and rollback. Gap is deployment/authorization architecture, not solved by UI checks.
6. **Append-only tombstones / durable generation table (not implemented):** keep identity after deletion to distinguish recreation; attacker restores old backup or rolls back tombstone independently. Test DB crash/restore and migration. Gap is durability, retention and restore consistency.
7. **Serializable transactions (not implemented):** serializable retries may prevent some interleavings, but don't identify an already recreated row and do not make an acknowledgement durable. Attacker: recreate before the transaction begins; test stale token after recreation. Gap is logical identity, not isolation alone.

At least fifteen misleading shapes: 200 with malformed body; timeout as rollback; empty refresh as final; name-only delete; reset revision as incarnation; truncated timestamp as unique generation; identical content hash as generation; a component lock as cross-tab lock; an advisory lock as binding for SQL bypass; new-server PUT as coverage of old writers; installed trigger as proof it was never disabled; current catalog state as proof of historical writes; ordinary trigger as protection against replication-role bypass; a UUID as authentication; a migration rerun as preserving outstanding tokens; two test rows as production migration timing; a 409 as evidence a prior delete committed; fake transport failure as an actual network outage; a modal's internal event stop as a global shortcut guard; fewer measured words achieved by hiding actions; setup timing as a Pareto full-gate speedup; self-assessed feature labels as independent Class-A proof. The retained TT215 modal test positively exercises Meta+A outside the modal then shifts focus behind the dialog; a modal-only propagation stop would not intercept the latter event.
