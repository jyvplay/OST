# TT166 — protecting the one-time token panel

## Runtime, scope, model, evidence threshold
Actually used: local git/gh, web search, shell, Node, TypeScript/Next production compiler, Chromium/Playwright, HTTP and exclusive disposable PostgreSQL. Two pure-test workers and sequential browser suites are configured for the full gate. No independent agent, simulator, theorem prover, human expert or assistive-technology review was used. Tests delay or abort genuine HTTP responses to create specific failure schedules; the test does not represent a fabricated token as a real one. Test token IDs are cleaned from the disposable DB; audit entries remain. Secrets are not printed or placed in test receipts.

Admissible object: one mounted Routines automation-token panel, its user interactions and local mint response; the server may process a request even if its response is lost. Resources counted: server POST attempts and displayed one-time secret state, not CPU or wall-time speed. For each tested schedule, the success predicate is: at most one POST begins while the panel is busy or holds an unacknowledged secret; after explicit dismissal another mint is possible; on a lost response the UI warns that a token may exist and refreshes the list. The number of pages/records is finite and no cross-tab lock is assumed. This is not server-side exactly-once minting, authenticated settlement, security certification, durable recovery of secrets, or a complete OS proof.

H+: a local synchronous guard and explicit acknowledgement can meet the bounded predicate. H−: the entire requested OS contract may be impossible under the constraints, but that is not proved by these experiments. H∂: unmount, navigation, browser crash, network ambiguity, concurrent tabs, failed refresh and accidental dismissal change the guarantee. Local commit threshold declared before commit: old-build adversarial failure, a production build/typecheck, a new attack on the repair, affected browser regressions, and honest full-gate outcome. Merge threshold remains a passing full gate on the exact build after main review. A speed claim requires a controlled equal-fidelity comparison, which was not conducted.

## Construction and measured evidence
Old build: two synchronous button activations while actual POST responses were held caused **two real tokens** to be minted; the test failed 2 vs expected 1. This establishes double issuance, not an observed reverse-order lost-secret sequence. A separate old-build test showed the expected unread-secret lock was absent. The repair uses a synchronous ref to guard activations before React can render, a disabled button while in flight or while a secret remains visible, and an explicit Done action to discard it. After a failed POST the UI warns the outcome may be ambiguous and refreshes the list; it cannot recover an already-lost secret, and retry may mint another token. The user can still discard a secret without copying it, or close the window before copying.

On the rebuilt production server, TT166 passed 3/3: rapid double activation against real POST, forced activation with an unread secret, dismissal and deliberate subsequent creation; pre-send request failure and explicit retry; and a real POST committed before its response was deliberately dropped, followed by warning and list lookup. The test compares secrets only in memory and does not print them. TT165 4/4, TT164 4/4, TT163 1/1, TT146 browser 5/5 and TT158 planner 1/1 passed. The browser test's short observation window and two programmatic activations do not establish every scheduling or accessibility condition.

OWASP's secrets-management guidance https://cheatsheetseries.owasp.org/cheatsheets/Secrets_Management_Cheat_Sheet.html recommends limiting visibility, revocation and not logging plaintext secrets; it does not certify this UI or provide durable recovery. The app's API stores a hash and returns the token only in the POST response. The result is not an independent audit of that API's cryptography or authentication. No global best-known achievability or impossibility result for the entire OS is established.

## Six independent mechanisms and strongest local attacks
1. **Synchronous in-panel mutex:** a ref blocks a second activation before render. Artifact: the old/new real POST-count test. Proved only for tested same-panel activations; attack forced events and double click, tested. Cross-tab and remount are local unresolved interfaces.
2. **Explicit unread-secret acknowledgement:** disable creation until Done; artifact: tested DOM state and subsequent deliberate mint. Attack premature dismissal/window close, not prevented; a local UX gap.
3. **Ambiguous-failure disclosure and refresh:** warn when response is lost, fetch actual rows; artifact: committed-POST/aborted-response attack. Test demonstrates discovery of the row, not recovery of its secret; failure of the list refresh remains local.
4. **Server idempotency key (alternative):** store request key and outcome transactionally to deduplicate retries; causal model is one logical request mapping to one creation. Attack concurrent equal keys, crash between commit and response, and secure secret recovery; not implemented, backend/privacy design gap.
5. **Queued one-time panels (alternative):** retain multiple pending secrets in memory until independently acknowledged. Attack close/reload and accidental disclosure across panels; no implementation, local memory and privacy gap.
6. **Cross-tab coordination (alternative):** shared Web Lock for minting. Attack unsupported browser, tab crash, two clients that do not cooperate; no implementation and not a server-wide guarantee. This gap is local coordination, not equivalent to all OS requirements.

Negative-space shortcuts: disabled button alone blocks same-tick handlers; no response means no server commit; one secret visible means all secrets recoverable; retry is idempotent; a row ID is its secret; refresh succeeded because warning disappeared; client mutex covers other tabs; one test proves every timing; same-tick DOM calls prove assistive technology works; a token hash proves authorization is secure; secret copied means clipboard is private; Done proves user saved it; successful GET proves future freshness; matching a label proves accessibility; no console errors prove security; fewer controls prove usability; a targeted test proves full gate; more tests imply speed; ledger labels prove Class A. The double-activation test detects the old unguarded handler; whether it rejects every disabled-only mutant has not been verified. The committed-but-lost response test attacks the false no-response/no-commit assumption.

## Clipboard privacy repair
Source review found that the generated curl example includes the bearer token but was copied with `sensitive=false`. `Shell.copy` consequently retained the full example in its in-memory clipboard history, which is also exportable; this is not a claim of disk persistence. An actual Chromium test demonstrated the token in history on the old build without printing the secret. Two earlier runs of that new test timed out on setup (one window-readiness issue and one zero-sized empty list); after correcting the empty-list wait, the explicit leak assertion reproduced. Marking the example sensitive uses the existing masked-history and best-effort clipboard clearing behavior. The rebuilt production test confirmed both the token and the curl example were masked in the app history. It did not verify system-clipboard clearing, browser permission handling on other browsers, or copied data in other applications.

After this repair, the production build passed; final targeted TT166 4/4, TT165 4/4, TT164 4/4, TT163 1/1, TT146 browser 5/5, TT158 planner 1/1 and clipboard workflow 11/11 passed. The first TT166 full-gate run `.cache/gate/20261111T212613Z/run-3339585-nHH92I` was intentionally stopped after discovering the clipboard issue; it is not a passing gate. A new full gate was started on the rebuilt final code.
