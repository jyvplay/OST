# TT218: generation-guarded preset deletion

> Deployment update: TT219 requires both the TT218 and TT219 migrations; see `docs/DESIGN-TT219.md`. The historical TT218-only instructions below are not sufficient for the current server.

## Model and decision boundary

A preset is a `desktop_state` row identified by `preset:<name>`. The supported new client obtains a generation UUID from the preset list and sends it with a distinct `deletePresetGuarded` POST. Each insert gets a fresh DB-generated UUID and the new server's existing PUT update rotates it. DELETE uses one SQL statement with both ID and generation, and returns 409 if no row matched. At Read Committed, PostgreSQL rechecks a waiting DELETE's predicate on an updated row; the test covers one such execution. An HTTP timeout is still uncertain, not a rollback or proof that the operation did not execute.

For all operations made through the new guarded path, if the DB has not restored/reused a prior UUID and all relevant updates rotate generation, a delete with an older UUID cannot delete a newer row with that ID. UUID collisions are probabilistic, not impossible. This property does not apply to the retained legacy unconditional DELETE, old servers, direct SQL that does not rotate generation, DB restoration, a stolen or forged token, an unauthorized caller, or a response-lost retry after an intervening legacy mutation. It is not authentication, exactly-once delivery, full desktop optimistic concurrency, or restore fidelity. Success is one returned deleted row and valid acknowledgement; zero returned rows means changed or absent, not which. Unit is a UUID and one DB statement, not a wall-time liveness bound.

**H+**: conditional deletion is achievable under the listed compatibility and uniqueness assumptions and was exercised by real HTTP/browser/database tests. **H−**: an unconditional request keyed only by name cannot distinguish a replacement; TT217's executable counterexample demonstrates it. **H∂**: mixed old/new servers, old clients, uncooperative SQL and restored UUIDs invalidate the premise; durable operation IDs and a wider writer protocol are separate work. Evidence threshold: migration preservation/idempotence on a disposable existing schema, production build, prepatch counterexample, postpatch real stale/recreated/update/row-lock attacks, old-list fail-closed UI, and rerun affected tests; full gate result reported without substituting targeted green tests for it.

External semantics: PostgreSQL [Read Committed](https://www.postgresql.org/docs/18/transaction-iso.html) explains predicate re-evaluation after a conflicting row update, and [DELETE](https://www.postgresql.org/docs/18/sql-delete.html) explains `RETURNING` for deleted rows. [RFC 9110 If-Match](https://www.rfc-editor.org/rfc/rfc9110.html#section-13.1.1) describes a related conditional request concept; this implementation uses an explicit operation, not an HTTP ETag implementation. No imported source code was copied.

## Deployment

Before starting new application code on an existing database, back up, schedule maintenance, and run `psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -f src/db/migrations/tt218-desktop-generation.sql` against PostgreSQL 13+ (which supplies `gen_random_uuid`). Adding a volatile default can rewrite the table and lock it; script uses 4 s lock and 60 s statement timeouts. It is idempotent for the published old/upgraded schemas, not a repair of an arbitrarily malformed pre-existing column. Migration applied twice to a disposable database preserved ID/state/revision for two existing rows and filled tokens; this small test does not establish production migration duration or restore behavior. The new UI talking to an older server sees no generation and disables preset delete; the new explicit POST is rejected by the old create-only POST handler rather than silently ignoring a condition. Older clients can still use unguarded DELETE. This is not a complete rolling-upgrade safety solution: old servers' PUT does not rotate the new token, and new servers require the migration to have run.

## Candidate portfolio and strongest structure-specific attacks

1. **UUID generation + conditional delete (implemented):** SQL predicate is in the delete; evidence: 4/4 HTTP tests and 2/2 browser tests. Attacker: old PUT, legacy DELETE, direct SQL, or snapshot restore; local protocol compatibility remains. Cheapest test: mixed old/new real servers and restore.
2. **Name only (rejected):** TT217 standalone experiment demonstrated duplicate DELETE after replacement removes it. Attacker: intervene between two deletes. No missing local lemma: operation has insufficient identity information.
3. **Timestamp guard (not selected):** database timestamp may collide, go backwards, or be truncated by clients. Attacker: same-millisecond delete/recreate; test with controlled clock and identical state. Local identity gap.
4. **Revision counter (not selected):** existing per-row revision can reset on recreate. Attacker: delete/recreate at revision 1; direct HTTP experiment. Local ABA gap.
5. **Conditional content hash (not selected):** identical content can recur after a replacement. Attacker: recreate identical state; compare hash. Local incarnation gap.
6. **Advisory lock (not selected):** serializes only cooperating writers while held. Attacker: old server bypasses the lock, or stale request arrives later. Run two actual connections with one unlocked write. Cross-writer compatibility gap.
7. **Durable request IDs (not implemented):** atomically store operation key/fingerprint and result; attacker mismatched retry, key expiration, DB rollback or restore. Run concurrent and crash/restart test. Separate acknowledgement/retention gap, not equivalent to OS completeness.

Misleading outcomes include: 200 with no body, treating timeout as rollback, list absence as final, simple name-only delete, identical content hash as incarnation, reset revision as generation, timestamp as monotonic ID, stale 409 as proven user action, same-process lock as cross-tab lock, advisory lock as protection against SQL bypass, new client as protection against old client, migration on two rows as production performance proof, interception as real outage, one browser as universal accessibility, modal event stop inside dialog as global shortcut suppression, density achieved by hiding actions, faster setup as Pareto full-suite gain, and self-reported ledger as independent Class-A proof. TT215's retained modal test proves Meta+A works without a dialog and then targets focus behind it; a propagation-only handler confined inside the modal fails that test.

## Verification and boundaries

Used Node/Next/TypeScript build, real disposable PostgreSQL and Chromium 143 via Playwright, shell, ESLint and web search; no independent agent, theorem prover, simulator, expert review or other browser. Prepatch HTTP generation tests 1/3 (the malformed-input check was already refused, not proof of the new guard); patched 4/4, including a delete blocked by a real row lock then refused after a generation-rotating update. Browser 2/2: stale displayed generation could not delete a replacement, and a list with generation removed disabled delete. TT217 5/5, TT216 refresh 3/3 and late-create 1/1, TT215 4/4, TT214 5/5, TT157 2/2. The TT216 lock observer initially failed once and its unfinished response promise produced an unhandled rejection; PostgreSQL statistics snapshots are cached during its transaction. The test now clears the stats snapshot on each poll and handles the response-wait rejection, and passed on retest. This is a test repair, not evidence of an app defect. Route/schema ESLint and diff check passed; Routines still has its known separate lint error.

Deletion remains uncertain after transport failure, warnings are not durable, and no automatic retry is added. The old unconditional DELETE is deliberately retained for compatibility and remains unsafe for stale clients. No ten Class-A promotions, all-app visual audit, original graphics or measured Pareto speedup was achieved. Full gate result is recorded separately when available.
