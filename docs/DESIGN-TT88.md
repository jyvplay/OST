# TT88 — user-held recovery for general backups

**Date:** 2026-10-26 (America/New_York). **Selected core feature:** BK-06, “Key custody, user-held recovery key, no cloud escrow by default,” A/P2, in `Full V2 and V2.1 Specs.txt` §7.10. **Previous state:** general encrypted backups were passphrase-only; the separate Privacy volume already had its own recovery mechanism. **Current state:** BK-06 is `built` for the bounded general-backup workflow described here. A user can select a new recovery-key archive, save and confirm a 256-bit key locally, download it, and later use either that key or the original passphrase to preview and restore. This is not a claim that every OS feature is complete or that the new cryptographic format has received a professional security audit.

## A. Formal model

**Objects and access.** A recovery archive is the application-specific JSON format `fusion-recovery-bundle-1`; it is not an age or restic file. Its plaintext is a valid bounded Fusion v2 config or data snapshot. The browser can read the selected file and secrets, generate randomness and use Web Crypto; the Fusion server participates in preview/restore but must not receive either secret. The client, server, database, other same-origin scripts and user-held key are separate trust boundaries. The server receives the **decrypted snapshot** on restore. A malicious script or compromised browser can read secrets in memory, and direct calls to the server bypass client-side guards.

**Construction.** For each download, generate a random 32-byte data key, 16-byte password salt and independent 12-byte IVs. Derive an AES-256 wrapping key from the user passphrase with PBKDF2-HMAC-SHA256 at 600,000 iterations; wrap the data key using AES-GCM. Separately wrap the same data key with the 32-byte user-held recovery key using AES-GCM. Encrypt the snapshot with the data key and AES-GCM. Domain-separated associated data binds the slot roles; the data tag authenticates the complete canonical header, including **both** wrapped slots, algorithm names, KDF parameters, salt and all IVs. The recovery key is rendered as `FSR1-` followed by eight groups of eight hexadecimal digits. The code verifies confirmation before enabling that download, then clears the display after the download starts; this cannot prove the user actually stored the key.

**Resource/parameter limits.** The secret is 256 random bits; salt is 128 bits, IVs are 96 bits and GCM tags are 128 bits. The accepted KDF range is 600,000–2,000,000 iterations, checked before derivation. The passphrase must be at least eight JavaScript UTF-16 code units, which is not a guarantee of entropy; an attacker can attempt an offline dictionary attack against a weak passphrase. Plaintext is limited to 64 MiB, with base64 and JSON overhead; this is an in-memory implementation, not a streaming constant-memory guarantee. The browser import cap is twice the plain snapshot limit. A secure context with Web Crypto is required. `getRandomValues` and AES-GCM's nonce conditions are assumed, not mathematically proved by a 100-sample uniqueness test.

**Quantifiers and success.** For a valid snapshot, a passphrase satisfying the local policy, a correctly generated recovery key, working browser cryptography, and a download that is actually saved, the intended contract is: opening that archive with **either** unchanged secret yields the same snapshot; a fresh destination-bound preview and an explicitly confirmed successful database transaction restore according to BK-03/BK-01 merge semantics. An altered header/slot/ciphertext, invalid credential, malformed schema, or disallowed work factor must not reach preview as a valid decrypted snapshot. Cryptographic authenticity/confidentiality are conditional on the security of AES-GCM, PBKDF2, random generation and secrecy of the credentials; a finite test set does not prove these universal claims. Lost commit acknowledgement remains an unknown database outcome, not a guaranteed rollback.

**Adjacent problems not substituted.** This is not a system image, automatic/incremental timeline, remote sync, monthly restore drill, hardware-backed keystore, escrow service, tamper-proof browser, secret-sharing quorum, password-reset service, proof a user stored the key, or a promise to recover an old passphrase-only download. BK-01/BK-02/BK-05 remain partial and FM-08 remains a probe. Existing passphrase-only downloads remain available and explicitly identified; a recovery slot cannot be retrofitted into a previously downloaded file without re-encrypting it.

## B. Outcome space and evidence threshold

- **H+ (supported for the bounded feature):** two independent credentials open the same freshly generated file, the other slot is authenticated, neither credential appears in observed browser requests, and the real restore path works. Acceptance threshold: optimized build/typecheck; scoped lint; bidirectional independent-format tests; real browser download, rejection and restore; mutation sensitivity; regression gates. These passed as detailed below. This is functional evidence, not an external cryptographic audit.
- **H− (stronger claim not supported):** an archive with neither correct secret nor an escrow service cannot be promised recoverable, and a checksum alone cannot authenticate a maliciously modified plaintext bundle. This is an operational boundary, not a claim that exhaustive brute-force recovery is mathematically impossible.
- **H∂:** missing secure-context crypto, lost credentials, old archive formats, browser/user storage choices, untrusted scripts, weak passwords and server trust change the answer. If the user wants an audited interoperable format, native key protection, or recovery without a locally retained secret, those are different additional requirements.

## C. External frontier and design choices

- [1](https://github.com/filosottile/age) is a BSD-3-Clause encryption tool with explicit identities and multiple recipients. [4](https://github.com/restic/restic) is BSD-2-Clause; its [1](https://github.com/restic/restic/blob/master/doc/design.rst) documents password-protected repository keys and the need to re-encrypt data when a master key leaks. These are useful permissive references, not a claim that this JSON is interoperable with either project. Their source was not copied or renamed and no dependency was added to the PWA.
- [1](https://developer.mozilla.org/en-US/docs/Web/API/AesGcmParams) states the AES-GCM IV must be unique for each encryption under a given key and that associated data is authenticated. Independent random 96-bit IVs make collision unlikely, not impossible. `crypto.getRandomValues` is used rather than `Math.random`. Secure contexts are required for SubtleCrypto [13](https://developer.mozilla.org/en-US/docs/Web/API/Crypto/subtle).
- The remaining cryptographic interface is not an algorithm proof: this is a newly composed envelope with no independent security review, memory-hard passphrase KDF, hardware key custody, streaming design or interoperable external file format. A weak passphrase is an alternative attack path even when the recovery key is strong. Keys lost or disclosed cannot be revoked for already downloaded copies.

## D. Negative shapes and modal-shortcut failure

The following are distinct ways an apparent recovery solution can fail; the named suites exercise them unless explicitly marked a limitation:

1. Wrong passphrase; 2. a different but syntactically valid recovery key; 3. malformed key or wrong group count; 4. no Web Crypto/secure context (injected absence); 5. duplicate generated keys in a 100-key sample; 6. a changed salt; 7. changed passphrase IV; 8. changed passphrase-wrapped data key; 9. changed recovery IV; 10. changed recovery-wrapped data key; 11. changed data IV; 12. changed ciphertext/tag; 13. changed KDF count; 14. correctly authenticated but below-floor KDF; 15. correctly authenticated but above-ceiling KDF; 16. non-integer KDF; 17. substituted passphrase slot from a second valid archive; 18. invalid algorithm/format; 19. unknown extra field; 20. malformed or noncanonical base64 padding with identical decoded bytes; 21. oversized ciphertext; 22. missing required field; 23. download without re-entering the key; 24. generated key still visible after download; 25. credential accidentally posted in preview; 26. user loses both secrets (limitation, no recovery claimed); 27. using a recovery key with an older passphrase-only archive (explicit refusal); 28. believing an unkeyed checksum authenticates its source (not claimed). The two-slot tamper tests try **both** credentials, so damage to the unused slot cannot be silently ignored.

The modal shortcut counterexample remains the prior real regression: keyboard shortcuts from Save-as could act on the editor behind it. Production `e2e-tt81.mts` E3 opens the modal, sends Ctrl+F and Delete to its input, verifies no underlying Find panel and unchanged saved bytes, then verifies Ctrl+F works again after Escape. E5 checks the Word Count focus trap. The full suite passed 7/7; `e2e-tt67-input` independently passed 5/5 including its modal/Meta+Q check. No new modal was invented for the recovery flow.

## E. Six independent alternatives, artifacts and falsification

These are genuinely different solution branches, not claims that all six were deployed.

| Approach / central construction | Concrete artifact and verified portion | Exact unresolved interface | Cheapest falsification | Gap class |
|---|---|---|---|---|
| Plain JSON + SHA-256 | TT87 `bundle.ts` detects accidental corruption and malformed inputs | Anyone able to change JSON can recompute SHA-256; it does not authenticate a source | Recompute the digest after changing a setting | Authentication / original security problem |
| Passphrase-only authenticated archive | Existing `fusion-encrypted-bundle-2`; old browser regression remains 6/6 | No separate recovery if the passphrase is forgotten | Attempt recovery with only a newly generated key | Original recovery problem |
| Recovery secret as the only encryption key | Candidate model: raw 256-bit key can decrypt, but there is no independent passphrase path | Losing that key makes ordinary passphrase recovery impossible | Supply only a valid passphrase | Original usability/recovery problem |
| Two-of-two split/threshold secret | Candidate model: require both independent secrets, reducing single-secret compromise | Violates the requested ability to recover if either one is lost | Try with just the saved key | Different access structure |
| Two independently wrapped slots + authenticated complete header | `src/lib/backup/recovery.ts`; two-way Python/Chromium tests, malformed/tamper checks, 10 targeted mutants | No professional cryptographic audit or native secret custody; weak password remains an alternate path | Swap/damage the unused slot and open via the other | Local security-review boundary |
| Use a mature external age/restic tool instead | Reviewed BSD-licensed sources [1](https://github.com/filosottile/age), [4](https://github.com/restic/restic); no code copied or dependency included | Their repository/recipient formats are not the present single PWA browser workflow or this envelope | Export an age file and ask the current importer to read it | Interoperability / integration |
| Server escrow/reset | Existing server can receive data snapshots; no escrow code is added | Contradicts no-escrow and expands server trust | Search captured preview requests and server data for recovery key | Different threat model |

The delivered solution also contains distinct mechanisms: secure random key generation and user confirmation; independent PBKDF2 and recovery wrapping; complete-header AEAD binding; strict bounded parsing before KDF; local authentication before any preview request; and independent bidirectional oracle plus mutant testing. The architecture does not treat a passing UI status as proof that the file was saved or recoverable.

## J. Remaining gap and next highest-information test

The bounded BK-06 workflow is implemented and exercised, but an independent cryptographic design review is the highest-information next step: ask an external expert to examine the complete-header/dual-slot construction, nonce and password assumptions, parser/KDF denial-of-service bounds and compromise/revocation model, then test fixed interoperable vectors against a genuinely different crypto implementation. Do not present the new format as audited, hardware-backed or interoperable with age/restic.

Broader work remains: actual incremental remote timeline backup, automatic restore drills and health states, native directory-picker and cross-process sync races, privacy enforcement against malicious/direct callers, missing native Android capabilities, and the non-clean lint gate. A browser-only PWA cannot honestly claim the native system-image, keystore, filesystem, privileged OS and device behavior the specification marks as platform-dependent. These omissions and the historical flakes rule out claiming all features are complete.
