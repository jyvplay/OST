# TT176 — prevent Backup save from overwriting a same-minute copy

## Bounded model and threshold declared before patch
Objects: the Backup panel's “Save copy to Files”, its already built snapshot, the existing minute-granularity name, `/api/fs` and real PostgreSQL VFS. Inputs: one or more actual panels, concurrent or sequential attempts in one minute, existing live/trashed/absent destination, server/network faults, folder availability. Observables: exact destination identity, content/version, HTTP/JSON outcome, visible feedback and busy state. Resource: files/requests/statuses, no throughput claim. For every tested occupied-path or concurrent-create schedule, the old file's identity/content/version must be unchanged; at most one new creation at a path may succeed, and the UI must not report success for a failed/unconfirmed request. For each tested successful empty path, one copy is readable and inventory refreshes. Explicitly not guaranteed: two distinct saves within a minute, immutable copies against other VFS operations, exactly-once on a lost response, all schedules, automatic unique naming, offline backup, all modern OS features or Class A. Use actual production build, browser/HTTP and exclusive disposable database; commit only after a pre-patch real counterexample, build, patch-specific collision/concurrency/lost-response attacks, affected regressions. Full gate status separately disclosed.

H+: create-only conditional write and honest conflict/uncertainty handling can satisfy bounded no-overwrite; H−: the existing unconditional write breaks it (to be tested, not assumed); H∂: behavior depends on occupied paths, server response, concurrent creation, folder liveness and shared UTC/local clock. Existing conditional VFS writes rely on an actual unique path constraint, transaction, and parent locking; they do not control external raw SQL or old servers.

Runtime resources: shell/git/gh, public documentation via web search, Node/TypeScript/Next, Playwright with real Chromium, and disposable PostgreSQL. No independent agent, theorem prover, simulator, human expert or accessibility specialist. Source and tests are directly inspectable. No complete independent proof or real user deployment is available.

PostgreSQL documents `INSERT ... ON CONFLICT DO NOTHING` takes the alternative action on a conflicting inferred unique index, with concurrent inserts possibly blocking: https://www.postgresql.org/docs/current/sql-insert.html. This supports create-if-absent only with the relevant unique constraint and correct transaction behavior, not certainty of receiving an HTTP response or new names for all requests. A missing row is not secured by a prior read; the unique index is the arbiter. The open interface is durable outcome reconciliation after response loss and a collision-free, backward-compatible naming/retention policy.

## Mechanisms and candidate-specific adversaries
All are concrete designs or tests, not six implemented solutions. Gaps are local unless otherwise indicated.
1. **Unconditional overwrite:** existing `write` and the real browser test are the artifact. Attacker: two saves in the same minute. Observed old DB version 1→2; this breaks no-overwrite. It fails locally.
2. **Read-before-write:** candidate design lists/stat checks then issues write; attacker creates between read and write. Cheapest test: barrier two clients after both reads and forward both writes. No atomic absence guarantee; local race.
3. **Create-only at fixed name:** implemented conditional request `writeIfUnchanged` with `expected:null` and the unique index. It rejects an existing live or trashed path; after unknown responses it warns and refreshes. Attacker: real simultaneous tabs; drop response after actual commit; malformed 200 after actual commit; duplicate activation; existing trashed node. Tests pass below. Gap: no second same-minute copy or exactly-once outcome reconciliation; local product/interface gap.
4. **Generate random suffix:** executable design is a candidate random filename plus conditional create; attacker forces collision or random generator failure, and an old parser classifies the suffix as unknown, so retention no longer recognizes it. Test injected repeated suffix plus parser/retention interoperability. Not implemented; naming compatibility and retry policy gaps.
5. **Sequential numeric suffix:** executable design is a bounded loop of names and create-if-absent; attacker exhausts namespace or concurrently creates the next candidate, or sort ties misidentify the newest copies. Test concurrent creation and oldest/newest sorting with ties. Not implemented; local format/order and exhaustion gaps.
6. **Server-allocated monotone ID plus metadata:** design stores ordering independent of user clock. Attacker moves/imports legacy bundles, clock reverses, operation commits but response is lost. Test migration, delete/recreate, cross-client concurrent creation and response loss. Not implemented; schema/migration and compatibility gap.
7. **Durable idempotency key:** candidate design records request fingerprint, destination and result in the same transaction, allowing later query. Attacker reuses a key with different content, client loses the key or transaction commits without an acknowledgment. Test replay with altered content and lost response. Not implemented; wider distributed recovery interface.
8. **Client mutex alone:** executable candidate uses a component ref and busy state, with old server write unchanged. Attacker uses a second tab, an already existing copy or a remount; test same-minute cross-tab. Local exclusion cannot secure a shared path.

## Negative space and modal shortcut
1. Success UI not a stored copy. 2. One file exists not proof it was newly created. 3. An unchanged filename not an unchanged identity/version. 4. Matching bytes not absence of overwrite/version churn. 5. One browser panel not all tabs. 6. Client disabled button not atomic server admission. 7. A preliminary stat not a lock on absence. 8. Randomness not collision freedom. 9. HTTP failure not proof of rollback. 10. HTTP 200 not valid JSON or confirmed operation. 11. A trash node is not a free filename. 12. Retrying blindly is not exactly once. 13. Two copies are not necessarily independently recoverable. 14. A current list is not a protected snapshot. 15. Create-only does not ensure immutable backup files against other operations. 16. An empty disposable directory is not all production data states. 17. Passing targeted tests is not a green full gate. 18. A word count is not usability. 19. Existing authored coverage tags are not proof of Class A. 20. More concurrency is not automatically a Pareto speedup. The modal shortcut is list/stat then unconditional write: two writers can both see absence and write the same path. The actual old browser test independently demonstrates a repeat write by version 1→2; the patched cross-tab barrier test attacks concurrent create at the same name.

## Evidence and residual risks
Pre-patch production build/Chromium/PostgreSQL: repeat same-minute save changed version 1→2; test failed. Final production build passed. TT176 browser 6/6: sequential conflict preserves all stat fields, two actual tabs race one absent name with one winner, response dropped after real server commit, existing trashed path retained, synchronous repeated activation sends one request while held, and malformed 200 after a real create does not produce success. The network faults are deliberate interception of real requests/responses, not simulations of the database. TT175 2/2, TT174 2/2, TT173 4/4, TT172 4/4, TT171 2/2 (430/440), and TT127 conditional 3/3. The gate gains the new adversarial suite; no benchmark demonstrating speedup was made. A Backup conflict screenshot at 1500×960 was visually inspected: the refusal message and saved filename were visible. This is not an all-app or assistive-technology review.

The response 409 is deliberately phrased as an existing copy **or** unavailable folder, because the shared conditional-write operation uses 409 for both. Users must wait until a new minute or choose another export path to produce a second copy; no same-minute unique name is provided. If a response is lost, creation may have occurred and retry is refused if the path is present, but the interface does not prove which attempt created it. A non-JSON or malformed response warns and refreshes. `writeIfUnchanged` preserves current copy but does not protect it from subsequent intentional edits or uncooperative writers. Concurrent changes can still affect pruning. No 20 new Class-A features, all-app visual survey, new graphics, complete OS verification or test-speed gain is claimed.
