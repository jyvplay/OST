# TT169 — storage overview failure and recovery

## Scope, resources, threshold
Admissible object: the existing PWA Storage overview GET interaction, its real API and exclusive disposable PostgreSQL data. Access is repository, HTTP, local Chromium/Playwright, build/compiler, shell/git/gh, and public documentation; test interception can change or delay responses. Resources counted are test outcomes and wall time, not an unmeasured speedup. The independent external executors actually used are the Next/TypeScript compiler and real Chromium; no independent agent, theorem prover, simulator, expert or assistive-technology reviewer was used. Fault-injected transport responses are tests, not a production simulation.

For every tested schedule, initial failed or malformed overview must not imply zero server data, an unsuccessful refresh of a loaded overview must visibly mark it stale, and retry must recover when the service responds correctly. A late older failure must not override a newer successful request in the tested schedule. Units: request status/body, visible alerts and list state; waits are test deadlines (6 seconds for fault alerts), not a performance guarantee. This says nothing about all schedules, browsers, or deployments. Local commit threshold: old-production counterexamples, production build, affected existing regression, new patch-targeted attacks, documented remaining gaps. Merge threshold: full gate on the exact build and reviewed main; full gate failure blocks merge. Do not substitute success of a single suite for the gate, structural shape check for complete schema validation, stale warning for fresh data, or bounded tests for whole-OS production readiness.

H+: scoped reporting and recovery are achievable for tested schedules. H−: old UI demonstrably fails the two initial schedules, not a theorem that the broader goal is impossible. H∂: correctness depends on response ordering, availability and server data changing after an overview; stale data is not a snapshot lock.

## Frontier and source boundaries
MDN's fetch specification summary says HTTP error responses fulfill the promise, so callers need to inspect status/ok; network failures reject (https://developer.mozilla.org/en-US/docs/Web/API/Window/fetch). React documents cleanup before rerunning an effect with changed dependencies and on unmount (https://react.dev/reference/react/useEffect); neither source proves this component's complete behavior. No global best or impossibility result has been established. The open interface is reliable freshness and schema validation under all interleavings, and the much broader PWA and density requirements.

## Candidates and structural adversaries
Each is a falsifiable design contract, not a claim that all six were implemented or proved. Gaps are local to this overview unless stated otherwise.
1. Ignore failures (old artifact: silent catch). Gap: initial zero-looking and stale displays. Attacker: HTTP 500 and network failure; the two pre-repair browser cases failed. Not a solution.
2. Replace failures with zero: a concrete empty-value fallback. Attacker: nonempty real server data plus failed request; compare to live overview. Gap: truthfulness; not implemented.
3. Alert only: error banner, retaining old body. Attacker: initial error still displays false no-duplicates and zero counts. Probe initial failure plus absence of empty claim. Gap: local initial-state semantics.
4. Reject status and hide initial unknowns: gap out-of-order responses. Attacker: hold older failure, allow newer success, then release old failure; targeted browser test. Gap: local ordering.
5. Abort previous request: potential resource saving, but abort races with already resolved callbacks. Attacker: delayed completion around abort; would require generation guards too. Not implemented or benchmarked; local gap.
6. Latest-request epoch plus explicit unknown/stale state, HTTP status and top-level response-shape checks (implemented). Attacker: malformed 200, success-shaped body paired with 500, or delayed old failure. New browser tests attack all three; proof limited to measured schedules. Deep nested shape and all schedules remain open.
7. Server revisions/snapshots: concrete design would attach versioned revision to each response and compare on mutations; attacker changes data after preview or between GET and mutation. Not implemented; server and client transaction semantics are the interface, beyond this local fix.

Misleading results and distinguishing probes: 1 green build vs browser failure tests; 2 HTTP completion vs status; 3 200 vs malformed body; 4 `ok:true` body vs 500; 5 no exception vs rendered truth; 6 zero vs unavailable; 7 old rows vs stale warning; 8 warning alone vs retry recovery; 9 latest success vs delayed older failure; 10 request completion vs active component cleanup; 11 populated categories vs all nested fields valid; 12 preview count vs later purge contents; 13 one browser vs all browsers; 14 one test vs full gate; 15 passing gate vs Class A for all features; 16 elapsed wall time vs equal-fidelity Pareto speedup. The modal shortcut is catch-and-ignore: the initial 500 and failed-refresh tests directly detect it.
