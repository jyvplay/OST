# TT172 — Backup inventory uncertainty

## Model and predeclared threshold
Admissible object: the Backup /Backups inventory GET and local prune affordance in the existing PWA using the actual server and exclusive disposable PostgreSQL. Information: repository, HTTP, Playwright/real Chromium, Node/Next/TypeScript, database and public documentation. Count test verdicts, listed files and default-view words; no speed or throughput claim. For each tested schedule, a failed/malformed initial inventory must not claim the folder is empty; a failed refresh must mark retained rows stale and prevent prune based on them; a successful retry must expose real rows and permit normal action. No claim of all schedules, clients, response shapes or a transactional prune. Test timeout is a finite harness bound, not a latency guarantee. Build + pre-patch failure + new patch-targeted attacks + affected browser/backup tests are required before commit. The full gate is recorded without weakening any caps. Merge is not requested and PR stays open.

H+: explicit list state and guarded refresh can satisfy the tested schedules. H−: old catch-to-empty behavior fails at least an injected request failure; no whole-OS impossibility theorem is known. H∂: cross-tab changes or an interrupted multi-delete can change the truth after listing; a new list is not a lock. Distinguish an inventory from a verified restore, a successful GET from immutable snapshot isolation, per-panel guards from cross-client coordination, and a test pass from Class A.

Runtime actually available: shell/git/gh, public web search and fetch, Node, Next/TypeScript, real Chromium, disposable PostgreSQL and external oracle Python. No independent agent, theorem prover, simulator, expert or assistive-technology review. MDN explains that fetch does not reject for HTTP error statuses, so check Response.ok (https://developer.mozilla.org/en-US/docs/Web/API/Window/fetch). NIST SP 800-209 notes backup copies require correct generation, retention, secure storage and accessible restoration, and recommends periodic tests (https://nvlpubs.nist.gov/nistpubs/SpecialPublications/NIST.SP.800-209.pdf); neither fact proves this UI's behavior. Exact open interface: reliable fresh inventory and safe prune across concurrent writers or lost delete responses; this change does not solve those distributed problems.

## Candidate mechanisms, artifacts, adversaries
These are independent design contracts, not six implemented or proved solutions. Gaps are local except the full distributed retention workflow.
1. **Catch-to-empty (old UI).** Artifact: old code and pre-patch browser failure on HTTP 500. Attacker: actual nonempty folder plus failed GET; falsely displayed empty. Local information-loss gap.
2. **Retry automatically forever.** Artifact: bounded backoff design sketch; attacker holds service unavailable or recovers after client unmount. Cheapest probe: count attempts and ensure no false empty; resource/liveness gap is local. Not implemented.
3. **Clear list on failure with explicit warning.** Artifact: unknown-state contract; attacker loses access to a last-known useful list during temporary outage. Probe success→failure. Local usability gap; unimplemented.
4. **Retain rows, explicit stale indicator and disabled prune.** Artifact: implemented component. Attacker: delayed older response, malformed 200, failed refresh, repeated refresh and stale local actions; measured tests below. Local uncertainty remains across external writes and unmount.
5. **Abort previous request.** Artifact: cancel-controller design; attacker completes prior callback just before abort. Probe delayed success/failure racing abort. Needs generation ordering, local gap; not implemented.
6. **Server-issued snapshot plus atomic conditional prune.** Artifact: protocol sketch including version, selected names and compare-and-delete transaction. Attacker: another client replaces an identified file or loses the delete response. Probe concurrent rename/write and fault after commit. Gap is distributed lifecycle, wider than this local UI; not implemented.
7. **Client optimistic deletion.** Artifact: remove rows on activation; attacker fails second deletion after first succeeds. Probe response loss and inspect real DB. Local UI alone cannot prove atomicity; not implemented.

Misleading shapes and probes: 1 an empty array vs unavailable (HTTP 500 with real files); 2 rejected fetch vs HTTP failure (500 case); 3 200 vs valid response (malformed JSON shape); 4 old rows vs current (stale label); 5 stale label vs safe button (disabled assertion); 6 disabled render vs pending request (held refresh); 7 later-started success vs older failure (release reverse order); 8 retry click vs recovery (actual server rows); 9 filename displayed vs verified backup (no verification claim); 10 one list vs immutable state (concurrent writer test remains open); 11 one successful delete vs atomic batch (partial-failure test remains open); 12 test cleanup vs end-user data (only own checked-empty fixture paths purged); 13 fewer words vs comprehension (user/AT study remains open); 14 browser pass vs all browsers; 15 isolated passes vs full gate; 16 faster-seeming change vs measured equal-fidelity performance. The modal shortcut is catch-and-return-empty: initial failure against a nonempty real folder detects it.

## Results and limits
Old production: 0/2 fault cases, first timed out waiting for a warning; the second had no refresh action. New build compiled and the four real-browser tests passed, including a held response/race and malformed success. TT171 2/2 (430/440 on empty inventory), TT87 6/6, TT88 6/6, TT89 9/9 and TT123 UI 3/3 passed in separate targeted runs. No deletion was performed by the TT172 tests; fixture files were created under checked-unoccupied names and purged after. The stale list can still change after a successful GET, names may be replaced before pruning, multiple deletions are not a transaction, a failed/lost delete may partially succeed, and the refresh guard is not cross-tab. The race test uses a short post-response observation and does not prove all orderings. No 20 promotions, all-app visual review, independent human review or measured speed improvement is claimed.
