# TT213 — cooperative inventory guard for Backup Trash

## Contract and evidence threshold
Admissible objects are direct, live `/Backups` files observed by the UI, their name/id/version/SHA guards, the new guarded-Backup Trash operation, PostgreSQL transactions and VFS mutations that take the existing advisory lock. At most 10,000 inventory entries are accepted; a missing/malformed guard refuses. For each guarded request: after taking the exclusive VFS transaction lock, compare the captured live-file inventory with the current live-file inventory; if different, do not perform that request's Trash. If identical, the existing target guard and Trash transaction still apply. Each acknowledged successful Trash is removed from the next expected snapshot. The count/identity comparison and Trash share the transaction; this is not one atomic transaction for the whole batch. A lost response is unknown, not retried. Units: requests, database transactions, inventory entries, wall time. The UI sends the full captured list per target and the server reads/compares it per target; this adds O(files × requests) work and has not been benchmarked as a speedup. A folder over 10,000 files is refused, not partially pruned.

Information model: the client cannot know changes after its list; the server checks its current rows after waiting for the lock. The guard is cooperative consistency, not authentication or a defense against a client that lies about its snapshot. No trusted clock or cross-device global ordering is assumed. Different problems: durable generation order, whole-batch atomicity, unknown commit outcomes, old clients issuing legacy Trash, uncooperative SQL/older servers or writers outside the lock, detached database instances, independent storage, secure erasure and full OS/Class-A completeness.

H+: matching cooperative writes serialize through the shared/exclusive advisory lock, so mutations committed before the locked check can invalidate the snapshot. H−: uncooperative writers and separately committed batch operations cannot be covered by this protocol alone. H∂: the result changes with lock participation, request ordering, database isolation, inventory size, client/server version and failed acknowledgments. Threshold: prepatch real counterexamples; successful production build; real browser/DB test of insertion before the first request and between requests; patch-specific attacks on a retained-file rewrite, malformed guards and a held cooperating transaction; affected Backup regressions; explicit full-gate outcome. This is not evidence for all schedules.

## Frontier
PostgreSQL documents that [transaction advisory shared locks conflict with exclusive locks on the same key](https://www.postgresql.org/docs/current/functions-admin.html); locks require cooperating participants and transaction-level locks end at transaction completion. Under [Read Committed](https://www.postgresql.org/docs/current/transaction-iso.html), a new SELECT statement sees data committed before that statement begins. Here the inventory SELECT executes after obtaining the exclusive lock, and cooperative VFS writers take the shared lock before their mutation. This reasoning does not apply to raw SQL, older implementations, other databases or a writer outside the lock. `trashBackupGuarded` is a distinct operation: an older route's unknown-op default rejects it rather than silently ignoring the guard; this follows from inspecting the earlier route, not from a mixed-version deployed-server experiment. No external code was copied.

## Portfolio and attackers
1. **Client list then target-only guard**: TT212 actual counterexample and TT213 baseline 0/2: one extra future file caused two real deletes, even between requests. Local gap.
2. **Client refresh just before each request**: attacker writes after the response and before Trash. Another fetch narrows but does not close the TOCTOU window. Causal counterexample; cross-layer gap.
3. **Target row guard only**: the target may remain identical while a kept/new file changes; real retained-copy rewrite attack checks this. Local gap.
4. **Full captured inventory under cooperative transaction lock**: implemented. Actual tests cover added copy before/between requests, rewritten retained copy, bad input and an uncommitted shared-lock writer. Attacker bypasses advisory lock or uses older writer; unprotected and explicitly outside model. Cross-layer gap.
5. **Serializable transaction**: an option for coordinated database transactions, but serialization errors, concurrent non-participating writes, whole-batch contract, retries and uncertain acknowledgment require design and tests. Not implemented; cross-layer gap.
6. **Single atomic server batch**: could validate one inventory and perform every intended deletion in one transaction; would change existing partial-result behavior and requires explicit bounded request, locking and error/timeout semantics. Not implemented; cross-layer gap.
7. **Durable generation sequence**: can establish application-level order, but imports, legacy backups and multi-writer protocol are unresolved. Not implemented.
8. **Forbid pruning**: conservative but removes working ordinary retention; existing successful prune test rejects that alternative.

Misleading results rejected: fresh fetch treated as atomic; target unchanged treated as inventory unchanged; shared lock assumed mandatory for raw SQL; guard silently dropped by old server; inventory list measured outside transaction; actual commit loss called rollback; partial batch called atomic; future warning yet Trash sent; new file inserted between requests ignored; retained file rewritten without detection; duplicate guards accepted; no guard accepted; malformed hash accepted; 10,001 entries truncated; stale name without identity; browser clock called trusted time; captured list called refreshed; security inferred from advisory lock; simulated database called real; one Chrome run universal; faster claim without timing; passing targeted tests called green full gate; app fix called ten Class-A features.

## Actual observations and limitations
Actual tools used: Git/gh, shell, web research, Node 22, production Next/TypeScript build, ESLint, Chromium 143 via Playwright and exclusive disposable PostgreSQL. No independent agent, theorem prover, simulator or independent expert was used. TT213 baseline before server fix: 0/2 real browser tests; both caused unwanted Trash. After the first implementation, 5/5 including new attackers passed. A second-order review found that sending an extra field on legacy `trash` could be silently ignored by an old server, so the gate was stopped and a distinct operation introduced. The rebuilt final version passed TT213 5/5, TT211 2/2, TT172 4/4, TT173 4/4, TT174 2/2, TT175 2/2, TT176 7/7; the prior TT212 attack now reports all five files live. The held-lock test uses a real PostgreSQL transaction, takes the shared advisory lock, inserts a row, observes no response for 300 ms, commits, then observes HTTP 409 and unchanged original targets. This observes one schedule, not every lock interleaving. A test-only direct SQL writer cooperated explicitly; raw SQL that does not take the advisory lock is outside the guarantee. The new endpoint's malformed/missing guard tests returned 400 without trashing the target; old unguarded Trash remains supported and is tested by TT174.

The previous TT212 counterexample script now asserts the fixed outcome; TT212 documentation records the original historical run. A moving system clock after a particular check, uncertainty once clock catches up, changing inventory by uncooperative writers, batch partial completion, stale old clients and a lost server response remain unresolved. No all-app visual audit, graphics, ten Class-A promotions or Pareto speedup is claimed. The full gate result is appended below.
