# TT199 — measure Files fixture concurrency; attack no-match policy

## Scope and acceptance
Admissible objects: a production app with exclusive disposable PostgreSQL, actual `/api/fs` operations, a real Chromium browser suite and a 2-CPU sandbox. Resources: wall milliseconds for 41 fixture writes, whole-suite wall seconds, and shell-reported client/child CPU seconds; server CPU was not measured. Success for a proposed optimization requires preserving all actual browser assertions and file identities/content, waiting for outstanding writes before cleanup, and a repeatable significant end-to-end improvement without greater CPU or reliability costs. Three suite samples and no server CPU measurement are insufficient for a Pareto claim. Separate issues not to substitute: faster setup vs faster suite, client vs server CPU, timing on one host vs general performance, browser tests vs AT, and regression tests vs production feature completeness.

H+: independent writes may overlap and reduce fixture latency. H−: on this 2-CPU environment overlap may add contention or fail to improve whole-suite cost. H∂: outcome changes with connection latency, server load, file size, concurrency and scheduling. We keep no optimization unless the evidence meets the above threshold. The bounded reproducibility artifact is `scripts/tt199-files-fixture-benchmark.mts` (requires BASE, DATABASE_URL and TT89_DISPOSABLE_DATABASE=1, only on an exclusive disposable DB). It executes 9 alternating real batches, verifies all 41 names and all contents each round, and purges each directory. It is not in the ordinary gate and does not measure full-suite or server CPU.

## Frontier and approaches
Promise aggregation can reject before other operations stop; see [Promise.all discussion](https://www.tidyurls.org/blog/promise-all-vs-promise-allsettled). This does not prove any server transaction or cancellation property. The open interface is performance and failure cleanup on this app's VFS, not general promise scheduling.

1. **Serial**: unchanged TT193 fixture; real three-run suite baseline 2/2 each. Attacker is high per-request latency; benchmark shows slower setup on this host. Local potential cost, not proof of bad overall performance.
2. **Two bounded writes per batch using allSettled**: actual experimental patch awaited every batch and rejected any failure before cleanup. All three browser suite runs passed with same wide geometry; attacker is whole-suite CPU/contention. Measured median wall worsened, so patch was reverted. Failure cleanup under network hangs was not tested; local unresolved gap.
3. **Two continuous workers**: experimental real API benchmark verified file names/content and showed setup latency reduction. Attacker is a worker failure leaving another still writing; benchmark used allSettled but has not been subjected to a held-open/failure attack. Not adopted; local correctness and suite performance unproven.
4. **Unbounded parallel requests**: causal resource-counterexample is 41 simultaneous DB writes on 2 CPUs and fail-fast cleanup races; no implementation or claim of timing. Cheapest falsification: lock/throttle one write and observe cleanup. Local resource/safety gap.
5. **Batch database insert or fixture bypass**: would alter API/journal behavior and no longer exercise the same real write path; existing 41 HTTP writes are the comparison artifact. Attacker inspects missing side effects. Not adopted; fidelity gap.
6. **Two browser lanes**: historical `run-gate.sh` records no speed improvement and timeout failures on 2 CPUs. That historical artifact is not a fresh experiment this turn. Attacker: simultaneous high-CPU browser suites. Broader shared-state/CPU gap.

Modal shortcut: `Promise.all` appears to wait for a batch, but rejects on the first failure while other writes can remain in flight; cleanup can race those writes. `allSettled` drains each batch in the experiment, but a real lock/failure attack remains unrun. Other misleading shapes: fewer files; names only but wrong content; synthetic database; changed fixture geometry; single lucky sample; comparing warm and cold runs; excluding setup; measuring only client CPU; assuming wall gains prove CPU gains; ignoring browser children; abandoning concurrent writes on rejection; swallowing errors; parallel suites sharing DB; unbounded concurrency; changing timeouts; changing expected failures; content regenerated differently; one host treated as universal; benchmark outside gate treated as gate success; using synthetic key events as real IME; a narrow fix called Class A. These are failure/evidence shapes, not claims of full coverage.

## Results and independent attack
The checked-in benchmark on the real app produced serial write-wall ms `[875,860,734,686,659]` (median 734) and two-at-a-time `[521,516,447,422]` (median 481.5); every round verified 41 names and contents. These are small, alternating, non-randomized samples, not a full-suite or CPU improvement. Actual TT193 serial whole-suite wall seconds were `[11.539,11.889,10.922]` (median 11.539); experimental two-at-a-time `[12.921,11.638,12.411]` (median 12.411), with 2/2 browser tests and the 18 vs old-estimated 19 columns in every run. Shell-reported client/child user+system CPU was noisy: serial `[5.277,18.857,5.011]`, experimental `[21.355,5.891,5.533]` seconds; server CPU was not measured. This does not establish a speedup or Pareto improvement, and the experimental suite edit was reverted.

The open PR's type-ahead policy was also attacked: a new actual browser test types `b`, then an invalid extension `c` while Charlie exists; focus must stay on Beta and the next `b` starts a fresh search. A temporary independently constructed product mutation that immediately retries the last character failed this test 0/1; the mutation was removed and the restored production build passed all four TT198 tests. This is a mutation test, not a real user or IME trial. Available and actually used: shell, git/gh, web search, Node/TypeScript, ESLint, Chromium 143, disposable PostgreSQL and gate oracles. No independent agent, expert, theorem prover, or simulator was used. No all-app visual review, original graphics, ten Class-A promotions or verified OS-completeness percentage was established.
