# TT163 — bounded automation-token list

## Contract, evidence threshold and runtime
Object: the Routines window's server-backed automation token list in the existing PWA, not token authentication or the whole OS. Access: source and live local production build, HTTP and disposable PostgreSQL, Chromium/Playwright, TypeScript/Next build, and public documentation. No other agent, simulator, theorem prover, expert review or assistive-technology system participated. Unit of pagination: eight matching token rows; ordering remains the API's ascending creation-time order. For any fixed API response and text query, the client filters the complete response by case-insensitive substring of ID, name, scope and live/revoked label, displays successive slices without modifying the data, and clamps the requested page if the list shrinks. There are no server-side pagination or large-response memory guarantees.

H+: bounded visible rows and discoverable search/navigation can preserve list operations. H−: this does not solve all density requirements or prove universal accessibility or eliminate race conditions. H∂: concurrent list mutations, tied timestamps, browser/AT differences and very large result sets require more conditions. For this local patch the declared evidence threshold is: production build and typecheck pass; an adversarial real-browser test must fail the old build and pass the repair; affected existing Routines, planner and automation browser suites pass; no pre-existing density checks are weakened. A full passing gate on the exact build is required for merge, not inferred from targeted tests. Speed superiority additionally requires controlled before/after CPU and wall-time measurements at equal fidelity.

## Causal evidence and implementation
Before the change the real database contained 94 token rows and 10 routines; the page rendered every token. The new client-side search and pagination leave token mint, copy, revoke and audit API intact; filters do not delete records. A newly minted token resets the search and selects the last page based on the prior list length. The 11-owned-token attack failed on the old server because no token searchbox existed. On the rebuilt production server it passed: search, first and second pages, keyboard Enter/Space navigation, exact token ID search, later-page revocation confirmed through the server, unaffected earlier token, no-match handling and search reset. Its owned token rows are deleted in finally on the disposable database; audit entries persist. This is one controlled scenario, not an exhaustive proof.

Production build passed. Targeted e2e TT163 1/1, planner TT158 1/1, automation TT146 5/5 and routines TT147 6/6 passed. TT124 density still failed 21/23: Routines 480/300 and Storage 579/480. TT162's earlier run recorded Routines 1406/300, but database and test state differ, so these numbers are not a controlled causal benchmark. No caps or fidelity assertions were removed. The extra search field and page controls are a trade-off, not a demonstrated Pareto improvement for every user; the list still fetches all records.

The existing TT162 report contains the six distinct mechanisms, candidate-specific attacks and 15+ misleading result shapes; they are not established solutions. Here the chosen pagination candidate's attacker is an 11-item search result with an actionable item on the next page. Rendering only the first eight without navigation/search would conceal a revocable credential; the real server test catches that shortcut. Other unresolved attacks include simultaneous external minting and a changing filter between page selections, timestamp ties, very long names, thousands of records, and screen-reader discovery of repeated Revoke buttons. Mint's initial selected page is computed from the previously loaded count, so concurrent new tokens may leave the newly minted row on another page; its secret is nevertheless shown in the existing one-time panel. These are not claims of universal correctness.

A W3C disclosure example describes keyboard-operable disclosure and visible state under its stated markup and interaction assumptions: https://www.w3.org/WAI/ARIA/apg/patterns/disclosure/examples/disclosure-card/. It is design context, not an independent verification of this pagination UI. No best-known global achievement or impossibility result for the complete OS task has been established. The open interface is preserving discoverability, focus and data access for changing/large lists while meeting separately validated density and accessibility requirements; the next high-information test is a deterministic concurrent-mint/list-reordering browser test and real assistive-technology review.
