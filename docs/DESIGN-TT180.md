# TT180 — mint recovery timing and external framing evidence

## Contract and information model
Admissible system: the current Routines UI, its token HTTP API, real PostgreSQL and Chromium, plus test-only interception that delays or fails selected HTTP requests. A tester may observe DOM state, requests and database rows and control request delivery; this is fault injection, not an independent network outage or a complete proof. Resources: wall-clock seconds and two logical CPUs, not a measured CPU or memory budget. For every tested failed-mint schedule, while the recovery list request remains pending the UI must warn that creation might have committed, hide any unreceived secret, prohibit another mint and explain the delay; after the recovery settles it must permit a deliberate retry when scopes remain selected. A successful mint must remain locked while its one-time secret is displayed. This is a bounded behavior contract, not a quantification over all schedules or the entire OS. No response-time guarantee exists for a server that never responds. The test waits up to 10 seconds for retry after release, not a production timeout.

H+: this bounded contract can be achieved and observed with real browser, server and DB. H−: without additional response or protocol assumptions, a lost POST response alone cannot distinguish a committed creation from failure before commit. H∂: liveness depends on recovery request settlement; externally observed GitHub framing depends on TLS trust and network. Evidence threshold: production build, real-browser held-refresh attack and failed-refresh attack, adjacent token regressions; never promote the entire app to Class A from these checks.

Adjacent non-equivalent problems: exactly-once minting, durable idempotency, server-side recovery of one-time secrets, automatic retry safety, hardware or screen-reader accessibility, testing all apps, system-wide completeness, and Pareto-optimal test performance.

## Frontier and evidence boundary
Playwright documents auto-retrying locator assertions, including `toBeEnabled`, unlike immediate state sampling: https://playwright.dev/docs/test-assertions . This applies to a locator during the assertion timeout; it is not a proof that a user ever sees a usable control in every execution. Node documents that `--use-system-ca` adds system trusted CAs to the selected trust configuration: https://nodejs.org/learn/http/enterprise-network-configuration . This is appropriate only when the operator trusts that system store; it does not justify disabling certificate validation or guarantee any endpoint's policy. Fetch does not treat an HTTP error status as a network rejection: https://developer.mozilla.org/en-US/docs/Web/API/Window/fetch . None of these imported descriptions proves the application's end-to-end correctness.

Open interface: TT179's timing failure is consistent with the UI showing the error before its awaited refresh finishes. The new held-request attack constructs this exact interval but cannot prove it was the particular schedule that caused the earlier failure. A lost response still has ambiguous commit status. Separately, TT134's failure can depend on the server's TLS configuration, which is distinct from the test runner's Node flags.

## Mechanisms, artifacts and adversaries
1. **Immediate enabled sample** (old test, executable history): cheapest attack holds the post-error GET; observed button disabled. It incorrectly assumes warning render implies refresh settlement; local test-ordering gap.
2. **Wait for observable enabled state** (implemented test): Playwright polls the control up to 10 seconds; new held-GET and failed-GET attacks test both intermediate safety and eventual recovery. Not a guarantee of liveness when GET never settles, nor an exact diagnosis of the historical failure.
3. **Release lock before refreshing** (design, not implemented): would remove this wait but allows another creation before the user can inspect a newly committed row. Attack: commit POST, drop response, delay listing, click retry; ambiguity remains. Local safety gap.
4. **Add timeout to recovery fetch** (design, not implemented): bounded UI waiting, but old responses can arrive late unless aborted and/or versioned; a timeout cannot reveal whether creation committed. Attack delayed old result after a later refresh. Local race plus protocol gap.
5. **Idempotency key with durable server record** (design, not implemented): correlate retries with one logical creation. Attack concurrent duplicates, transaction rollback, lost key and lost secret; requires durable protocol and careful secret treatment. Cross-API/storage gap.
6. **Operator-trusted system CA in server process** (experiment, not code change): observed verified GitHub probe change from TLS uncertainty to reported X-Frame-Options denial, without turning off validation. Attacker: untrusted system root or later remote policy change. Deployment trust/availability gap; it is not proof of internet-wide policy.
7. **Fake the deny response** (rejected design): would exercise a rendering path but cannot establish external peer behavior. Attack: real TLS verification failure or changed peer policy. Equivalent to losing the particular integration claim.

Each unimplemented item is a candidate, not a completed solution; no external code was copied. The held request and request aborts are test-only fault injection around real browser/server/database operations.

## Negative space
An error badge is not refresh completion; enabled eventually is not enabled immediately; an enabled button is not proof of a failed commit; failed fetch is not rollback; HTTP 500 is not necessarily a rejected fetch; a stale list is not an empty list; one successful GET is not a stable global snapshot; a displayed secret is not recoverable from a stored hash; a click is not a single server transaction; one lock is not a cross-tab lock; successful refresh is not proof another client did not mint; a trusted system CA is not a universally trustworthy CA; TLS failure is not framing denial; a framing header is not evidence of unrelated content; a screenshot is not accessibility verification; one Chromium is not all browsers; one passing suite is not a full gate; a lower wall time is not Pareto superiority; a saved ledger label is not an independently verified Class-A rating. The modal shortcut is sampling enabled immediately after the warning: the held-GET test forces the warning visible while the button is correctly disabled.

## Executed results and remaining gap
Available/used: local shell and Git/GitHub CLI; web search; Node 22, Next/TypeScript build; Playwright Chromium 143; a local disposable PostgreSQL; actual production Next server. Two CPU logical processors reported. No independent agents, theorem prover, simulator, human accessibility review, external expert or full all-app survey used. Dependencies and browser/database test tools installed locally; no new shipped package.

Production build passed with DATABASE_URL (first attempt omitted it and failed). Real browser mint suite: 6/6, including held recovery, failed recovery, response lost after actual commit, duplicate activation and masked clipboard history. Token paging 1/1, race 4/4, recovery 4/4, DB atomicity 4/4, revoke 4/4, storage recovery 5/5, and Routines 2/2 passed. TT134 review: 6/8 with the initial server (probe reported `unable to verify the first certificate`); after restarting the *server* with `NODE_OPTIONS=--use-system-ca`, direct probe reported HTTP 200/X-Frame-Options deny and the full TT134 review passed 8/8. This compares configurations on this machine, not all deployments. TT179's suite-runner flag was not necessarily inherited by an already running server. No TLS verification was disabled. The Routines pending-state screenshot was visually examined; other applications were not comprehensively reviewed.

The full gate was not rerun here and previous incomplete/failing gate remains historical evidence, not a pass. The recovery list request can hang indefinitely; the failure warning remains ambiguous, the server has no exactly-once protocol, and accessibility beyond the role=status markup is unverified. No 20 Class-A promotions, new graphics, all-app visual inspection or measured Pareto speedup. The historical register is self-reported, not independent evidence of completeness. Highest-information next tests: hold and release out-of-order recovery responses under multiple clients while testing a bounded/abortable recovery design, then run the full gate against a deliberately configured disposable server with its trust store explicitly documented.
