# TT217: acknowledge preset deletion honestly

## Model and threshold

Admissible requests are user-initiated deletion of a named preset from Routines, in one mounted component and one browser, against the current HTTP API and shared PostgreSQL database. The network can reject, delay, truncate or lose a response after a real commit. Success for an individual invocation is shown as confirmed only after a non-aborted 2xx JSON response containing `ok:true`; otherwise the UI must say unconfirmed, not automatically retry, preserve a warning even if the row disappears, and refresh the list with its existing bounded/error-reporting behavior. Concurrent clicks on the same component/ID are sent at most once while that invocation is locked. This is conditional on browser fetch and timer progress; 12,000 ms is the deadline passed to a timer, not a hard real-time bound. API response correctness, successful database commit, list freshness, cross-tab locking, stale deletion, safe retries, user authorization and eventual completion are distinct problems.

Threshold: real Chromium against a disposable PostgreSQL-backed app; demonstrate pre-patch failure; production build; post-patch rejection, lost committed response, delayed committed response, malformed response and ordinary delete; rerun affected suites and report full gate separately. These are observed executions, not universal proofs or production-readiness/Class-A certification.

**H+**: under compliant fetch and a mounted component, confirmation validation and scoped duplicate-click suppression are implementable; tested examples pass. **H−**: the same client-side lost/timeout observation can follow either a committed delete or no delete, so silence alone cannot establish which happened. The current unguarded delete cannot distinguish an old resource from a replacement sharing the ID. **H∂**: safe stale-delete prevention requires additional generation identity and an atomic server predicate, with a migration and a protocol that older servers do not silently ignore; durable retry/result identity needs further atomic retention and lifecycle decisions.

## Mechanisms and attacks

1. **Bounded fetch plus honest warning (implemented):** validate body/status, abort after 12 s and do not automatically retry. Artifact: `Routines.tsx`; tests include a real committed delete with response deliberately lost/held. Attacker: commit after timeout or loss; warning remains unconfirmed, but doesn't reconcile it. Next test: actual server-side lock hold across timeout; local uncertainty gap.
2. **Per-component ID lock (implemented):** `Set` checked before sending and a disabled button prevent simultaneous duplicate local clicks. Held-response test dispatches two clicks and sees one request. Attacker: another window, tab or legacy client; locks are not shared. Next test: coordinate simultaneous tabs. Gap is cross-client concurrency.
3. **Versioned conditional delete (not implemented):** server mints a non-repeating per-generation identity on creation; delete must atomically compare the identity and ID, and refuse mismatches. Attack: delete/recreate ABA, legacy writes or name reuse with the same version. Next test: hold a stale request, delete/recreate, release it, verify replacement survives. Gap is schema/migration and all-writer interoperability; timestamp or reset revision alone is not enough.
4. **Transactional durable operation record (not implemented):** commit operation ID, payload fingerprint and delete outcome together; identical retry reads recorded outcome. Attacker: key reused for different data, concurrent attempts, deletion of retention record or crash before commit. Next test: real transactional barriers and restart. Gap is retention and schema lifecycle; not equivalent to the entire OS.
5. **Read-after-timeout (rejected as proof):** refreshing the list is useful but cannot rule out a late request. TT216's real lock test demonstrated the corresponding late *create*. Attacker delays delete until after refresh and an intervening replacement. The standalone `scripts/tt217-delete-aba-counterexample.mts` tests repeated HTTP DELETE with intervening replacement; it is deliberately not an acceptance gate and documents the current hazard rather than endorsing it.
6. **Confirmation dialog alone (rejected as concurrency control):** consent can authorize an intended action but cannot freeze a mutable row or prove server completion. Attacker replaces the row after confirmation. Cheapest falsification: two clients and a barrier. Local precondition gap.
7. **Whole-table/advisory lock (not implemented):** lock during read and deletion, if every writer honors the chosen mechanism. Attacker is a legacy/uncooperative writer or an old request arriving after lock release. Cheapest test: concurrent direct SQL or legacy PUT. Gap includes writer compatibility and cannot resolve response loss alone.

[HTTP semantics RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.2.2) defines DELETE as idempotent in terms of intended effect of repeated identical requests; this does not prevent an intervening actor from creating a new resource at the same ID. [If-Match](https://www.rfc-editor.org/rfc/rfc9110.html#section-13.1.1) uses strong comparison to make operations conditional; a correct generation validator and atomic database enforcement would still have to be designed. No cited code was copied.

## Misleading result shapes

Do not substitute: (1) HTTP status without checking the body; (2) malformed 200 as success; (3) fetch abort as rollback; (4) empty list immediately after timeout as final; (5) a 503 as proof that the database did nothing; (6) a button lock in one component as a cross-tab lock; (7) HTTP idempotency as a defense against an intervening replacement; (8) retrying a delete by name as a version guard; (9) a timestamp as a guaranteed non-repeating generation; (10) a revision reset to one as an ABA defense; (11) a modal as a database lock; (12) stopping keyboard events only inside a dialog as global modality; (13) a transport fault injected by Playwright as a real network outage; (14) one browser's green suite as assistive-technology coverage; (15) a clean-database density run as the populated full gate; (16) a partial timing win as a full-gate Pareto improvement; (17) a self-assessed feature register as independent Class-A proof. The existing TT215 modal browser test first proves the shortcut works outside the dialog, then moves focus behind it and verifies Meta+A is blocked; stopping propagation only inside the modal would miss that event. It tests that one shortcut and browser, not all modality cases.

## Evidence and gaps

Runtime tools actually used: Node/Next/TypeScript build, disposable PostgreSQL, Chromium 143 with Playwright, test-only HTTP interception, shell, ESLint and web search. No independent agents, theorem prover, simulator, expert review or cross-browser evaluation was used. The pre-patch browser suite failed 0/2 for missing delete warnings. Patched TT217 passed 5/5 (rejection, lost response after commit, held response/double click, malformed 200, confirmed delete). TT216 refresh 3/3 and late-create 1/1; TT215 4/4; TT214 5/5; TT157 2/2. A TT215 locator initially matched both Restore and the new accessible delete name containing a preset called `restore`; exact role-name matching corrected the test, after which it passed. The real DELETE route remains unchanged and unconditional. Warnings and locks are not persisted across reload and do not prevent other tabs or older clients. The list refresh can itself fail; it uses TT216's stale-list warning. Deletion can take up to the request timeout plus the refresh timeout and scheduler delay. No overwrite UI, durable reconciliation, atomic versioned delete, full OS review, ten Class-A promotions, original graphics or measured Pareto speedup was achieved. The additional tests add work, not a demonstrated speedup. The previous full gate was red; this turn's gate outcome is recorded below when complete.

## Final results

The standalone ABA counterexample ran against the real API and disposable database: it created an original, deleted it, created a distinct replacement under the same ID, then sent the same unguarded DELETE again; the replacement was gone. It does not assert the timing of a particular browser retry; it demonstrates the API-level hazard. It cleans up its own key.
