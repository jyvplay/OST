# TT157 — safe routine trigger inputs

## Scope and formal contract
Admissible objects: routine rows with a whitelist of shell actions and the existing manual, interval, time-of-day and display-connected triggers. Access: one Next.js server, PostgreSQL, and real Chromium pointed at an exclusive disposable database. Count a firing as the existing shell executing a row's actions, then writing lastRun; time is local civil time for daily triggers and milliseconds for intervals. The scheduler is a 60-second foreground-page poll, subject to governor and browser throttling; it is not an OS scheduler.

The narrow safety predicate: for each new or legacy row, if its interval or time string fails the validator, then no poll executes it automatically; a new invalid trigger receives HTTP 400. For valid intervals in [1, 525600] minutes, due means no lastRun or elapsed time at least the interval. For valid HH:MM values 00:00–23:59, due means local time has reached today's target and lastRun precedes it. Display events retain the existing sampled rising-edge semantics. Manual run remains possible. Quantifier order: for every input considered, for each poll, invalid values are rejected or skipped; the tests cover a finite selection rather than proving the universal predicate. Valid display sensing, reliable timing across tab closure, exact-once execution in multiple windows, DST policy and scheduler recovery after crashes are distinct problems and not claimed solved.

H+: shared validation can prevent malformed schedules being guessed into executions. H−: the complete native OS automation specification cannot be guaranteed by an intermittently running browser page alone under this access model. H∂: supported browser APIs, display policy, DST, sleeping tabs, failures and multiple shells alter behavior; additional coordination and platform support are needed. Evidence threshold for this bounded change: production build and real HTTP plus real browser demonstrating invalid refusal, a running valid control, and legacy skip; full merge requires the full project gate, not merely these tests.

## Frontier and six candidates
The prior code coerced blank interval to 60 and malformed time to midnight. Browser timers are throttled in background pages ([MDN Page Visibility](https://developer.mozilla.org/en-US/docs/Web/API/Page_Visibility_API)); `Screen.isExtended` is experimental, secure-context limited and may be false when policy blocks it ([MDN Screen.isExtended](https://developer.mozilla.org/en-US/docs/Web/API/Screen/isExtended)). Neither source establishes exact timing or multi-window execution semantics.

1. **Shared validator + fail-closed poll** (implemented): `src/lib/routine-trigger.ts`; HTTP, UI and scheduler share parsing. Pure boundaries and real PostgreSQL/Chromium test are evidence, not a formal proof. Attack: pre-existing invalid DB row; tested alongside a valid sentinel that actually ran. Gap: coordination and delivery, global to scheduling.
2. **Validate only at HTTP** (rejected): counterexample is a pre-existing invalid DB row; adding an API check leaves the existing client coercion. Cheapest falsification: insert legacy row and start the shell. Local gap, tested by the new end-to-end attack.
3. **UI-only validation** (rejected): direct HTTP bypass is a concrete counterexample. Cheapest test: POST malformed values. Local gap; tested.
4. **Default invalid input to midnight or 60 minutes** (rejected): causal counterexample is a malformed string which changes desktop state at a time never selected. Old production server returned HTTP 200 to a blank interval before patch. Local gap.
5. **Cross-window database claim/lease** (not implemented): would serialize competing shells before action execution, requiring crash and stale-lease semantics. Attack: claim succeeds, browser crashes before or during execution. A simple lease does not prove exactly-once effects; global gap requires coordinated action semantics and recovery test.
6. **Native/background scheduler** (not implemented): could improve delivery when the page is closed, but a PWA cannot assume such a service or device privileges. Attack: close all tabs or deny background capability. Global platform gap; browser-only timing claims must be downgraded.

## Negative space
A green build is not a full gate; a unit parser is not a real scheduler; API rejection is not protection of old rows; a UI disable is not server validation; a status label is not behavior; a dry run is not execution; a created row is not a fired action; a zero lastRun is not evidence a polling loop ran; a mock clock is not a real browser timer; one successful run is not exactly-once; an elapsed interval is not a calendar schedule; local midnight is not a universal time zone; a sampled display edge is not reliable hardware discovery; a silent fallback is not user consent; a PWA background tab is not an OS service; a historical receipt is not a current gate. The shortcut especially dangerous here is API-only validation: the new legacy-row test inserts directly into the disposable PostgreSQL database and asserts skip while a valid sentinel fires.

## Actual verification and limitations
No external agents, theorem prover, simulator or expert reviewer were used. TypeScript/Next production build and Node pure tests were run locally; PostgreSQL and Chromium 143 were real. Before implementation the new end-to-end test failed both its HTTP and legacy-row checks against the previous production build. After the patch it passed 2/2: invalid HTTP values rejected, valid row accepted, legacy invalid row skipped, valid sentinel executed, and browser form showed an error. Pure boundary test passed 1/1. The screenshot records the valid sentinel opening Notes, which obscures part of the Routines window; it is not a full UI visual audit.

Known adjacent risk discovered during review: `automation-entry.ts`'s local planning token check does not compare the request token value or mark the stored token used. That local planning UI is distinct from the server's bearer-token queue; no claim is made that either entry surface meets a complete cross-origin security contract. A separate security repair and adversarial real multi-origin tests are needed.

Full-gate and density results are reported separately when known; no Class-A promotions, all-app visual review, original graphics, measured test-speed gain, screen-reader evaluation, or 20 new features are claimed here. The highest-information next test for scheduler completeness is two independent real browser contexts competing for one due row, with action outcome and crash recovery measured; implementation requires a carefully designed claim protocol, not a cosmetic test change.
