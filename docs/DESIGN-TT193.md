# TT193 — Files grid keyboard movement

## Runtime, model and threshold
One coding agent used Bash, Git/gh, web research, Next/TypeScript production build, ESLint, real Chromium 143 through Playwright, and a disposable PostgreSQL-backed server. Two CPUs were available; mutating browser suites shared an exclusive database and ran sequentially. No independent agent, simulator, theorem prover, expert, or actual assistive technology was used. The code is independently written and adds no dependency. Real Files UI, server-created files, browser keyboard events and actual rendered element positions are exercised; no test fixture pretends to be a file operation.

Admissible objects: a Files list/grid of rendered options in DOM order, a focus/selection state, an ArrowDown/Up input, CSS-pixel rectangles and layout dimensions. The attacker controls file count, pane width, filter, modifier and key sequence. The selected contract is the existing product's spatial grid behavior: in a regular row-major grid, up/down move by its rendered column count, clamped at ends, retaining existing modifier behavior. Quantifiers: for each exercised width, count, position and modifier, if options form a regular CSS row-major grid with the same first-row top within one CSS pixel and the browser renders it, focused destination and selection must agree with measured geometry and existing `keySelect`; in list mode step remains one. Failure is wrong focus/selection or broken existing file features. Units: CSS pixels, one-pixel top-coordinate tolerance, integer DOM indices. Tests prove their cases, not all devices or grids. Arbitrary transforms, reordered/dense/spanning grid placement, vertical writing modes, changes during a keyboard event, real AT, and universal Class-A OS completeness are different problems.

H+: actual geometry can determine the regular rendered row width, including gaps. H−: dividing the container width by a rounded item width cannot generally infer track count if gaps/fractional tracks are ignored; the 2786px experiment is a counterexample. H∂: layout, scale, width, gaps, item count and selection modifiers alter the result. Evidence threshold: prepatch failure in real browser from measured geometry; production build; postpatch wide and narrow/filtered/list attacks, affected Files and broader regressions, plus honest gate report. The actual test evidence is finite, not a proof of all positions or cross-browser semantics.

## Frontier and mechanisms
[MDN gap](https://developer.mozilla.org/en-US/docs/Web/CSS/gap) states that grid gaps are space between tracks and that margins, padding, or distributed alignment can make visible spacing larger; width/item-width alone omits that space. [W3C listbox pattern](https://www.w3.org/WAI/ARIA/apg/patterns/listbox/) describes vertically oriented listbox down/up as next/previous option and modifier selection models; it does not certify this spatial grid implementation. Files currently exposes the grid visually under listbox semantics, so actual AT interpretation and whether a grid semantic pattern is preferable remain unresolved. Merely passing this test is not WCAG certification.

1. **Measured first-row positions (implemented):** count until a row top changes by more than one CSS pixel, only for grid up/down; reuse existing selection logic. Real wide/narrow and modifier browser tests. Attack transforms, reordered or staggered positions, or many columns causing layout reads. Gap local to layout assumptions and performance; cheapest test: real resize immediately before keypress and heterogeneous content.
2. **Round container/item width (baseline):** real Chromium counterexample: width 2786px, actual 18 columns, estimated 19; down from item 0 focuses 19 not 18. Gap local geometry.
3. **Width plus computed gap formula:** valid only when track widths, gap, container box and alignment follow the assumed formula and rounding is handled. Attack fractional tracks, scrollbars, padding or variable sizes; cheapest test compare against rendered positions at threshold widths. Causal design only; local gap.
4. **Parse computed grid-template-columns:** may include empty auto-fill tracks even when fewer items exist; depends on serialization and explicit/implicit placement. Attack a one-item grid and browser-specific serialization. Causal design only; local gap.
5. **Search nearest visual neighbor on every key:** geometric nearest-x/y could support irregular layouts but has more edge rules for partial rows and selection; attack reordered overlapping or spanning items and compare against declared keyboard semantics. Executable idea only; local design gap.
6. **Fixed number of columns in CSS and keyboard:** removes responsive adaptability or requires breakpoints, and font/zoom/container changes can invalidate assumptions. Attack resizing across a breakpoint. Causal design only; local gap.
7. **Change to a fully specified ARIA grid pattern:** potential broader semantic fix requiring row/cell roles, focus model, selection, keyboard and real AT review. Attack existing listbox operations, single-column view and focus ordering. Design only; local accessibility contract is not proved by this patch.

## Negative space and modal shortcut
A visible badge is not keyboard access; DOM order is not necessarily visual order; width divided by item width is not track count when gaps exist; CSS grid is not an ARIA grid; a listbox role is not proof of correct grid semantics; selected is not focused; Ctrl movement is not selection; Shift range is not a single row; a passing 1800px run is not a wide-layout proof; a one-item grid is not an empty grid; clamping is not wraparound; a browser key injection is not a physical keyboard survey; a screenshot is not an all-app audit; one browser is not cross-browser proof; a build is not a functional test; a test oracle sharing the product's arithmetic can repeat the same bug; one layout is not every zoom or writing mode; clipped DOM text is not necessarily visible text; fewer counted words is not automatically better usability; a ledger entry is not Class A; more tests are not measured faster tests. Modal shortcut: infer the number of actual columns from a width ratio without including the gaps. The new independent geometry test groups actual row tops and detects the wrong destination; the 1800px baseline pass before the 2800px counterexample illustrates why one passing width is insufficient.

## Verification and gaps
Before the patch, a 1786px listing happened to pass (11 actual/11 estimated). At 2786px the old code failed 0/1: 18 actual columns versus 19 estimated. Production build passed after repair; the final TT193 suite passed 2/2, covering 41 real files, wide/narrow grid, up/down, Ctrl movement, Shift range, end clamping, one filtered item and list mode. Test-file and changed-product-file ESLint, shell syntax and diff checks passed. Complete gate `.cache/gate/20261119T185837Z/run-93994-6OAk0l` failed TT124 Routines 332/300, TT125 Files 375/260, TT123 Files 375/320; TT193 passed 2/2, TT192 2/2, TT191 4/4, TT55 Files 15/15, TT183 5/5, TT155 Files 1/1 and e2e-a11y 9/9. A generated dual-pane Files screenshot and Routines/Notes screenshot were inspected, not all apps or assistive technologies. The change does not fix the separate data-dependent Files/Routines density contracts; TT186 showed legacy counters include clipped rows, not that their caps should be weakened. No measured speedup, comprehensive visual review, new graphic set, or ten Class-A promotions are claimed. The next highest-information tests are width/zoom resizing during active keyboard navigation, one-column and empty layouts, cross-browser rendering, and actual screen readers; a full ARIA grid assessment remains separate.
