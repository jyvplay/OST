# TT182 — bounded automation-token creation wait

## Contract and hypotheses
Objects: the real Routines panel, its POST and GET token APIs, production Next server, Chromium, exclusive disposable PostgreSQL, and test-only network interception. The observer can see browser state, HTTP results and database rows; the adversary may hold or drop request/response delivery and order real transactions. Resource: timer delay in milliseconds, browser requests and logical CPU count; no claim of CPU or performance superiority. For each tested mint attempt with unchanged requested scopes, if the browser's event loop runs and fetch honors AbortSignal, a POST still pending when its 12,000 ms timer fires must leave the synchronous lock via the existing failed-mint recovery, warn that creation may have occurred, refresh the list subject to its separate 8,000 ms timeout, and never invent or overwrite a secret. A received successful secret remains locked until dismissed. Old completion must not overwrite a newer displayed secret in the tested delayed-response schedule. Timer values are scheduling requests, not wall-clock deadlines under suspension, throttling, CPU starvation or a noncompliant transport. Success is bounded to these conditions; failure includes a falsely assured rollback, silent duplicate retry or fabricated secret.

H+: bounded client waiting and explicit uncertainty are experimentally attainable with native abort. H−: a timeout alone cannot distinguish a POST that committed from one that did not, so exactly-once or safe blind retry cannot follow from it. H∂: actual liveness depends on event-loop execution, fetch abort behavior and GET recovery; concurrent tabs and server-side processing are separate boundaries. Explicit threshold before commit: genuine prepatch hung POST counterexample, production build, postpatch browser attacks for committed and not-yet-delivered requests, adjacent token regressions, and report gate status. Adjacent problems not substituted: cancellation of server transaction, exactly-once minting, durable retry keys, secret recovery, lost-response reconciliation, cross-tab arbitration, physical device verification, all-app Class A, or test speed optimization.

## External frontier
MDN documents that AbortController cancels fetch and may also cause body reads to reject after headers (https://developer.mozilla.org/en-US/docs/Web/API/Fetch_API/Using_Fetch); it does not promise rollback of server effects. Stripe documents a *different service's* idempotency contract, where same-key same-parameter retries within its retention period can avoid repeated side effects, while a new key or expired retention can create another operation (https://docs.stripe.com/error-low-level); those hypotheses and guarantees are not provided by OST. Reviewed the MIT-licensed https://github.com/milonpatowary/express-idempotency documentation as one candidate architecture; no package or code was copied, and its stated behavior was not independently verified here. Persisting/replaying a one-time secret has additional confidentiality implications absent from generic response caching. The open interface is safe reconciliation or deduplication of the mint itself without storing recoverable bearer secrets, including concurrent requests and delayed commits.

## Independent mechanisms and attackers
1. **Wait forever**: old POST flow, executable counterexample: real server committed a token but the browser response was held; the UI remained locked without uncertainty warning beyond 18 seconds. Local liveness gap.
2. **Abort a pending POST after 12 seconds**: implemented; timer cleared as soon as POST settles, followed by existing GET recovery and explicit ambiguous-outcome warning. Real committed/drop and pre-delivery blocked tests passed. Adversary: original request commits after timeout or event loop suspends. Local liveness improvement, not original exactly-once problem.
3. **Auto-retry POST**: rejected causal model: the committed-but-lost test demonstrates that sending another POST is a distinct operation and can mint a second credential. Cheap falsification: count rows and requests after response loss. Original cross-transaction deduplication gap.
4. **Durable idempotency key**: unimplemented design: unique key and payload fingerprint in same DB transaction as token/audit; matching concurrent retries return a previously recorded outcome. Attack key reuse with changed payload, crash, expiration, authorization scope and response loss. Returning the original secret conflicts with hash-only storage; cross-API/security gap.
5. **Deterministic credential derived from request key**: unimplemented causal design: retry can reproduce a secret without storing it directly, but key compromise, entropy, derivation keys, rotation and authentication require security design. Attack predictable keys and stolen operation key. Cross-protocol security gap.
6. **Abort plus block all retry forever**: unimplemented policy stops same-panel duplication but a real user cannot recover from an uncommitted request and another tab still can mint. Attack permanently lost response. Local availability and global coordination gaps.
7. **List-and-confirm reconciliation**: existing explicit list and warning, tested by observing actual committed ID after a lost response. A GET snapshot cannot exclude an original POST that commits later; names may collide. Attack delayed commit following list. Cross-request ordering gap.

## Negative space
A client abort is not server rollback; a timeout is not an absolute deadline; a missing response is not a missing transaction; a list refresh is not a transaction barrier; one token name is not a unique intent; one tab lock is not cross-tab locking; disabled is not inaccessible; retry is not idempotence; a successful GET is not a future guarantee; a secret hash cannot be reversed for replay; a shown secret is not evidence of no other token; a 201 whose body is lost is not a failed creation; an HTTP error is not proof of no side effect; a simulated drop is not a physical outage; two observed schedules are not all schedules; a passing production build is not an accessibility review; a passing targeted test is not a full gate; one screenshot is not an all-app survey; a runner that adds coverage is not automatically faster; stored register labels are not independent Class-A proofs. The modal shortcut—wait indefinitely for POST—was falsified by a real commit plus withheld response; the repair was retested with two adversarial schedules and a late old response after a second secret appears.
