# TT190 — uncertainty across Routines windows in one document

## Runtime and model
One coding agent used Bash, Git/gh, web research, the Next/TypeScript production compiler, ESLint, real Chromium 143 through Playwright, and a disposable PostgreSQL database. No independent agent, theorem prover, simulator, expert review, or real assistive technology was used. The storage exceptions and delayed list delivery are explicit test fault injection; DELETE, locking, token creation and bearer authorization execute against the real server/database. The workspace has two CPUs. The shared-database browser suites run sequentially. The patch is independently written and adds no package or external service.

Admissible objects: existing eight-character automation token IDs, list snapshots, same-document Routines panels, DELETEs, per-tab session storage and immutable in-memory snapshots. The client has no access to an in-flight server transaction's eventual outcome; the attacker can lock a row, delay a real list response, deny storage, trigger revocation from a panel, and release the lock. Resources: one ID per distinct attempted token in each document's monotone in-memory snapshot and (when available) tab storage; listener notifications per mounted panel and linear array/set work per marker insertion; no quantitative resource-performance bound is established. Timeouts are 12 seconds for DELETE and 8 seconds for list, subject to event-loop scheduling. Distinct browser tabs, server operation journaling, globally synchronized authorization, page suspension, actual screen-reader announcements, and a full modern OS are different problems and must not be substituted.

Candidate success predicate with explicit quantifiers: for all IDs and any two mounted panels in the same JavaScript document, after one panel starts revoke and the other renders a last-seen-live row for the ID, it should show uncertain even if sessionStorage access throws, including a list response captured before the revoke but delivered after it; unrelated IDs remain unaffected. This predicate assumes the running document and a shared module instance, ordinary React subscription/update behavior and no arbitrary same-origin script modification. One observed revoked row is still only an observation. Failure is an unqualified live badge for that ID in the exercised ordering, a falsely marked unrelated ID, or broken revocation/authorization. Real tests establish selected finite cases rather than the universal proposition. H+: the property is achievable within the same document using a shared monotone store. H−: with no common memory/communication/durable record, one tab cannot infer another tab's delayed mutation from an earlier live list. H∂: reliability depends on tab boundaries, storage and process lifetime, server ordering, and other clients. Evidence threshold for the narrow patch: baseline real-DB counterexample, production build, multi-panel plus denied-storage attack, late captured-list attack targeted at the repair, affected regression suites and honest gate report. It does not certify ten Class-A features or the complete task.

## Frontier and six independent constructions
[React's useSyncExternalStore reference](https://react.dev/reference/react/useSyncExternalStore) requires stable unchanged immutable snapshots, listener registration/cleanup, and matching server/hydration snapshots; notification causes React to re-read, not proof of our distributed protocol. [MDN storage event](https://developer.mozilla.org/en-US/docs/Web/API/Window/storage_event) says a storage mutation does not notify the document that performed it; sessionStorage notification is scoped to other same-origin contexts within the same top-level context. [PostgreSQL READ COMMITTED](https://www.postgresql.org/docs/current/transaction-iso.html) gives ordinary SELECT a statement-start snapshot; it cannot predict later transaction commits. These results apply only with those hypotheses. The open interface is sharing uncertain intent inside a document without mistaking it for confirmed server state, and beyond that document recovering the intent and outcome durably.

1. **Shared monotone external store (implemented):** module-held cached readonly snapshot, stable subscribe/unsubscribe, empty SSR snapshot; per-ID storage retained for same-tab reload. Real tests lock DB row and test two panels, denial and an old captured response. Attacker destroys storage or uses another tab, or races a separate module instance. Gap local to cross-context communication, but server outcome is still the original distributed ambiguity.
2. **Independent React state per panel (baseline):** real two-panel tests fail 0/2: second panel remains live with storage available and denied. Attacker starts DELETE from the first panel. Gap local: state sharing, not the entire OS.
3. **Native sessionStorage event alone:** same-document writer gets no storage event under MDN's stated rules; two components are not two documents. Causal counterexample, not implemented. Cheapest attack is two panels in one document, already exercised. Gap local.
4. **Custom document event plus per-panel state:** event can notify currently subscribed components but an unmounted/late subscriber needs replay; event is lost if fired before subscription. Causal trace: revoke, subscribe, render old list. Cheapest attack is late-mounted panel with storage denied. Gap local; not implemented.
5. **BroadcastChannel:** async cross-context messaging needs eligible same-partition recipients and has no guaranteed replay for late joiners. Causal counterexample: message sent before other tab opens. Cheapest test open tab after send while original transaction remains pending. Gap local communication plus durable replay; not implemented.
6. **Shared parent React context:** lift state to common owner and pass via provider; state loss on parent unmount or new tab still possible, scope depends on placement. Causal trace parent teardown then early live read. Cheapest test unmount/remount provider with denied storage. Gap local; not implemented.
7. **Durable server operation status:** record authenticated operation identity and lifecycle with idempotency/retention and define pending/delivery semantics. Attack original request delayed past status lookup, retry or record expiry. Design only; gap is a new distributed protocol, not proof of OS completeness.

## Negative space and adversary
A timeout is not failure; timeout is not success; client abort is not server cancellation; a live list is not future liveness; a warning dismissal is not confirmation; a revoked observation does not prove future state; a shared document store is not cross-tab; a storage event is not same-document notification; sessionStorage is not durable operation state; a marker is not bearer authorization; token ID is not a secret but is still metadata; a disabled button is not a server lock; browser fault injection is not a real network outage; a single database execution is not all transaction schedules; Chromium alone is not cross-browser verification; build success is not behavior proof; UI role is not screen-reader evidence; one screenshot is not all-app visual review; more tests are not a speed improvement; historical ledger labels are not Class-A certification. Modal shortcut: treating the second panel's earlier live snapshot as a present and future authorization fact. The two-panel row-lock test checks that panel while the actual DELETE waits, then releases the lock and checks real bearer 401. The new late-list test attacks a repair that could overwrite or miss the shared marker when storage is unavailable.
