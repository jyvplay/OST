# TT191 — advisory cross-tab revocation uncertainty

## Model, runtime, and threshold
One coding agent used repository inspection, Git/gh, web search and primary documentation, Node 22, the Next/TypeScript production compiler, ESLint, real Chromium 143 through Playwright, and disposable PostgreSQL. Two CPUs were available; shared-database browser suites were sequential. No independent agents, theorem provers, simulators, expert review, or assistive technology were used. The denied channel in one test is targeted fault injection, not an actual browser-policy survey; token creation, database row locks, DELETE and bearer authorization use the real server. The implementation is independently written and adds no package.

Admissible objects: token IDs (eight lowercase alphanumerics), last-seen token lists, DELETEs, Routines panels in same-origin same-partition tabs, per-tab sessionStorage and same-name BroadcastChannel messages. Tabs observe messages while a panel is mounted but cannot directly observe another tab's future server transaction. The attacker may order tab opening, DELETE, database lock, message delivery, list refresh and channel availability; same-origin scripts may send messages. Resources: one channel per mounted panel, IDs held for the document/tab lifetime, payloads of at most 100 IDs per message; handshake can emit ceil(n/100) messages per receiving panel, with n accumulated IDs, and all receivers may write synchronous session storage. No performance bound or Pareto improvement is established. Units: existing client deadlines are 12 s DELETE and 8 s list, subject to event-loop scheduling; test polling deadlines are 8 s with Playwright's normal assertion timeout. These are not hard real-time guarantees.

Scoped success, with quantifiers: for each of the tested ID/orderings, if same-partition channels are active and deliver either the original marker or a late-join request and response from a peer that already knows the marker, the receiver must qualify a last-seen-live row as uncertain, not change an unrelated token, and never treat a marker as actual authorization; local revocation must remain usable if this channel cannot be created. Failure is an unqualified badge under the exercised delivered-message schedule, an unrelated change, inability to revoke locally in the injected failure, or treating a marker as proof of revocation. Tests demonstrate finite cases only, not this universal claim. Different tabs when no knowledgeable peer is listening, late subscription while a peer has yet to rehydrate its own markers, a missed or delayed message, browser shutdown, partition changes, hostile same-origin scripts, other devices/clients, server completion, and a complete OS are adjacent problems, not substitutes.

H+: advisory notification of existing peers and handshake with a still-listening knowledgeable peer is possible under successful delivery. H−: with no communication or shared durable operation record, a receiver cannot distinguish a request that will later commit from one never delivered using the same early live snapshot. H∂: delivery, partition, peer lifetime, storage and scheduling change what can be known. Evidence threshold: prepatch two-tab real-DB counterexample, production build, already-open and late-join attacks, malformed and channel-failure attacks directed at the patch, related suites and honestly reported full gate. None establishes ten Class-A features.

## Frontier and portfolio
[MDN BroadcastChannel](https://developer.mozilla.org/en-US/docs/Web/API/Broadcast_Channel_API) limits communication to appropriate origin/storage partitions and describes named channels and explicit close; [its interface](https://developer.mozilla.org/en-US/docs/Web/API/BroadcastChannel) excludes the sending channel object from receiving its own message. It provides message transport, not a durable replay/transaction protocol. [MDN sessionStorage](https://developer.mozilla.org/en-US/docs/Web/API/Window/sessionStorage) describes per-tab lifetime, opener copying and policy exceptions. [PostgreSQL READ COMMITTED](https://www.postgresql.org/docs/current/transaction-iso.html) states ordinary SELECT sees a statement-start snapshot, not later commits. These sources require their stated hypotheses; none proves application-wide completeness or message delivery in every lifecycle.

1. **Broadcast advisory + request/response (implemented):** marker before DELETE, same-document monotone store, listening peers replay known IDs in bounded messages, receiving tabs save IDs to their own session when possible. Concrete two-tab locked-row tests and message validation tests; attacker closes or freezes peers, delays handshake until before their rehydration, disables transport or sends spoofed messages. Gap local cross-tab delivery and original distributed operation ambiguity; cheapest next attack is delay peer's list/rehydration while another tab requests replay.
2. **TT190 same-document state only:** real two-tab tests failed 0/2 on unqualified live badges. Attacker opens independent tab; gap local cross-document notification.
3. **Broadcast without handshake:** a late listener misses an earlier notification; causal trace send, open tab, early live list, delayed commit. Gap local replay; cheapest attack is late-joining test.
4. **Origin-wide localStorage markers and events:** provides a readable shared record where permitted but extends retention of token-ID metadata beyond tab closure; writes can fail, events aren't transactions and same-origin scripts can modify it. Attack quota/policy denial and new tab after clear. Gap local privacy/lifetime tradeoff plus server ambiguity; not implemented.
5. **Polling server list:** repeated reads may all precede late commit and cannot identify pending intent; row-lock counterexample from TT188 is executable. Gap equivalent to client-only outcome identification under unbounded delay; not implemented as a guarantee.
6. **SharedWorker coordinator:** allows a shared live owner but late joins after termination miss volatile history; worker support, lifetime and fallback matter. Attack worker termination during pending DELETE. Causal model only; gap local lifecycle and replay.
7. **Authenticated durable server operation journal:** stable operation identity, authorization, retained status and clear pending/cancellation semantics could cover restarts but needs a new protocol. Attack late request after a status query or retention expiry. Gap local to that protocol, not proof of the whole OS.

## Negative space and modal shortcut
Client abort is not rollback; timeout is not failure; timeout is not success; an earlier list is not future state; a message is not server confirmation; a marker is not authorization; a same-origin sender is not a trusted server; a token ID is metadata even if not bearer secret; a late subscriber is not guaranteed replay; a handshake is not durable storage; a channel is not cross-device; same origin alone is not enough across storage partitions; a failed constructor is not proof all browsers block it; fault injection is not a production outage; a lock test is not every schedule; one Chromium is not browser coverage; a build is not functionality; a screenshot is not all-app visual review; an ARIA attribute is not assistive-technology testing; extra tests are not demonstrated faster; ledger labels do not certify Class A. Modal shortcut: treating a different tab's last live list as evidence of current or future authorization. The real blocked-DELETE attack tests this shortcut and verifies eventual bearer 401; a valid marker injected without DELETE still yields bearer 200, proving the marker is not authorization.

## Verification and gaps
Prepatch two-tab attack failed 0/2 on missing uncertainty. The production build passed. Final TT191 passed 4/4: already-open and late-joining tabs, oversized-message rejection plus actual bearer 200, and channel-constructor failure with local revoke and actual bearer 401. Test lint and whitespace checks passed. The channel-failure test blocks only the Routines channel: indiscriminately replacing BroadcastChannel also broke unrelated shell startup and was not accepted as a Routines-specific result. Complete gate `.cache/gate/20261119T071935Z/run-197717-maLRw7` failed TT124 Routines 350/300, TT125 Files 375/260 and TT123 Files 375/320; TT191 passed 4/4, TT190 3/3, TT189 4/4, TT188 1/1, TT187 3/3, TT168 4/4, TT163 1/1 and e2e-a11y 9/9. These density counts are data-dependent and can include clipped rows, but that does not establish cap compliance. Routines retains its pre-existing hook-effect lint error. A post-gate TT188 screenshot run passed 1/1 and the desktop Routines panel was inspected; it is not a review of all apps, viewports or assistive technology. No message guarantee, durable server operation status, all-app visual review, new graphics, ten Class-A promotions or measured speedup is claimed. Other tabs may be out of date; the UI says so. Next high-information attack: sender rehydrates session markers after a late receiver's handshake, with the original DB transaction still blocked; design a replay mechanism with explicit lifetime, failure and privacy boundaries if stronger guarantees are required.
