# TT209 — backup save availability after inventory stalls

## Contract and available verification
Admissible systems are the Backup UI, its real `/api/fs` conditional-create endpoint and an exclusive disposable PostgreSQL-backed application, exercised in Chromium. A save is pending until the folder and conditional-create requests settle; inventory refresh is an independent list operation. For every tested settled create, a later list that never settles must not indefinitely hold the save lock. For every save still pending, duplicate activation must not issue another create. Existing no-overwrite, uncertain-outcome reporting, inventory epoch and guarded prune semantics remain unchanged. The test holds a real browser route open and observes the production app and database; this deliberately injected network failure is not a claim that the server itself hung. Two-second button readiness is a test bound, not a universal latency guarantee. Not equivalent: successful backup restoration, guaranteed network termination, unique same-minute backup names, avoiding duplicates after an unknown acknowledgment, all-browser accessibility, or an A-grade backup product.

Actual tools: git, gh, web search, Node 22, TypeScript/Next production compiler, ESLint, Playwright Chromium 143, PostgreSQL, Linux process tools, shell; no independent agent, theorem prover, independent expert or simulator. H+: release the save lock once create settles and start the list separately. H−: if the create response never settles, releasing safely without an idempotency protocol can allow a duplicate or misrepresent an unknown outcome. H∂: behavior depends on request settlement, browser lifecycle, server state, and time; a stalled inventory can still keep its own loading indicator and pending request. Threshold for the bounded change: actual baseline counterexample, patched browser test plus existing concurrency, uncertain-response and inventory/prune regressions, build and lint reporting. This does not establish global correctness.

## Frontier and portfolio
The Fetch API resolves/rejects asynchronously; aborting a request is not proof the server rolled back ([MDN](https://developer.mozilla.org/en-US/docs/Web/API/Fetch_API/Using_Fetch)). A request racing a timeout may therefore have committed. The existing conditional-write implementation and TT176 tests, not this citation, establish the tested no-overwrite behavior. Open interface: reconciling unknown outcomes and arbitrary delays with exactly-once semantics requires a server-supported operation identity and reconciliation contract.

1. **Await inventory before unlock**: baseline artifact TT176 new case 6/7. Attack: hold list indefinitely; fails availability. Local gap.
2. **Unlock before create settles**: causal counterexample is two activations during a pending create, already exercised by TT176 duplicate-activation test. May duplicate or obscure a committed operation. Local safety gap.
3. **Unlock after create settles, launch inventory independently**: implemented. Baseline 6/7, patched 7/7, including an attacker holding the list and issuing another save. Existing epoch prevents older inventory completion overwriting newer results in the separately tested late-failure case. Remaining hung-list resource use and create uncertainty are not solved; local gap.
4. **List timeout plus unlock**: a timeout can bound UI waiting, but abort is not a guarantee of server rollback; malformed/late response and retry ordering need tests. Not implemented; local gap.
5. **Server idempotency key and status reconciliation**: a durable key linked to result could make retries attributable if integrated transactionally and retained across client interruption. Counterexample: response lost after commit, retry with a different key. No implementation or proof; broader cross-layer gap.
6. **Unique filenames and retry on collision**: strict parser, inventory and prune order all require changes; 409 also covers an unavailable folder. Blind retry can disguise failure. Counterexample: parent disappears between mkdir and create. Not implemented; cross-layer gap.
7. **Offline queued save**: requires durable queue, identity and trustworthy recovery; attacker closes browser after server commit before acknowledgment. Not implemented; broader gap.

Misleading result shapes rejected: list returns quickly only; button enabled while create pending; fake server success; no database check; one tab only; overwrite of previous copy; duplicate activation; hidden loading state; lost response called failure with no uncertainty; retry on every 409; stale inventory re-enables prune; malformed list accepted; late older list overwrites newer list; unbounded request described as completed; cancellation claimed as rollback; same-minute names called unique; one browser called cross-browser coverage; build called functional verification; local fix called Class A; fabricated speedup.

## Execution and unresolved risk
The prepatch production build yielded TT176 6/7, failing the held-inventory test on button readiness. Rebuilt with DATABASE_URL set and reran on a real Chromium/PostgreSQL app: TT176 7/7; TT172 inventory 4/4; TT173 prune 4/4; TT174 prune conflict 2/2; TT175 browser dates 2/2. The test checks that the retry cannot overwrite the existing version. The initial build without DATABASE_URL failed at page-data collection; the configured build passed. ESLint passed for the test file; linting Backup.tsx reports two pre-existing errors (set-state-in-effect at line 123 and unescaped apostrophe at line 481) and a ref cleanup warning. The first-install TT178 script refused execution because the existing disposable database was not newly initialized; its requirement was not bypassed. The full gate was not rerun for this change. No script speed improvement, ten Class-A promotions, complete all-app visual review or graphic work is claimed.

The separate PR runner repair remains blocked: numerical process-group IDs can be reused after the leader is reaped. `kill -0` or `ps` is not an atomic identity proof. Linux `waitid(..., WNOWAIT)` leaves a child waitable ([manual](https://man7.org/linux/man-pages/man2/waitpid.2.html)), suggesting a supervisor that signals before reaping; an implementation still needs careful signal/timeout semantics, leader identity, cleanup and compatibility tests. A claimed `kill -0` check before a later signal is insufficient because the last original group member can exit between the check and signal. No dangerous PID-reuse experiment was run on this shared host. Highest-information next test: implement an isolated supervisor in a separate PID namespace where available, verify that every group signal precedes leader reap and exercise timeout/cancellation/leader exit and escaping descendants. Until then do not merge the runner repair.
