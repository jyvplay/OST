# TT167 — token lifecycle and audit atomicity

## Declared threshold and admissible model
Scope: PostgreSQL-backed `/api/automation/tokens` POST and DELETE, and corresponding audit inserts, on an exclusive disposable DB and production server. Count committed rows and HTTP outcomes; the desired bounded invariant is that a creation or first revocation and its audit row commit together, and competing revocations record no more than one first-revocation event. For each tested input and induced failure/interleaving, the HTTP and database assertions must hold. This is not exactly-once delivery, external authorization, proof of general DB durability, or recovery of a secret after a lost successful response. Commit threshold: pre-patch real DB counterexample, production build, affected regressions plus a new fault-injection and race attack; merge threshold: clean full gate and main review. H+: transactional writes can meet this bounded invariant. H−: a complete perfect OS under all requested constraints might be impossible, but that is not proven. H∂: failures before commit differ from lost responses after commit, and isolation, transaction participation and DB availability matter.

Actual tools: git/gh, shell, web search, TypeScript/Next build, Node HTTP, PostgreSQL, and Chromium/Playwright when run. No independent agents, theorem prover, simulator, or expert review. Fault-injection triggers and row locks use real PostgreSQL; they require an exclusive disposable DB and are removed in finally. PostgreSQL documents atomic all-or-nothing multi-statement transaction blocks and visibility on commit (https://www.postgresql.org/docs/current/tutorial-transactions.html); those properties require the relevant statements to participate in the same transaction, and do not guarantee delivery of the HTTP response or coordination with nonparticipating writers. There is no established global best-known solution or impossibility theorem for the requested entire OS here.

## Concrete counterexamples and repair
The old production build failed 0/3 real PostgreSQL/HTTP attacks: an audit-trigger exception left one created token without its creation audit; a revocation audit exception left the token revoked and its hash erased; two revocations waiting on a held row lock both returned first-revocation responses instead of exactly one `alreadyRevoked`. Temporary trigger functions and rows were removed in `finally`. The old failure output included a test fixture hash (not a bearer secret); the passing receipt replaces that failure receipt.

The patch performs token creation and audit insert in the same DB transaction. For revocation it takes `SELECT ... FOR UPDATE`, checks the locked row, and performs the status/hash update and audit insert in the same transaction. Concurrent DELETEs on the same row are serialized; the second sees the revoked state and returns unchanged. With the same server and actual DB, production build passed and TT167 passed 4/4, including an additional successful create/revoke/repeat attack that checks the issued bearer works before and is refused after revocation, the timestamp remains unchanged, and the two audit entries do not contain the bearer. TT160 admission 3/3 (including its revocation race), TT159 settlement 2/2, TT146 HTTP 4/4, TT166/165/164 browser 4/4 each, TT163 1/1, and TT146 browser 5/5 passed. These are finite observed executions, not a proof against every writer or failure. The actual credential is never intentionally printed or stored in test receipts.

## Six distinct mechanisms, artifacts and attacks
1. **Transaction grouping:** create/update and audit in a single DB transaction; executable artifact is the patched route and injected audit exceptions. Both tested operations roll back, not proof of every failure. Attack: audit trigger throws after token write (performed). Local DB atomicity gap remains for nonparticipating writers.
2. **Row-lock serialization:** `FOR UPDATE` before checking revocation; artifact is a held-lock two-HTTP-request race. Exactly one event and unchanged response observed. Attack: two blocked clients released together (performed); arbitrary external DB writes remain a local coordination gap.
3. **Conditional mutation (alternative):** update only rows with null revoked timestamp and use RETURNING to select the winner; artifact is the equivalent single-row winner contract. Attack: a concurrent delete or audit rollback; not implemented here. Its local gap is proving error/404 semantics and audit atomicity.
4. **Transactional outbox (alternative):** write a durable token event in the same transaction and asynchronously publish it. Artifact is event/row atomicity design, not implementation. Attack consumer crash, duplicates and ordering; local downstream delivery remains unresolved, not equivalent to the whole OS.
5. **Idempotency key (alternative):** map retried mint requests to one logical operation. Artifact is a uniqueness/response-replay contract; attack crash after commit before response and secret confidentiality. Not implemented; durable secret recovery versus privacy remains unresolved.
6. **Serializable transactions (alternative):** retry aborted transactions when conflicting predicates span multiple rows. Artifact is a proposed retry protocol, not implemented. Attack serialization failure and duplicate external effects during retries; local multi-row integration gap, not a proof of whole-app correctness.

Misleading result shapes: 500 means no commit; a token row implies its audit committed; an audit row implies HTTP response arrived; row lock by one path governs unrelated writers; two 200s imply two changes; repeated DELETE success means timestamp unchanged; hash erasure proves all existing copies invalidated; response lost means no token created; a retry is idempotent; audit insert is durable after a later rollback; trigger simulation substitutes for a real DB (the test uses actual PG); isolated success equals full gate; no bearer in audit proves no secret leak anywhere; a browser-only test proves transaction semantics; a transaction solves exactly-once execution; status built proves Class A; old code failure proves universal impossibility; parallel workers imply speedup. The real audit-failure trigger detects the modal multi-autocommit shortcut.

Remaining boundaries: after transaction commit the response can still be lost; no plaintext recovery or server idempotency is implemented. The shell settlement path remains unauthenticated and multiple shells can execute a queued action. Row locks do not protect direct writes that ignore this protocol. The most useful next test is a forced connection loss just after DB commit but before client receipt, followed by a retry and explicit check for orphaned/multiple tokens without exposing secrets.
