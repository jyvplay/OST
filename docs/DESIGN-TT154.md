# TT154 — recovery-layout and regression review

## Model and threshold

The object under test is this PWA, its real HTTP server and an explicitly disposable PostgreSQL desktop. Browser tests use Chromium 143 with real DOM input; network routing is used only to hold one real request in the adversarial test. No independent agent or theorem prover was used. Node/TypeScript, Playwright, PostgreSQL, external Python document decoders and zxing-cpp were available. A finite browser run cannot establish universal correctness or an A grade.

For the targeted drag, success for each exercised desktop and saved-draft state means: after the asynchronous recovery lookup has settled and rendered its result, a native 60 CSS-pixel drag of the actual header handle changes the cell width by 60 ± 2 CSS pixels; the lookup must not delete a draft. A recovery-ready signal cannot assert completion while its lookup remains blocked. Stale lookups must not publish offers for a different document. The tests cover selected states and timings, not all interleavings, browsers or failures. Separately, a stale alarm edit must preserve the newer state and retain the unsaved form, with an explicit warning. A successful gate requires all its suites to finish with zero failures, not merely a selected test passing.

H+: these bounded failures are repairable without dropping recovery, encryption or responsive controls. H−: complete native-OS equivalence is not demonstrated by a browser PWA and cannot be inferred from these tests. H∂: behavior depends on draft state, asynchronous arrival, viewport and browser; broader coverage requires more conditions and evidence. Threshold for these local changes: reproduced failing real-browser case, deterministic adversarial delay and mutation, TypeScript/build, affected real lifecycle and layout suites, and honest retained failures. This is not a threshold for merging the whole PR.

## Observations and mechanism

A capture-phase event trace on the production build showed `mousedown` landing on “Unsaved changes found” rather than the header handle: the recovery banner arrived between the test's hit-target check and mouse input. This explains the reproduced 138 → 138 resize result in that run, not necessarily every failure with that shape. The old test checked hit target before mouse movement, which cannot prove that a later event still hits it. The new regression holds the actual recovery listing request, asserts readiness remains false and no banner is shown, releases it, verifies that the signal and real banner appear together, and verifies the draft's contents remain unchanged. Changing the signal to `ready` alone made this test fail (`true !== false`); restoring the repair passes. The signal means the lookup attempt completed, not that storage errors can never occur. Existing storage error handling is unchanged.

The recovery result is keyed by document kind/path and published atomically with its completion state; an effect cleanup ignores a late response. The spreadsheet exposes that state to tests. Office and accessibility drag tests wait for it rather than discarding drafts, force-clicking or changing resize tolerances. Editor and Writer keep their recovery behavior. The clock implementation already reported “Changed elsewhere — reopen the editor.”; the old test waited for different wording. The test now checks the actual explicit warning, the retained unsaved edit and the newer persisted alarm.

The older recovery suites also had stale dialog wording and assumed hidden responsive toolbar buttons had visible inner text. They now assert the current warning and use the real More menu when necessary; file bytes, encrypted drafts, cancellation and restore checks remain in place. No production save or recovery feature was removed.

## Portfolio and counterexamples

Six distinct candidate mechanisms considered, with the cheapest distinguishing test and unresolved interface:

1. **Pointer capture**: ensures subsequent pointer events target the captor after a successful down; MDN documents this at https://developer.mozilla.org/en-US/docs/Web/API/Element/setPointerCapture. Artifact: event trace proves the down landed on the banner, so capture cannot solve this initial hit. Attack: delay the banner until before down. Gap: separately evaluate touch/cancel handling.
2. **Stable test coordinates**: wait for completed lookup and then measure the actual handle. Artifact: readiness attribute plus delayed-response test. Attack: make readiness true early (mutation failed). Gap: later unrelated layout shifts remain possible.
3. **Delete all drafts in setup**: could remove the shift but destroys evidence and is unsafe for real data. Counterexample: the delayed test asserts draft bytes survive. Rejected.
4. **Force click or enlarge tolerance**: can report success without a genuine interaction. Counterexample: trace shows the hit went to the banner; original ±2 px drag assertion is retained. Rejected.
5. **Freeze desktop overflow or stack shelf behind windows**: could hide interception but conflicts with the shell's title-bar and shelf behavior. MDN notes `overflow: clip` does not support programmatic scrolling: https://developer.mozilla.org/en-US/docs/Web/CSS/overflow. Gap: reconcile off-screen window recovery, resizing and responsive layouts with real-browser tests; not implemented.
6. **Fit saved windows to available desk**: could make controls reachable, but indiscriminate clamping changes deliberate partial-offscreen window behavior and restore geometry. Artifact: current reducer enforces reachable title bars, not whole-window containment. Attack: small viewport, text scaling, deliberate drag, maximize/restore and viewport growth. Gap is global geometry compatibility; not implemented.

Fifteen misleading result shapes, none sufficient for the full contract: a compiled build; a single passing case; a passing mutation-free test; a stubbed network; a synthetic DOM click; an initial hit-test alone; an increased timeout; a larger numeric tolerance; a discarded recovery draft; a relaxed density ceiling; a hidden control clicked by script; a mock scheduler presented as native; an aggregate ledger count; a prior build's test result; and a gate stopped before completion. The modal shortcut here is the initial hit-test: it passed, then asynchronous layout change moved the target. The held-listing test detects premature readiness, and the full office test still uses native input and measures displacement.

## Verification and remaining gap

The rebuilt production server passed delayed recovery 1/1, office 11/11, spreadsheet layout 7/7, Clock 13/13, lifecycle 6/6, sealed recovery 2/2, and TT151 2/2; targeted accessibility resize passed 1/1. Python document decoders independently checked saved and sealed document bytes. The full accessibility suite and full production gate were not rerun to completion. Gate now includes TT151 QR/time, TT151 UI, the new recovery attack, and the two recovery suites; these make it more powerful but are not a measured wall-time speedup. The QR and time pure suites passed 6/6 and 11/11 in two parallel workers. A TT69 server/database suite was accidentally run alongside early production checks; the later focused office and Clock reruns were exclusive. Earlier density and shelf failures remain open; no limits were raised. A previous run also recorded two unrelated accessibility timeouts; a targeted drag pass does not establish they are resolved.

The screenshot `docs/screens/tt69-close-confirm-dark.png` was inspected: the Spreadsheet and recovery confirmation are legible at that tested desktop size. This is not a visual review of every app, viewport, theme or interaction. No new Class-A promotions are claimed. The next high-information test is a dedicated real-browser window geometry matrix that reproduces shelf interception under resize, restored oversize geometry, maximize/restore and keyboard focus, before changing window invariants.
