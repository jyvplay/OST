# TT175 — invalid backup dates and retention safety

## Model, scope and threshold
Admissible objects: filenames listed as files under `/Backups`, the existing local-time parser/inventory/prune plan, the Backup panel and VFS API. Inputs include four-digit years 0000–9999, numeric month/day/hour/minute and arbitrary nonmatching filenames. A matching filename is accepted only if its local calendar fields round-trip without normalization; a locally nonexistent time is unknown. Quantifiers: for every input in the tested finite set, invalid calendar fields must return null and not be selected by the existing plan; for each explicitly exercised browser schedule, a real invalid dated-looking file remains live, an eligible old valid file moves to Trash, and stale cross-tab requests do not move other targets. No proof for every timezone/date/browser, complete OS, permanent erasure, all batch schedules, or Class-A readiness. Units: filenames, calendar fields, DB node identity/trash flag, HTTP statuses, browser-visible state; no latency goal. Evidence threshold for this bounded patch: actual pre-patch browser/HTTP/DB counterexample; final build; independent arithmetic boundary checks; post-patch real browser/DB verification and affected backup regressions. Full gate and its prerequisites must be reported separately.

H+: strict local field round-trip can prevent this normalization failure. H−: the old implementation violates the contract on February 30 (observed), not a general impossibility theorem. H∂: DST gaps, ambiguous fall-back times, timezone changes, clock drift, timestamp precision, shared filenames, concurrent inserts and client/server visibility limit date ordering and safety. This parser interprets the user's current local timezone, not the timezone in which an imported file was originally named; overlap times remain ambiguous. Pruning is per-file and sequential, not an atomic newest-two snapshot.

Actual resources used: git/gh, shell, Node 22/TypeScript/Next build, real headless Chromium 143 via Playwright, HTTP, disposable PostgreSQL 18, and web search. npm dependencies and test-only browser/PostgreSQL were installed from npm. Two independent one-shot tasks (build and npm audit) were run concurrently; browser DB suites ran sequentially. No independent agents, simulator, theorem prover, assistive-technology tester, external human expert, or full app visual survey. `npm audit --omit=dev` reported zero production vulnerabilities at this run; `npm ci` reported 12 moderate including development dependencies, which were not investigated or fixed here.

## Frontier and imported facts
MDN documents that the multi-argument Date constructor uses local time, normalizes overflows/underflows, and maps years 0–99 to 1900–1999 (https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Date/Date). The experiment shows overflow is consequential here, not that all parse failures follow from that documentation. PostgreSQL documents that a `FOR UPDATE` row lock blocks conflicting writes/locks of that row and that advisory locks are cooperative (https://www.postgresql.org/docs/current/explicit-locking.html); neither guarantees a folder-wide stable set or response delivery. No global optimality or impossibility result has been established for the entire OS. Exact open interface: safe snapshot retention across concurrent membership changes and durable, recoverable acknowledgment of partial/lost responses; date names alone cannot resolve timezone ambiguity.

## Mechanisms, artifacts, adversaries and gaps
These are independent candidates, not six implemented or proven solutions. Except where noted, gaps are local to backup retention.
1. **Regex + Date constructor**: existing parser is the artifact; attacker uses `20230230` with three valid dates. Actual old UI/DB test moves the invalid target. Invalid dates normalize; candidate fails.
2. **Calendar arithmetic validation**: executable independent Gregorian oracle in `tt175-backup-dates.mts` checks leap/century/month boundaries. Attacker uses local DST gaps and ancient zone rules; arithmetic alone cannot establish existence in a local zone. Gap: timezone interface.
3. **Local field round-trip**: implemented parser checks all five fields after construction. Artifact: code and new tests; attacker supplies overflow, 0–99 year, February 29, DST gap, malformed suffix. Passing tests are bounded, not proof of all timezone transitions. Gap: ambiguous overlap, locale changes and midnight transition edge cases.
4. **UTC-only interpretation**: design artifact is an alternative contract requiring UTC dates. Attacker saves local-time filenames and changes timezone; behavior contradicts established local naming. Cheapest test: same local filename across a UTC boundary. Not implemented; compatibility gap.
5. **Explicit timestamp metadata**: design stores timestamp and zone/offset alongside bundle with identity guard; attacker edits name or metadata, legacy file lacks it, or two writers race. Test migrated/legacy and conflicting identity. Not implemented; schema, migration and trust gaps.
6. **Never auto-prune any date**: manual selection contract protects uncertain names. Attacker expects working BK-11 retention and selects incorrect files; test normal prune workflow. Not implemented; functionality/usability gap.
7. **Atomic snapshot/retention transaction**: design checks full collection and moves selected entries in one transaction under a writer gate. Attacker inserts or renames through noncooperative code; test concurrent creation/move and transaction rollback. Not implemented; broader writer-protocol and availability gap.
8. **Durable operation ID**: design records a request fingerprint and result atomically; attacker loses response or reuses key for different payload. Test committed response drop and retry. Not implemented; durable reconciliation gap, distinct from date validation.

## Negative space and modal shortcut
Misleading shapes: regex match not valid date; non-NaN not exact date; a rendered button not functioning prune; test data never overflowing; one timezone not all; valid Gregorian date not existing local time; local date not source timezone; repeated wall time not unique instant; filename timestamp not actual creation time; guard on one file not atomic batch; 200 response not proof of all operations; response loss not proof of rollback; same tab not cross-tab; Trash not erasure; green targeted tests not full gate; density count not comprehension; historical tags not Class A; reduced wall time without equal fidelity not Pareto; open-source dependency not a security audit. Modal shortcut: `!isNaN(new Date(...))` accepts overflow, so the actual Chromium test seeds February 30 and three real valid copies then inspects trash flags; it failed before the patch and passed after it.
