# TT236 — serialization of repeated pure-suite receipts

## Scope and resources

This is a bounded test-infrastructure improvement, not an OS feature promotion. Work used a Linux 2-CPU sandbox, Bash, Node/TypeScript, util-linux `flock`, the repo's actual runner, real child processes, and actual file system; the full gate uses the real Next server, PostgreSQL and Chromium. The race fixtures are small test-only programs and fault injection, not simulated app behavior. No independent agents, theorem prover or external expert review was used. Linux `flock` documentation was searched.

An admissible request is a `run-fast.sh` invocation naming existing pure-suite files (the current eligibility check is only a heuristic). A receipt is the shared `docs/test-results/<harness>.json`; logs belong to an invocation. For any cooperating `run-fast` invocations in the same workspace naming the **same validated suite name**, their test processes must not overlap; each requested occurrence must still execute. Different names should remain eligible to execute concurrently. A failed lock acquisition or failed worker must make the runner fail rather than print a successful exit. Lock acquisition defaults to a 1,200-second deadline (configurable to a nonnegative integer); a suite with surviving descendants holding a lock may cause a later same-name run to wait and fail at the deadline. This does not protect different suite names that write the same resources, other runner implementations or older copies, killed/detached writers that escape, renamed/unlinked lock files, incompatible network filesystems, receipt integrity against malicious code, or the heuristic's transitive dependency analysis. It is not a proof of app feature correctness or a benchmarked speedup.

H+: same-name cooperative calls can be serialized by an OS advisory lock without removing executions. H−: an advisory lock cannot protect against writers that ignore it or filesystems where its semantics differ; different-named tests can still collide. H∂: safety/liveness varies with filesystem semantics, inherited descriptors, cancellation, remaining child processes and shared receipt identities. Threshold: baseline real-process conflict, patched same-name and cross-run tests, distinct-name overlap, failure-injection test, runner regressions, and honest gate result. A green test-infrastructure result is not a Class-A feature claim.

## Frontier and mechanism

Linux `flock` is an advisory lock associated with an open file description, and duplicated or inherited descriptors can hold it until closed; see [flock(2)](https://www.mankier.com/2/flock) and [flock(1)](https://man7.org/linux/man-pages/man1/flock.1.html). `flock` does not force unrelated programs to cooperate and may behave differently on remote filesystems. The implementation creates workspace-local per-name lock files, validates suite names, acquires an exclusive lock around each full suite execution, propagates worker/xargs failure, and saves individual full logs for repeated names alongside the canonical log. The existing gate-log auditor still uses the canonical log for each same-named pure occurrence: the separate files are available but that auditor has not been changed to independently bind every occurrence. Receipt names may differ from suite file names; the lock is keyed by suite name, not discovered receipt identity.

The baseline real process experiment (`scripts/tt236-run-fast-serialization.mts`) returned **1/3**: duplicate-name processes overlapped and one failed an exclusive marker, while distinct names overlapped. Its synthetic missing-lock-command test only applies after a lock mechanism exists. Patched, **6/6**: duplicate same-run serialization, distinct-name concurrency, concurrent independent runners with the same suite, separate duplicate logs, a real held-lock immediate timeout, and fail-closed injected lock failure. The runner-contract suite passed 6/6 with its explicit disposable flag; an initial run without it failed 5/6 at that environment precondition and was rerun. A real `run-fast` invocation with the new suite and two unrelated suites passed. No before/after performance study occurred, and these checks add wall time and can serialize duplicate work: there is no Pareto speed claim.

## Mechanism portfolio

| Mechanism and artifact | Proven observation | Adversary / cheapest falsification | Unresolved gap |
|---|---|---|---|
| Workspace per-name flock (implemented, 6/6) | identical requested names in two tested runners do not overlap | noncooperating runner; alias name; lingering child; lock unlink | local cooperative boundary and liveness |
| Uncoordinated xargs (baseline 1/3) | distinct names can overlap | same suite twice with exclusive marker | counterexample |
| Drop duplicate names (design) | avoids same-name collision | compare requested execution count | loses executions; not accepted |
| Global single lock (design) | can serialize all cooperating suites | two unrelated long suites | removes useful parallelism |
| Per-invocation temporary receipts (design) | would isolate test results | hard-coded receipt path and cross-run shared app state | harness and auditor migration |
| Discover harness identity statically (design) | could coordinate aliases | computed/imported identities and dynamic side effects | transitive behavior analysis |
| Server/database parallel lanes (previous experiments) | separate datasets could enable parallel browser work | 2-CPU contention and timeouts | previous measurements did not establish Pareto improvement |

A passing summary, a green shell exit, a single log reused twice, same test name, distinct process IDs, two suite filenames, a successful run in isolation, a timestamp, a lock in a different directory, a noncooperating writer, a killed parent, a file left on disk, a fast wall time, one green test, a mock server, a reviewed source file, a status report, and a ledger label do not establish the stated property. The modal shortcut is a normal run in which suite names are distinct; the test intentionally sends the *same* name twice and asserts two real child executions do not overlap. The cheapest next attack is cancellation with a descendant that holds/inherits the lock, followed by an audit that binds each repeated invocation to its own receipt and full log.

No ten new Class-A features, all-app visual review, original graphics, complete PWA OS, measured Pareto speedup, or defensible modern-OS parity percentage was established. TT235 companion races, old-writer compatibility and density failures remain separate unresolved work.
