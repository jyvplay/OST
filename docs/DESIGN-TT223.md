# TT223 — CSP versus XFO precedence

## Runtime and scope
One agent used Node 22, Next production build and servers, an exclusive disposable PostgreSQL database, real local HTTP origin, Playwright Chromium 143, ESLint and web search. No independent agent, theorem prover, simulator, independent review or hosted CI was used. The origin returns controlled actual HTTP headers; its test server has the explicitly test-only loopback-port exception documented in DESIGN-TT222 and was stopped after testing. The normal server has no such exception. The work is not a universal browser conformance or product acceptance claim.

For a single observed probe response, the narrowly counted resource is the verdict. For headers in the fixture, success means an enforced CSP containing frame-ancestors is classified before XFO; report-only CSP and unrelated directive names do not override XFO. A standalone `*` is treated as network-origin-permissive; any other effective source list is conservatively restricted. This is not origin matching, a promise of successful framing, a claim about future responses or a substitute for a complete security model. H+: those finite cases are achievable; H−: a single server-side header read cannot establish every subsequent browser navigation; H∂: the answer depends on CSP enforcement, browser version, headers, nested ancestors, network and the actual response. Passing real fixture requests, a held-out browser enforcement check, fresh boundary attacks, build, affected regressions and the full gate were the evidence threshold for this narrow patch, not for ten Class-A features.

[W3C CSP3 §6.4.2](https://www.w3.org/TR/CSP3/#frame-ancestors-and-frame-options) specifies that an enforced frame-ancestors overrides XFO in conforming user agents; report-only is a different disposition. The specification does not imply all older engines behave identically or that a remote service will return the same policy to the user's browser. No external source code was copied.

## Counterexample, repair and attacks
On the prepatch build, an actual local response with `frame-ancestors *` and `X-Frame-Options: DENY` yielded `deny`; Chromium loaded that same cross-origin frame and displayed the real fixture content. With `frame-ancestors 'none'` and `X-Frame-Options: SAMEORIGIN`, the old route gave `sameorigin` rather than the effective CSP result; Chromium reported the CSP refusal. Two other baseline failures were test-oracle errors (comparing null response header to undefined), not app defects, and were fixed separately.

The route now uses enforced frame-ancestors first; it falls back to XFO when the directive is absent. The repaired real HTTP fixture plus independent Chromium checks passed 13/13; three new patch-specific attacks (a separate earlier CSP policy, similarly named directive, and empty enforced directive with XFO) then brought it to 16/16. Browser testing only exercised two conflicting header combinations on Chromium in this environment, not every source or browser. TT134's GitHub assertion was updated from XFO-first `deny` to CSP-first `csp-restricted` and strengthened to require the real XFO deny, effective `'none'`, and CSP reason; the test still requires the actual UI and live remote probe.

## Alternatives and exact gaps
The six candidate mechanisms, their causal models and 16 misleading shapes—including the modal shortcut—are in DESIGN-TT222. Specifically: XFO-first (actual conflicting-header counterexample); policy-first conservative classifier (implemented, attacked by report-only, mixed policy and empty directive); full ancestor matcher (unimplemented; nested scheme/port/browser inputs and tests needed); iframe trial (actual browser check here but cannot see all cross-origin failure causes); URL cache (stale, attacker changes response); unconditional handoff (breaks permissible embedding). Each has a different gap: the first is locally falsified, the second has unverified source-matching and older-browser boundary, the third needs a full standards-conformant parser and parent-chain inputs, the fourth cannot guarantee future requests, the fifth needs a freshness contract, and the sixth sacrifices functionality. The fixture is a concrete artifact, not an independent proof of universal compliance.

Remaining gaps include the separate `embed-policy.ts` parser, partial/non-exact XFO parsing, conservative false refusals for policies that actually allow this parent, Browser UI language that may overstate a conservative restriction, changing responses, TLS and nested frames. The `*` classification does not guarantee a frame renders; malformed policies and non-HTTP ancestor schemes are not exhaustively checked. Fixture tests require a separately configured isolated server and are not automatically part of the full gate.

This is one narrow repair, not ten production Class-A features. No complete visual review, graphics work, measured Pareto speedup, full OS parity, or distance-to-parity figure is substantiated.
