# TT197 — arbitrate Files selection and shell search chords

## Model and success predicate
Admissible inputs are actual key events delivered to a focused Files list/grid option in a shell using one of its three shortcut presets. State comprises the selected visible paths, focused option, preset, and whether the command palette is open. The palette chord is Ctrl+Space in hybrid/Windows and Meta+Space in mac. For each tested preset and view, when a delivered event matches that preset's palette chord and the shell is eligible to handle it, the palette opens and the existing selection remains unchanged; a distinct Ctrl+Shift+Space toggles the focused option without opening the palette. Filter focus must still permit the global chord. The environment is real Chromium 143, production build and exclusive disposable PostgreSQL; no proof covers all event sequences, browser/OS interception, user preferences, assistive technologies or dynamically configured future bindings. Resource is one constant-size binding lookup on keydown; no performance claim. Adjacent problems not substituted: keyboard accessibility conformance, native OS reserved-key delivery, user-remappable shortcuts, preserving IME input, and general arbitration of all shell and module shortcuts.

H+: routing an exact conflicting chord solely to the existing shell action prevents two effects. H−: if the operating system never delivers the chord, browser-side routing cannot make it work. H∂: different presets, actual OS/keyboard layouts, modifier combinations, input-method interception and focus contexts change the outcome. Evidence threshold for the bounded repair: real baseline counterexample, production build, explicit no-double-effect browser checks in each preset, a non-colliding toggle test, selected/unselected attacks and affected regressions, with full-gate failures disclosed. This is not Class-A evidence.

## Frontier and choice
[W3C's listbox pattern](https://www.w3.org/WAI/ARIA/apg/patterns/listbox/) describes focus vs selection and a Ctrl+Space selection model; its [multi-select example](https://www.w3.org/TR/2019/NOTE-wai-aria-practices-1.1-20190814/examples/listbox/listbox-rearrangeable.html) instead uses Space for toggling. Neither resolves this app's competing global palette chord or establishes behavior under OS-level interception. We retain the global palette for its existing presets and use Ctrl+Shift+Space as the discoverable non-conflicting multi-select toggle; this is a deliberate tradeoff, not a claim that the standard Ctrl+Space selection model is preserved in those conflicting presets. Existing plain Space behavior is unchanged. No third-party source code was copied.

## Six mechanisms and adversaries
1. **Existing parallel handlers**: actual baseline 0/3; palette opens while beta becomes selected in all presets. Attacker checks selection after opening, not just dialog visibility. Local failure.
2. **Suppress palette propagation from Files**: causal counterexample: focused Files option then global palette chord can no longer open search. Cheapest test is to assert palette opens from the option. Unimplemented, local feature loss.
3. **Shell ignores every `defaultPrevented` event**: could prioritize local action, but would change shortcut routing for unrelated modules, text fields and overlays. Cheapest attack checks global palette in a text field and non-Files modules. Unimplemented, broader integration gap.
4. **Hard-code Ctrl+Space only**: misses mac preset Meta+Space; existing three-preset real browser test detects it. Local interface gap, unimplemented.
5. **Exact configured palette binding takes precedence in Files**: implemented using existing `matchChord` and preset; no mutation on matching Space chord, event bubbles to the shell. Browser checks both selected and unselected states, list/grid, all presets, filter, and non-colliding toggles. Limitation: assumes shell has the same preset and is eligible to process the delivered event; native OS interception and screen readers are not tested. Local gap.
6. **User-remappable conflict resolver**: a UI could let users resolve collisions, but would need persisted per-context policy, conflict detection, migration and cross-module tests. No implementation; cheapest falsification is two contexts with competing mappings. Broader integration gap, not equivalent to completing the whole OS.

Modal shortcut is stopping propagation locally: it prevents double effects but silently removes the global palette from Files; the test asserts palette visibility from both list and grid. Other misleading shapes: palette opens but selection changes; no selection change but palette never opens; unselected case only; selected case only; hybrid only; Windows only; mac ignored; hard-coded Ctrl regardless of preset; only list not grid; keys swallowed in filter; alternate toggle lost; plain Space changed; Ctrl+Arrow selection lost; event handled twice; only synthetic events; shell modal assumptions ignored; synthetic mac preset presented as macOS testing; browser result claimed as screen-reader proof; full gate failure hidden; marking one narrow repair ten Class-A features.

## Experiment and runtime honesty
Used shell, git/gh, web search, Next/TypeScript production build, ESLint, real Chromium 143, real disposable PostgreSQL and the repository regression tools. No independent agent, expert, theorem prover or simulator was used. Baseline 0/3: all presets opened the palette and selected beta. First repaired test run failed 0/3 because its Grid setup used Ctrl+ArrowDown (which correctly moves by a full grid row); the fixture was corrected to Ctrl+ArrowRight, not the product. Subsequent 3/3 passed, including selected/unselected palette cases, list/grid, filter and alternate toggle. Tests use synthetic browser key delivery on Linux, not a real macOS keyboard; Ctrl+Shift+Space may be intercepted by OS/IME software. No all-app review, original graphics or measured Pareto speed improvement was established.
