# TT178 — interrupting the browser lane without leaving its active suite behind

## Model, access, thresholds
Objects: the real `scripts/run-gate.sh` browser-lane loop, its timeout wrapper, a Unix process group, Node test suite and its children. Inputs: normal completion, failure, timeout, SIGINT or SIGTERM while waiting; tests exercise real child processes, not simulated test results. Access: source, Linux shell/process table, Node compiler/toolchain when installed, git/gh and documentation. Count: surviving observed processes, signal/exit codes and existing assertions; no speed claim. For each explicitly exercised cancellation of a normal, cooperating process group during a browser-lane suite, the gate must exit nonzero and must not leave the active group executing after cancellation; normal 0, nonzero and timeout status must remain distinguishable. Quantifiers are over tested schedules, not all kernels or uncooperative descendants. This is not full cleanup of detached processes, whole-gate cancellation safety, non-Unix portability, a faster gate, a complete app, or any Class-A feature.

Pre-commit threshold: a direct observation of the old orphan behavior or existing real gate evidence, an executable real-process interruption test that fails on the old implementation, independent attacks on normal status/failure and interrupted/timeout paths, affected gate-runner regressions, and a clear full-gate status. No user data or shared production DB is to be touched. User asks for new PR, not merge.

H+: isolating and terminating the active browser-suite process group can close this observed cancellation hole for cooperating group members. H−: previous real full gate was stopped and left timeout/Node children running (TT177 evidence); this is not a general impossibility proof. H∂: an individual descendant can start a new session, ignore TERM, the caller may use SIGKILL, or platform process semantics may differ. Even successful group cleanup cannot protect against those cases. Available: shell/git/gh, Node and TypeScript once installed, real Linux processes; web research. No independent agents, theorem prover, simulator or human expert. Real Chromium/PostgreSQL require separate installation on this reset and are not presumed available.

## Research frontier and mechanisms
The Node child-process documentation explains that on non-Windows systems a detached child becomes a process-group/session leader and that killing a shell does not necessarily kill its descendants (https://nodejs.org/api/child_process.html). This is a platform behavior, not a proof that all descendants remain in that group. GNU `timeout` and util-linux `setsid` are actual dependencies; `setsid` is checked explicitly, and lack of it fails closed instead of silently losing isolation. No universal process-tree termination or whole-OS optimality theorem is claimed. The unverified interface is cleanup of children that create their own process groups/sessions and cleanup of DB fixtures when a suite is interrupted.

Mechanism portfolio (designs not used are not claimed verified; gaps local to runner unless stated):
1. **Foreground direct timeout**: previous actual gate and TT177 stop evidence. Attacker sends TERM to parent; timeout/Node continue. Concrete prior `/proc` observation is the counterexample. Local failure.
2. **Kill only direct timeout**: design sends TERM to its PID. Attacker spawns a child that outlives its parent or ignores TERM; cheapest test is a real shell plus `sleep` with different signal disposition. No group containment; local gap.
3. **Isolated process group with gate forwarding**: `scripts/gate-child.sh` uses `setsid` and `timeout`; cancellation KILLs the helper's group. Concrete real-process tests cover success, exit 7, timeout, TERM, INT, an ignoring child and independent concurrent helpers; actual gate cancellation also observed. Attacker uses a detached session or KILLs the parent before traps run; outside local guarantee, and interrupted tests may leave DB state.
4. **Cooperative graceful teardown**: proposal sends TERM and waits for finally hooks. Attacker ignores TERM or dies after a partial DB mutation. Falsify with a TERM-ignoring real child and partial write. Not implemented; local lifecycle and cleanup gap.
5. **Cgroup/container per suite**: design makes membership kernel-enforced and kills the cgroup. Attacker changes cgroups with privileges or platform lacks delegation. Falsify with a session-detached child. Not implemented; infrastructure/portability gap broader than this repo.
6. **PID-tree traversal**: proposal enumerates descendants and signals them. Attacker forks or reparents between enumeration and kill; test with rapid real forks. Not implemented; local TOCTOU gap.
7. **Disposable server/database per run**: design makes leaked writes affect only abandoned isolated data. Attacker exhausts resources or still leaves leaking processes. Test concurrent cancellation and isolated DB paths. Not implemented; environment and cleanup gap; does not replace process containment.

## Negative space
A stopped parent is not a stopped child; a direct child exit is not descendant exit; no PID in one `ps` snapshot is not a universal proof; a zombie is not a running worker; a successful `kill()` is not proof of teardown; a trapped TERM is not catchable SIGKILL; same process group is not a whole process tree; a detached browser is not contained automatically; kill of the process is not rollback of every external effect; a discarded DB connection is not fixture cleanup; a completed summary is not a zero exit code; a fast test is not unchanged fidelity; a fresh cache is not a clean database; one Linux distribution is not every host; a shell-syntax check is not execution; controlled child tests are not a real receiver or human validation; a partial gate is not a passing gate; the register is not Class-A evidence; an empty directory is not arbitrary user data; a full gate pass is not complete OS certification. Modal shortcut: terminating only the outer shell leaves an active timeout/Node worker. The real TT177 gate cancellation produced that exact result, while this turn observed an active new gate group before cancellation and verified its three recorded PIDs were absent afterwards.

## Newly discovered first-save regression: model and threshold
The completed full gate revealed TT176's first real save failing on an initially absent `/Backups`; later suites create that directory and mask this state. Hypotheses: H+ a safe idempotent directory-ensure before conditional create restores fresh-install saving without overwriting existing copies; H− the current first save is refused when the parent is absent; H∂ a trashed or non-directory parent, concurrent tree mutation, and lost responses must remain fail-closed. Explicit success: for each tested fresh disposable DB schedule, the first save must create a live folder and one copy; for tested blocked-parent schedules it must not revive/overwrite the parent or create a copy; previously existing same-name copies remain guarded. `mkdir` and create are separate transactions, not an atomic combined save. Evidence threshold before editing production code: reproduce on a newly created, isolated DB with real HTTP/Chromium; then rebuild, rerun fresh-path test plus TT176/175/174 and runner tests; full gate and interrupted earlier run remain honestly reported.

### Backup candidate mechanisms and attacks
1. **Old guarded write requiring existing parent**: real fresh-DB counterexample timed out waiting for success; its conditional write rejected the missing parent. Local first-run functionality failure.
2. **Unconditional `write` with implicit parent creation**: existing VFS operation can create parents, but the TT176 real repeat-save counterexample proves it overwrites an existing copy. Local data-safety failure.
3. **Ensure folder then create-only**: implemented existing `mkdir` followed by `writeIfUnchanged` with expected null. `mkdir` rejects trashed/non-directory parents; the second operation revalidates. Tested real browser fresh folder, trashed folder, file at parent and lost real mkdir response. Attacker trashes/purges between the requests; conditional write must refuse and can leave only the folder, so no atomic two-request guarantee. Missing exhaustive concurrent schedules is a local gap.
4. **Atomic server create-with-parent**: design puts directory creation and conditional insertion in one transaction with cooperative locks and unique path arbiter. Attacker races rename/trash or tries to use it against a file parent; cheapest test interleaves real transactions. Not implemented; API and shared VFS semantics gap.
5. **Client list-then-mkdir**: design creates only if listing says missing. Attacker changes the folder after listing or the listing is stale/failed. Test holding the request and changing parent. Not implemented; local TOCTOU gap.
6. **Always reject missing parent**: previous mechanism avoids creating a folder, but a fresh install cannot save. Real fresh test falsifies desired workflow. Local usability gap.
7. **User chooses a directory**: design delegates to existing folder picker. Attacker selects a trashed or concurrently removed folder; test write against actual VFS identity. Not implemented; UI and workflow compatibility gap, does not replace guarded server mutation.
