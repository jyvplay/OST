# TT160: concurrency-safe automation admission

## Model and evidence threshold
Admissible requests are valid whitelisted automation commands submitted with a live run-scoped bearer token to this Next.js route, sharing one PostgreSQL database. Count accepted requests per fixed 60,000 ms window anchored at the first accepted request (maximum 30 per token) and queued rows (maximum 50 globally). For every finite set of simultaneous route requests on the same database, at most 30 per token and at most 50 queued through the cooperating admission path are accepted. A full queue is a refusal rather than a consumed allowance. A token revoked before it acquires its row lock cannot enqueue. A statement failure must roll back its transaction. These are admission properties, not fairness, throughput, exactly-once execution, cross-origin protection, scheduler delivery or guarantees against independent SQL writers that bypass the lock.

H+: a single short transaction coordinating all route writers can uphold the bounds. H−: advisory locks cannot protect against a separate writer that does not take them; atomic admission alone cannot ensure exactly-once external effects. H∂: simultaneous revocation, database availability, wall-clock changes, bypass writers and queue drains affect outcomes. PostgreSQL's [advisory-lock documentation](https://www.postgresql.org/docs/current/explicit-locking.html#ADVISORY-LOCKS) describes transaction-scoped cooperative locks released at transaction end; it does not establish application-wide discipline or delivery semantics. Implementation is independently written.

Declared threshold: production build and TypeScript; both old-code concurrency attacks must fail before and pass after; add a new post-patch revocation race; rerun settlement, existing automation HTTP and browser tests. Full merge additionally requires a clean full gate. No independent agents, simulator, theorem prover or expert review were used. Actual tools include Node, Next/TypeScript, Chromium/Playwright, PostgreSQL, Git and web search.

## Mechanism portfolio and attacker
1. **Transaction-scoped global advisory lock + locked token row** (implemented): concrete route and `tt160-automation-concurrency.mts`. Same-token 40 concurrent requests accept 30, reject 10; three tokens with 60 requests accept 50, reject 10; a real held-lock/revocation race rejects the delayed request. Attack: a noncooperating SQL insert ignores the lock; global interface remains open. Queue depth can decrease concurrently, yielding conservative refusals, not over-admission.
2. **Read then write without coordination** (old code): executable counterexample accepts 40/40 and 56/60 respectively, breaking both limits. Local gap: transaction admission.
3. **Per-token row locks alone** (not implemented): prevents shared-token counter loss, but different tokens can each see the same available queue slot. Attack: concurrent requests from distinct tokens at depth 49. Global queue gap.
4. **Serializable isolation** (not implemented): may detect conflicting predicates; caller must correctly retry serialization failures and preserve responses and audit semantics. Attack: competing transactions and retry exhaustion. Local admission gap, but requires an explicit retry protocol.
5. **Database constraint or slot table** (not implemented): preallocated unique slots can enforce capacity in the schema, but need crash-safe release and migration. Attack: lost or leaked slot on failed enqueue and concurrent drain. Global lifecycle gap.
6. **In-process semaphore** (not implemented): two app processes do not share memory. Attack: concurrent requests across independent processes. Global coordination gap.

## Negative space
1. Thirty serial requests are not a concurrency test. 2. One token is not a global bound. 3. A count before insertion is not an atomic reservation. 4. A request validated before waiting is not necessarily still authorized. 5. Advisory locks do not constrain nonparticipants. 6. A queue cap is not exactly-once execution. 7. A terminal audit is not a completed external action. 8. Rate limit is not authentication. 9. A bearer secret is not cross-origin CSRF prevention for other endpoints. 10. A lock is not fairness. 11. A single server test is not multi-node verification. 12. A full queue refusal is not a permanent failure. 13. Wall-clock movement is not monotonic time. 14. Successful HTTP responses are not durable if the database subsequently fails. 15. Fixture deletion is not a production recovery mechanism. 16. A green targeted suite is not a green gate. The modal shortcut (serial tests only) is detected by the paired 40-request and multi-token 60-request real HTTP attacks.

## Verification and open interface
Against the previous production build the attacks accepted 40 rather than 30 and 56 rather than 50. On the rebuilt production server all three concurrency tests passed, TT159 settlement 2/2, existing automation HTTP 4/4 and TT146 Chromium 5/5; build and TypeScript passed. The global lock serializes all enqueue admissions, so a significant speed improvement is not claimed. Browser shell queue consumption still has no atomic claim, and settlement remains unauthenticated; this change is not a security audit or proof of a production-ready automation feature. Next: adversarial two-shell execution and crash recovery tests, with authorization and explicit ambiguous-outcome handling. No 20 Class-A promotions, full visual audit, original graphics or measured test-speed gain are claimed. Full gate outcome is reported separately.
