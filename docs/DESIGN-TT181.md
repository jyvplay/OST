# TT181 — bounded token-list recovery

## Formal model and hypotheses
The admissible object is the Routines token-list GET and its client state, with the real Next API, a disposable PostgreSQL and Playwright-controlled Chromium; tests may delay or drop actual HTTP traffic and inspect DOM/database, but fault injection is not a real network outage or a proof of all schedules. Count milliseconds of active event-loop timer delay and request attempts; no CPU or latency optimization is asserted. For each tested GET issued by this panel, if the browser event loop runs, the native fetch honors abort, and React renders, a request that has not settled by the 8,000 ms timer is aborted and the latest list is marked unavailable or stale, not empty; a failed-mint recovery eventually unlocks retry while retaining the ambiguous-commit warning. A successful mint must retain its one-time secret and stay locked while displayed. For all tested older requests superseded by a newer list, their late completion or timeout must not replace the newer result. Browser throttling/suspension and OS scheduling mean 8,000 ms is a requested timer delay, not a hard wall-clock bound. The mint POST itself is not timed out. A deliberate retry can still create an extra token after an ambiguous POST; this work does not supply exactly-once semantics.

H+: bounded GET recovery under the stated browser/fetch conditions can be tested. H−: aborting a GET or losing a POST response cannot tell the client whether the server committed the POST. H∂: suspension, a non-abortable transport, multi-tab activity, and a stalled POST change liveness; no claim over those cases. Distinct problems not substituted: POST timeout, server cancellation, complete reconciliation, idempotency, secret recovery, generic fetch reliability, universal accessibility, all-app Class A, and speed/CPU Pareto optimization. Evidence threshold: real pre-patch counterexample, production build, patch-directed real-browser attacks with real DB and affected token regressions; broad claims require additional gates and expert evidence.

## Frontier and interface
MDN documents `AbortController` and fetch: aborting can reject the fetch or a subsequent body read; it is not a server rollback guarantee (https://developer.mozilla.org/en-US/docs/Web/API/AbortSignal). MDN notes that `AbortSignal.timeout` uses active time and can pause in suspended contexts (https://developer.mozilla.org/en-US/docs/Web/API/AbortSignal/timeout_static); this implementation instead uses a cancelable `setTimeout` and clears it, and likewise makes no real-time guarantee under throttling. Reviewed MIT-licensed p-timeout's documented promise-timeout approach (https://github.com/sindresorhus/p-timeout); no package or source was copied. A promise race alone does not stop network work or prevent late state updates. Open interface: the browser can abort a GET and preserve version ordering, but a dropped mint response does not distinguish failure before commit from successful commit. Neither a timeout nor a list snapshot establishes exactly-once minting.

## Mechanism portfolio and attacks
1. **Wait forever**: old production code, a concrete counterexample: after a real committed POST was dropped and the subsequent real GET held, no timed-out list warning appeared within 14 seconds. Local liveness failure.
2. **AbortController plus timer**: production code, timer cleared in finally; new Chromium attacks hold a GET after lost POST and after successful POST. Stale/unavailable warning and deliberate list retry are observed; exact unresolved interface is browser/event-loop behavior and unresolved POST ambiguity. Local gap, not global OS proof.
3. **Promise race alone**: candidate causal model, not implemented: timeout can settle the caller while the original work keeps running; late response can overwrite current state. Cheapest attack delays an old response beyond a newer one. Local stale-update gap.
4. **Version/epoch guard**: existing request version compares every completion with the latest. New test times out an older held GET after a newer successful mint/list refresh; newer row and secret survive. It does not prevent multiple clients from minting or cancel server work. Local ordering gap.
5. **Automatically repeat POST**: rejected causal model: dropped committed response followed by a retry may create a second credential. Cheapest attack commits then drops the response. Equivalent to missing idempotency at the server/client interface.
6. **Durable idempotency protocol**: unimplemented design: persist a client operation key with server-side transaction and result strategy. Attack concurrent requests, lost keys, and safe handling of the one-time secret after response loss. Cross-API/database protocol gap; not solved by GET timeout.
7. **Never permit retry after failure**: unimplemented policy: avoids repeated client minting in this panel but can permanently lock the user after a failed request and still cannot govern other clients. Attack unreachable server and independent tab. Local liveness and cross-client gap.

## Negative space and modal shortcut
Timer scheduling is not a deadline; GET abort is not POST rollback; a rejected fetch is not proof of no commit; a refresh is not a durable transaction; a stale list is not an empty list; a visible warning is not evidence a user read it; retry is not exactly-once; same-tab guard is not cross-tab locking; one secret shown is not proof of no other secrets; an ignored old timeout is not global concurrency proof; a network timeout is not server failure; a promise race is not cancellation; a successful list is not permanently current; a test interception is not a physical network failure; an 8-second timeout is not an OS-wide policy; one browser is not all browser engines; a screenshot is not an accessibility audit; a build is not a full gate; increased test coverage is not a measured speedup; a self-reported register is not Class A. Modal shortcut: simply waiting for the list forever. The pre-patch real-browser held-response attack failed at 14 seconds; after repair it passes and checks actual stale warning and list retry, while a second attack preserves a real successful one-time secret.

## Execution, results and gaps
Available and actually used: two logical CPUs, shell/Git/gh, web search, Node 22 and TypeScript/Next build, Playwright Chromium 143, local disposable PostgreSQL, and a production Next server. No independent agents, theorem prover, simulator, human accessibility auditor or expert reviewer were used. Test transport interception was fault injection around actual browser/server/database traffic; no mock behavior ships. No external package added.

Pre-patch: `e2e-tt181-token-timeout` failed 0/1 waiting 14 seconds for a timeout warning. Post-patch production build passed; timeout suite 3/3 (lost committed response, real successful secret, older GET timeout after newer refresh); mint 6/6, token recovery 4/4, token races 4/4, paging 1/1, revoke 4/4, DB atomicity 4/4, and Routines 2/2 passed. The first new case was rerun after its screenshot/visibility assertion and passed 1/1. Shell syntax and diff check passed. The Routines stale-state screenshot was visually inspected; no all-app visual survey or independent accessibility review. The full gate was attempted but stopped at its read-only prerequisite check because test-only `@js-temporal/polyfill` and potentially other pinned tools/corpus were absent; no gate suites ran (`.cache/gate/20261116T034443Z/run-3704-o8Q5k8`). This is not a passing full gate. The prior TT179 incomplete gate and TT180 targeted TT134 result remain as recorded in those designs.

This increases tested recovery behavior, not 20 feature promotions or a claim of Class A. No new graphics, all-app review, or measured performance improvement. Eight seconds may be too short on slow networks; a timed-out server may still process its request; after list timeout a deliberate mint can duplicate a lost successful mint, and a POST itself can hang. Highest-information next experiment: a real transaction-backed idempotency/reconciliation protocol attacked with concurrent same-key POSTs and dropped responses, followed by a properly provisioned full gate and accessibility/device review.
