# TT165 — token list recovery and user intent

## Admissible model and acceptance
Scope: Routines' token list, mint response and search in the current PWA. Resources counted: actual real-browser test outcomes, page state and eight-row pagination; no CPU, speed or universal correctness claim. Access: local source/git/gh, web search, production Next/TypeScript, headless Chromium/Playwright, HTTP and exclusive disposable PostgreSQL. No independent agents, proof assistant, simulator, human expert or assistive-technology testing was used. The real POST response is delayed by the test without altering its body; other tests deliberately abort GET requests to inject failure, not claim a simulated response was production behavior.

For each tested interleaving, success means a user's later search remains after the mint response, failed list retrieval is not presented as a known-empty list, and retry obtains current server data without losing the one-time mint secret. For the branch as a whole, all mandatory suites must pass on the exact production build before merge. Local commit evidence threshold: a failing old-build regression for the targeted flaws; new attack against the patch; successful build, affected browser regressions, and honest disclosure of any failing full gate. H+: a scoped repair can satisfy these tests; H−: a universally correct and complete OS may be impossible under the stated constraints, not established here; H∂: correctness depends on ordering, network errors, concurrent actions, backend availability and browser/AT behavior. An empty API result is not a failed GET; client list freshness is not server authorization or exactly-once command execution.

## Evidence and construction
The old production build failed all three initial cases: pending POST reset a later search, initial GET failure supplied no dedicated recovery/unknown-state UI, and refresh failure supplied no stale/retry UI. The first directly observed `''` instead of the typed ID; the other two timed out waiting for a recovery control, so their test failures alone do not prove every displayed text. The proposed fix captures the interaction generation before the POST and clears/selects only when unchanged; list state separately tracks loaded/loading/error, preserves the last successful rows, labels failed refreshes stale and exposes retry. During loading, a previously empty list is not presented as a confirmed empty list. A fourth attack releases an older genuine successful GET only after a newer refresh has failed and verifies that it cannot mask the failure; retry must recover the minted row and preserve the one-time secret.

React's documentation https://react.dev/reference/react/useEffect describes out-of-order response risks and an effect-scoped ignore pattern. It does not certify this multi-request implementation, retry UX, or authorization model. The code here is independently written. No global best-known implementation or impossibility theorem for the entire OS task is established.

## Six mechanisms and their adversaries
1. **User-interaction generation:** capture a counter at mint initiation, conditionally apply selection; concrete delayed-real-POST browser attack changes search before release. Proven only in the tested sequence; simultaneous mints and unmount are local gaps.
2. **Request generation:** ignore older list completions; concrete held-old-GET and failed-new-GET attack. Tested ordering is not a global freshness proof; latest failure and network recovery remain local concerns.
3. **Explicit unavailable/stale states:** distinguish unsuccessful retrieval from known emptiness; abort a real initial or refresh GET, verify warning and secret retention. Unresolved: long offline periods and screen-reader review; local UI gap.
4. **Retry via fresh GET:** user invokes another real request; attacks include a failed retry, deletion or concurrent revocation before retry. The test establishes one successful retry only; local error-recovery gap.
5. **Abort obsolete requests (alternative):** use AbortController to reduce in-flight work; attack a completed response racing cancellation. No implementation or performance evidence; local lifecycle gap.
6. **Versioned server snapshots (alternative):** return server revisions and compare freshness; attack process restart and mutations from multiple tabs. No implementation; requires backend protocol and still does not solve full OS correctness.

Negative-space shortcuts: missing rows mean no tokens; old success cancels newer failure; user intent at response time equals intent at request time; a spinner proves eventual completion; error text alone enables recovery; retry implies success; aborting network proves the server never committed a POST; holding a response means the POST was not executed; stale rows are current authorization; client ordering proves transactional snapshot; hidden row means revoked token; accessible label alone proves screen-reader use; one browser proves cross-browser behavior; all passing targeted suites imply a full gate; lower word count proves usability; adding tests proves a performance win; aggregate ledger proves Class A. The modal known-empty shortcut is detected by the failed-initial-GET test.
