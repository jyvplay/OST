# TT189 — tab-session continuity for uncertain revocations

## Runtime, formal model and threshold
One coding agent used Bash, Git/gh, web search, Node 22, Next/TypeScript production compiler, ESLint, Playwright with real Chromium 143 and a disposable PostgreSQL database. Independent agents, theorem provers, and simulators were not used. Test-only injected Storage exceptions are fault injection, not claims about a real browser policy. The app code is independently written and adds no dependency. Two CPUs were available; browser suites share one disposable DB and run sequentially. Test setup downloaded third-party tools outside the app.

Admissible objects: eight-character token IDs from the existing API, not bearer secrets; a token DELETE, subsequent list reads, and sessionStorage operations in the same top-level tab and origin. The attacker controls the ordering of a genuine database row lock, revoke, list, timeout, reload, storage failure, and release. The client cannot inspect a pending server transaction. Measured resources: bytes/keys per attempted token (one sessionStorage key/value per distinct ID for the lifetime of a tab), time (12 s DELETE and 8 s list deadlines subject to scheduling), and test outcomes. No latency or scalability bound is proved.

Target, in quantifier order: for every exercised token and tested ordering, if the tab's sessionStorage successfully records the ID before DELETE and retains it, and a later list in that same page session reports that ID live, the rendered row remains qualified uncertain; if storage access fails while mounted the UI warns that a reload may lose the marker. A revoked row may be shown revoked. Failure is an unqualified live row in those conditions, no warning on the injected storage failure, false bearer persistence, or regression of the tested revoke behavior. The concrete experiments establish only their specific runs, not the universal quantifier. Other tabs, current concurrently mounted panels, cleared storage, new tab sessions, malformed server results, storage corruption, browsers other than Chromium, suspended event loops, server operation completion, durable restart and multi-client synchronization are not established. A warning before reload cannot be preserved through reload if storage writes fail. This is not server-side revocation confirmation, a universal distributed protocol, Class-A certification or a solution to the entire OS task.

H+: continuity across same-tab reload is achievable when session storage works and its value remains intact. H−: if a client loses both request response and all state before reload, an early live snapshot alone cannot distinguish an undelivered revoke from one waiting to commit. H∂: tab/session scope, storage availability, ordering, and caller behavior determine which guarantee applies. Evidence threshold for this narrow patch: fail a genuine prepatch late-commit reload case, build the patch, demonstrate both early and late reload with real DB locking and bearer checks, test storage failures and retest related suites; report full gate honestly. No claim of overall success if any mandatory global requirements remain unmet.

## Frontier and alternatives
[MDN sessionStorage](https://developer.mozilla.org/en-US/docs/Web/API/Window/sessionStorage) specifies per-origin and top-level browsing-context storage surviving reload in a page session; an opener can initially copy it, then changes are independent, and security policy can throw. It is not a durable cross-tab journal. [PostgreSQL READ COMMITTED](https://www.postgresql.org/docs/current/transaction-iso.html) states that an ordinary SELECT sees a snapshot from statement start and may precede another transaction's later commit; row-updating operations can wait on locks. These statements require their stated isolation, storage and browser conditions; they do not prove our code correct.

Six distinct candidates, with candidate-specific attacker and evidence or causal artifact:
1. **Per-ID session markers (implemented):** synchronously write only ID before DELETE, read markers before rendering new list. Attacker reloads before timeout or after warning dismissal while the server is genuinely blocked; tests verify uncertainty and actual late authorization failure. Gap local: storage denial/loss, separate tabs, concurrently open panels do not synchronize, and no durable server proof. A separate key avoids read-modify-write loss across distinct IDs in the same tab, but does not notify other mounted panels. Cheapest additional attack: two simultaneously mounted panels, then revoke from one and inspect the other.
2. **Only component state (TT188 baseline):** marker exists until unmount; the real row-lock reload experiment failed 0/1 on baseline. Gap local is component lifetime.
3. **One JSON session array:** read/modify/write updates can overwrite concurrently stale arrays from separate panels. Causal interleaving: both read empty, A writes [A], B writes [B]. Gap local; cheapest attack is two panels updating from the same initial array. Not implemented.
4. **Persistent localStorage plus cross-tab events:** broader scope, but leaves longer-lived ID metadata and events do not establish server completion; storage policy and crash timing still matter. Attack: clear data or start a tab after stale snapshot. Causal design only; gap local for storage, original distributed ambiguity for commit.
5. **A single post-timeout refresh:** DB-lock experiment yields a live snapshot and then commits; it cannot distinguish pending and never-delivered operations. Concrete counterexample, not adopted. Gap is equivalent to the client-side outcome-identification problem under this access model.
6. **Authenticated durable server operation journal:** allocate identity before mutation, persist transition and provide status/cancellation semantics, with carefully defined idempotency and retention. Attacker delays original delivery beyond a status lookup or retention boundary. Causal design only; gap local to a new protocol, not proof of whole OS completeness.
7. **Automatically repeat DELETE until success:** tested same-ID retry can be idempotent, but indefinite networks and server failures defeat a bounded guarantee; additional requests and retention semantics matter. Attacker blocks network forever or starts a request just before retry. Not implemented; liveness gap remains.

## Negative space and modal shortcut
Abort is not rollback; a timeout is not a failure verdict; a timeout is not a success verdict; one snapshot is not a future-state guarantee; dismissal is not resolution; same-tab persistence is not cross-tab synchronization; session storage is not a durable journal; a marker is not authorization; an ID is not a secret bearer; same-origin scripts can read storage; a row lock test is not a real production network; injected Storage exceptions are not a browser-policy survey; one browser is not all engines; a successful build is not runtime correctness; an accessibility role is not a screen-reader test; one screenshot is not all-app review; more tests are not a speedup; a historical feature label is not Class-A proof. Modal shortcut: infer that a token will remain live because a read currently says live. The attacker holds the actual row lock through the refresh and reload, releases it, then checks real bearer 401, detecting the shortcut.
