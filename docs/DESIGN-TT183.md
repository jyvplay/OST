# TT183 — Files and Monitor: example-versus-live boundary

## Scope and verification model
The object is the shared Trash policy, drag/drop mechanics, and volume panels in the web shell, not a new operating-system filesystem. Accessible resources: repository source and tests, two CPU sandbox, production Next build, disposable local PostgreSQL, Playwright Chromium 143, independent Python zipfile oracle. The browser checks exercise one fixture, window geometry, browser version and origin; they do not quantify over every browser, layout, accessibility technology, or user dataset. No outside source code was copied. W3C's [disclosure guidance](https://www.w3.org/WAI/ARIA/apg/patterns/disclosure/examples/disclosure-card/) informs accessible disclosure design, not a proof that this interface conforms.

H+: example results are identified as such, the live origin estimate is separately identified, a missing or rejected estimate terminates in an honest unknown, and an actual trashed row remains unchanged. H−: a fixed result suggests that a user's Trash was emptied, a transfer happened, or a volume was actually inspected; an unavailable estimate stays loading forever. H∂: a browser may provide partial estimates, reject, suspend, never settle, or throw during property access; quota is origin-wide, not server filesystem capacity. The implementation catches access errors but no global-app claim is made for a hostile navigator.storage getter.

## Mechanisms considered and boundaries
1. Label existing pure examples (implemented): preserve the demonstrations while identifying their hypothetical inputs and outputs; attacker: mistake a badge for real operation. Browser and DB witness covers this fixture, not all mental models.
2. Remove example panels: reduces confusion but removes existing functionality; not adopted.
3. Connect examples to actual filesystem mutation: would require real authoritative operations, permissions, failure handling and destructive-action UX; no such adapter or proof was built.
4. Move examples into disclosures: W3C disclosure pattern offers keyboard/expanded-state guidance; requires layout, accessibility and discovery retests; not adopted here.
5. Distinguish unavailable and failed browser estimates (implemented): absence uses unavailable; rejection/access error uses failed and unknown; partial remains partial. No timeout for a promise that never settles.
6. Verify state against PostgreSQL (implemented test): actual trashed row remains unchanged while panels render. Doesn't prove every Trash workflow or concurrent mutation.

## Misleading results / modal shortcuts to avoid
A passing build is not a functional proof; a labelled example is not a real operation; a no-mutation test is not a proof of all write paths; origin quota is not disk space; partial is not complete; rejection is not API absence; a browser's response is not universal; a single geometry is not responsive-layout coverage; a keyboard strip check is not full accessibility conformance; a density cap is not a usability assessment; a passing isolated zip test is not a passing suite; baseline reproduction is not root cause; prerequisite failure is not a gate pass; historical coverage labels are not Class-A accreditation; a hypothetical faster execution is not a measured Pareto gain. In particular, “could”, “should”, and “might” are hypotheses rather than executed evidence.
