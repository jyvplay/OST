# TT224 — atomic revision check on desktop PUT

## Runtime, contract and frontier
One agent used web search, Node 22, the Next production build/server, PostgreSQL, actual HTTP requests, Playwright/Chromium through the full gate, and ESLint. No separate agent, independent review, simulator, theorem prover or hosted CI was used. All mutation tests require an exclusive disposable database and server.

Admissible operations are PUTs to an existing or absent desktop_state key with int4 revision in 0–2147483647 and a JSON state. Resource counted: committed row writes and response statuses, not application features or elapsed time. For each write through the patched route against the same row, the database must not apply it if the row revision at the write's conflict arbitration is higher. Equal revision remains accepted, preserving the existing contract. Success of a test requires the actual row's revision and state as well as HTTP status; clicking a modal or merely seeing a notification cannot establish a committed write. Adjacent problems not solved: equality conflict detection, conflict-free multi-tab merge, exactly-once acknowledgement, uncooperative SQL writers, privacy of unsealed state, and all OS feature acceptance.

H+: a single conditional upsert can reject a lower revision after a row lock. H−: under the compatibility rule allowing equal revisions, two different concurrent states with equal revision cannot both be preserved by last-writer-wins; a response lost after commit cannot prove noncommit. H∂: protection requires all writers to use the new route, valid monotonic revisions, an available unique key and the deployed PostgreSQL behavior. The separate read that supplies a 409 row can see a later replacement or deletion. The threshold for the narrow repair was an actual locked-row prepatch counterexample, success postpatch, at least one fresh race attack, production build and affected tests; no claim of complete production safety follows.

PostgreSQL's INSERT documentation describes ON CONFLICT DO UPDATE's condition evaluated after conflict identification while rows are locked, with RETURNING only for rows inserted or updated: https://www.postgresql.org/docs/18/sql-insert.html . This is for supported PostgreSQL semantics, not proof against a bypassing old server or privileged SQL. The exact open interface is equal-revision concurrent edits and reconciliation between writers, not solved by comparing lower revisions alone.

## Evidence
Before patch, a transaction updated a row from revision 1 to 3 and held its lock; the HTTP PUT of revision 2 waited, then after commit returned 200 and overwrote it. Real PostgreSQL/HTTP negative control 0/1. After patch the conditional upsert returned 409 and preserved revision 3 and the newer state. A new concurrent creation test verifies highest of 10 and 11 survives, a stale attempt doesn't rotate generation, and an equal revision is still accepted; 2/2 total. This is one scheduled race and one two-request interleaving, not exhaustive concurrency verification. The test is included in the ordinary gate. Build and route ESLint passed.

## Alternatives, attacks, and misleading results
1. Old SELECT then UPDATE: real lock counterexample demonstrates a local gap.
2. Conditional atomic upsert: implemented SQL and test are artifacts; attack with equal revisions, old servers, or lost responses remains a larger coordination gap.
3. UPDATE with revision predicate then INSERT: concurrent first writers can collide; test is simultaneous absent-row creation, local arbitration gap.
4. SELECT FOR UPDATE plus transaction: would cover existing rows, but absent-key arbitration and transaction rollback need independent tests, local implementation gap.
5. Serializable transactions with retry: PostgreSQL may reject transactions and application must retry safely; attacker forces serialization failure and lost acknowledgement, coordination gap.
6. Version tokens/compare-and-swap plus per-write unique mutation IDs: can distinguish equal concurrent versions and replay only with atomic idempotency records; attacker reuses keys or loses acknowledgement. Requires new protocol, storage and clients, original concurrency/retry problem not implemented.

Misleading results: (1) SELECT saw old revision, (2) no overlapping requests, (3) HTTP 200 without row verification, (4) modal accepted without request, (5) status checked without commit, (6) conflict message without retained data, (7) response cache, (8) one old client still writes, (9) equal revision silently overwrites, (10) abort called rollback, (11) insert conflict ignored, (12) token regenerated on failed write, (13) checking stale database statistics snapshot, (14) test aimed at wrong database, (15) raising a density cap instead of fixing UI, (16) one passing race presented as exhaustive correctness. The test explicitly checks HTTP 409 and reads the actual row after releasing the real DB lock; the modal-only shortcut cannot pass it.

Ten Class-A promotions, comprehensive visual inspection, original graphics, Pareto speedup and OS parity are not established. Probe fixes and older deployment safety caveats remain in DESIGN-TT219–TT223. The failure of a prior density readiness wait is not proven to be caused by this race; the next high-information test holds an actual browser pagehide save while a later fixture PUT is committed and verifies final stored and hydrated identities, plus a separate equal-revision multi-tab collision test.
