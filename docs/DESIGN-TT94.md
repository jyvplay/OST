# TT94 — Photos save truth, stale-owner guard and production boundary

## A. Formal scope, runtime and success predicate

The requested system is a complete single-PWA OS satisfying `Full V2 and V2.1 Specs.txt`, preserving privacy, existing good behavior and a lightweight stack, with at least ten additional fully functional Class A core features. The specification's **A/B/C/X** labels describe Android capability/permission tiers; they are not a license to relabel a browser implementation or a measurement of feature quality. A PWA cannot acquire Android MediaStore, native SAF, ADPF, device-default associations or privileged system-image access merely through JavaScript. The ten additional Class A features and complete OS remain **unmet**; no new Class A promotion is asserted here.

The bounded construction studied here is a public PostgreSQL-VFS photo `p`, its recipe `sidecarPath(p)`, an editor-observed tuple `(path, row id, version, stored-content SHA-256)`, and cooperating operations issued to the **current** server. For each guarded write/clear, if the owner exists, is a live image file and matches all four fields including a recomputed digest, the check and recipe mutation execute in the same transaction while participating tree operations use the shared/exclusive advisory gate. If the owner does not match, the mutation must reject and leave that recipe unchanged. This is a conditional safety property, **not** authentication, a promise that all requests succeed, universal serializability or a guarantee for direct SQL, legacy clients/servers, Private, RAM overlay or cross-provider files. Lost COMMIT acknowledgements and uncooperative writers remain outside this quantifier. SHA-256 collision resistance is assumed, not proved. Row identities can be subverted by external database manipulation.

The VFS limit is 8 MiB decoded content. The save guard hashes the stored owner content on the server; no large-image/large-tree latency bound was established. Existing privacy acceptance gates are unchanged: browser AES-GCM encryption ≥50 MiB/s and median 256 KiB Private save ≤1.3× host median + 8 ms, on that test's eight host/private pairs. These are measurements in a particular environment, not guarantees for every browser/device.

Actual tools: Node 22, TypeScript, ESLint, a source-watching Next.js server, real HeadlessChrome 143 driven by Playwright, a fresh exclusive PostgreSQL database (the exact server version was not recorded in that turn), Python/Pillow/independent office/PDF oracles, `git`, `gh`, web search and inspected permissive upstream material. Database triggers deliberately inject failures into this disposable database; they are not simulated production behavior. No independent agent, human expert reviewer or theorem prover was used. A sandbox reset removed the TT93 processes/database; TT94 recreated a fresh explicitly disposable database and rehydrated pinned, test-only corpus objects.

## B. H+, H−, H∂ and frontier

- **H+ (bounded):** the current public Photos path can reject several stale saves/clears; real PostgreSQL waits, fault-trigger tests and browser/SQL observation exercise named orderings. A repaired failure does not count as independently proved for all interleavings.
- **H− (platform boundary):** a standalone web origin does not itself provide Android native/privileged APIs, unrestricted access to other apps, guaranteed physical-device behavior or secure erasure of database WAL/backups. No claim of a mathematical impossibility for every future platform is made.
- **H∂:** the guard works only for cooperating public requests. Older clients and arbitrary `/api/fs` writes may omit it; current Private and RAM paths intentionally retain their previous privacy behavior rather than sending plaintext owner names to the host. Sidecar trash/restore/purge follow remains best-effort. Web Locks coordinate only participating same-origin tabs on supporting browsers; legacy clients, direct storage changes and browsers without Web Locks remain outside that guarantee. Offline queued requests can be replayed later. A failed response after an unacknowledged COMMIT remains ambiguous; even a lock holder cannot make PostgreSQL and localStorage one transaction. The performance gate has varied across runs and is not yet established as repeatable.
- **Frontier:** at least ten additional canonical Class A features remain outstanding; the native/device and full-spec boundary, Private/cross-store recipe pairing, universal lock participation, crash recovery and physical tests remain open. A public per-photo guard does not establish those results.

## C. Source review and independent work

[Web Cryptography Level 2](https://www.w3.org/TR/webcrypto-2/) specifies browser crypto interfaces but does not guarantee throughput. The MIT [noble-ciphers documentation](https://github.com/paulmillr/noble-ciphers/blob/main/README.md) distinguishes authenticated ciphers, fresh nonces and implementation-dependent benchmarks; no replacement crypto was adopted. MIT [Filerobot Image Editor](https://github.com/scaleflex/filerobot-image-editor) documents asynchronous save callbacks; its persistence semantics are not a drop-in solution for OST's VFS. Apache-2.0 [Squoosh](https://github.com/GoogleChromeLabs/squoosh/blob/dev/LICENSE) was reviewed as a browser image tool, not imported. PostgreSQL cooperative-lock and isolation hypotheses are recorded in `DESIGN-TT93.md`.

For the queue blocker, [MDN Web Locks](https://developer.mozilla.org/en-US/docs/Web/API/Web_Locks_API) describes same-origin exclusive locks, automatic release and the secure-context/availability constraint. MIT [LocalQueue](https://github.com/anubhavsahoo/LocalQueue/blob/master/LocalQueue.js) was inspected; it uses simple storage read/modify/write and does not itself solve the observed multi-tab replay window. MIT [OfflineQ](https://github.com/Dexr1te/Offline-Action-Queue/blob/main/LICENSE) documents durable multi-tab work as a goal and current in-memory contract tests; its readiness and integration were not assumed. New changes were independently written, not copied from those projects.

The fresh TT94 browser diagnostic performed nine authenticated 4.25 MiB AES-GCM-shaped operations, checked SHA-256 round trips and rejected modified ciphertext. Median raw encrypt/decrypt were 61.7/61.6 ms (about 69/69 MiB/s), with preparation 2.0 ms, packing/wiping 2.6 ms and copy/wiping 2.3 ms. This local diagnostic is neither the application benchmark nor a throughput guarantee; it suggests, but does not prove, that browser/host crypto and load dominate some failed runs. No cryptographic security requirement or threshold was relaxed.

## D. Negative shapes and modal detection

Not solutions: (1) falsely acknowledging a failed recipe purge; (2) optimistically displaying a failed rating as saved; (3) accepting a stale recipe after a move; (4) attaching it to a byte-identical new owner with a different id; (5) accepting it after a byte-identical rewrite with a new version; (6) trusting a stale hash after corruption; (7) letting a stale clear delete the new owner's recipe; (8) allowing an owner guard to target an unrelated path; (9) dropping the guard in an unlocked privacy layer; (10) forwarding a Private name or recipe plaintext to the host; (11) allowing amnesic recipe edits to reach host storage; (12) ignoring a database rollback fault; (13) claiming a wait/race was forced without observing a real lock; (14) treating a crashed or unselected mutant as killed; (15) declaring source-watcher timing failures production bugs without evidence; (16) overwriting an existing destination sidecar; (17) silently undoing an in-flight pixel edit; (18) treating unguarded old clients as guarded; (19) calling best-effort trash/restore/purge atomic; (20) claiming data deletion securely erases WAL; (21) treating a partial feature tag as full canonical completion; (22) equating a diagnostic benchmark with the unchanged performance gate; (23) replacing a failed aggregate with passing isolated reruns; (24) claiming a manifest installs native defaults; (25) letting global/editor shortcuts act behind a modal.

For (25), TT90's real Chromium `e2e-tt81.mts` E3 moves focus outside the Slides Save-as modal, exercises Tab wrapping and editor/global shortcuts, then independently reads the presentation. Two separate mutations removed the editor shortcut guard and shell modal hold; both were detected in that historical run (2/2). The weaker pop-only mutant survived, as recorded in TT93. This test does not prove every modal or shortcut.

## E. Mechanism portfolio and adversaries

| Mechanism / concrete artifact | Supported portion and strongest targeted attacker | Unresolved interface / cheapest next falsification |
|---|---|---|
| **Confirmed UI state** `Photos.tsx` | A real DB-triggered purge failure is surfaced instead of acknowledged; rating changes apply after success. A failed save stays retryable. | Offline queue/lost acknowledgement and unmount are not fully resolved. Abort after server COMMIT and inspect UI plus DB; local gap. |
| **Synchronous in-editor exclusion** `saving` ref + disabled controls | Forced PostgreSQL wait tests an overlapping rating operation while a later pixel edit stays dirty. | Multiple tabs/old clients are outside a component-local lock. | **Owner identity/version/digest** `parseExpectedPhoto` + row lock | Real HTTP tests attack moved, recreated, rewritten, corrupt and trashed owners and mismatched paths. | A client can omit the guard; same-owner concurrent recipe writes are still last-write-wins. | **Tree ordering** `lockVfsWriter` / `lockVfsPurge` | Save-first and move-first were forced by actual PostgreSQL waits; outcomes are checked in SQL. | Cooperative only; direct SQL and earlier servers bypass it, and hash/lock latency at the 8 MiB cap is unbounded here. | **Privacy dispatch** `PrivacyLayer` | Real host/Private/RAM tests check that an unlocked public guard survives dispatch while Private data is encrypted and RAM data stays off host. | Private/RAM do not receive equivalent stale-owner guarantees; pre-hydration/direct-server calls are outside the browser guard. - Before the owner guard, the new HTTP/SQL stale-owner baseline was **2/8**; moved/recreated/rewritten owners, stale clear, mismatched path and missing media identity failed. After the repair, an initial expanded test passed **11/11**, real forced lock order **2/2**, privacy-layer **13/13**, browser stale editors **2/2**, the Photos UI fault suite **7/7**, TT54 Photos **8/8**, transfer **17/17** and transfer races **5/5** in a sequential dev regression.
