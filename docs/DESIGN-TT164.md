# TT164 — token pagination ordering and asynchronous refresh

## Runtime, model and acceptance threshold
Actually used: local git/gh and web search; Node, TypeScript/Next build, Playwright headless Chromium, HTTP and real disposable PostgreSQL. No independent agent, formal proof assistant, simulator, external expert or screen reader was used. Source is independently written here. No borrowed external code was incorporated.

Admissible object: the Routines automation-token management UI and its GET/POST/DELETE API, not execution of queued commands, security authorization, or the entire OS. Data are finite server-returned token rows, paginated client-side in groups of eight. Access is the real app, browser, API and database with a test-only delayed delivery of an unmodified HTTP response. Resource counts are rows per page and observed test outcomes; no comparative CPU or wall-time performance measurements were made. Proposed local acceptance: production build/typecheck succeeds, the specific attacks reproduce the old bugs, the revised tests and affected browser/API suites pass, no existing checks weakened. Merge threshold: full mandatory gate on the exact build passes and main is reviewed. Quantifier: for each tested sequence, the observed behavior must satisfy the test's predicate; passing finite sequences is not a guarantee for all schedules.

H+: ID-based page selection and unique tie-breaking can satisfy the tested scenarios. H−: no implementation can meet the complete requested OS contract under the stated constraints; this broad impossibility is not established, and the old implementation's failures do not prove it. H∂: ordering stability holds for a fixed database state and database collation; concurrent deletions, failed refreshes, interleaved actions, unmounting, and network errors require separate reasoning. Pagination is neither authentication nor authorization, and total deterministic order of a fixed set is not snapshot isolation across concurrent changes.

## Evidence and boundaries
Ten real minted tokens were given equal database timestamps. The old API's actual order did not match PostgreSQL's `ORDER BY created_at, id`; the old UI also failed to display its newly minted row after 16 external mints. These are concrete failures, not an exhaustive impossibility proof. The old-build delayed-listing test also failed but before the old response was released, so that run does not independently isolate stale-response overwriting. A revised test now specifically searches for the new ID, releases an earlier genuine response and asserts the row remains. No claim is made that this revised attack was run against the old build.

The patch orders by `(created_at, id)` and chooses the new token's page by looking up its returned ID in the actual refreshed list. A request version prevents older outstanding GET responses and errors from replacing newer results, and interaction version prevents a pending mint refresh from overriding a search or navigation performed after the POST. A newer failed request can still leave older data displayed alongside an error; automatic retry and cross-window live synchronization are not implemented. Search remains client-side and GET loads the full list; page selection cannot guarantee the minted row still exists after concurrent deletion or after another operation supersedes its refresh. A search entered while the POST itself is pending can still be reset when the mint succeeds. The ID is random, not a chronological sequence: using it as a tie-breaker only makes tied timestamps deterministic, not true creation order.

Four real PostgreSQL/HTTP/Chromium regressions passed on the production build: same-time order, 16 external mints before UI mint, delayed genuine earlier GET, and user filter change during mint refresh. Old build failed first two; its preliminary delayed test failed earlier for a different reason. The previous pagination regression passed 1/1, TT146 automation browser 5/5 and TT158 planner 1/1; production build passed. These checks are bounded and do not validate every race or accessibility combination. The fetched PostgreSQL documentation https://www.postgresql.org/docs/current/queries-order.html states: PostgreSQL specifies a sort by each expression in sequence; equal earlier keys are ordered by later keys. Here uniqueness of ID gives a total order for a fixed result, subject to the database's ordering semantics. This does not assert that IDs identify chronological insertion order.

## Mechanism portfolio and attacks
Each item is a distinct falsifiable construction, not an implemented or proven system-wide solution. The first three are implemented locally; the remaining ones are alternative designs, not hidden work.
1. **Composite sort:** `(time, unique ID)`; artifact is the API order and a ten-row timestamp-tie test. Fixed-set ordering is the scoped portion; concurrent mutation remains local and needs interleaved-paging tests. Attack: all timestamps equal and insertion order differs from ID order (performed).
2. **Identity-based page location:** find the created ID in the returned list, divide its index by eight; artifact is the HTTP/browser test with sixteen external mints. The tested interleaving passes; disappearance or later list changes remain local. Attack: enough intervening inserts to cross two page boundaries (performed).
3. **Request epochs and user intent:** discard older GET completion and avoid selecting a page after later interactions; artifact is delayed-response and typed-filter tests. Tested schedules pass; failed latest request and interactions during POST remain local. Attack: deliver genuine earlier snapshot after a later one; change filter while newer response is held (performed).
4. **Server cursor pagination:** order and seek by composite key with a bounded server response; artifact would be a cursor contract, no implementation here. Proof gap: mutation and cursor consistency; attack delete/insert around cursor and equal timestamps. This is a local data-interface change.
5. **Snapshot session:** freeze a versioned list for navigation; artifact would bind every page to a version and define expiration. Gap: storage, staleness and security while revoking; attack revoke after snapshot and expire mid-navigation. Local but cross-request synchronization required.
6. **Push/invalidation:** notify all open panels to refresh after mutations; artifact would be a same-origin event protocol with recovery. Gap: dropped events and background throttling; attack disconnect/reconnect and interleaved writes. Local synchronization gap; not proof of exactly-once command execution.

Misleading shortcuts: stale pre-mint count as a page index; non-unique timestamp as a total order; random ID as insertion time; offset pagination as a snapshot; last response to arrive as newest state; mutation completion as proof refresh completed; mock GET as real database evidence; a visible secret as proof the row is reachable; changing the query after the user typed; an error-free console as correctness; one passing browser as all-browser coverage; one keyboard test as screen-reader proof; one tied timestamp test as all interleavings; fixed rows as scalability; fewer displayed rows as less CPU or less network; faster one-off run as Pareto proof; targeted success as full gate; ledger status as Class A. The old stale-count shortcut is detected by the 16-insert test. The new test adds meaningful race coverage rather than weakening an existing assertion.
