# TT221 — browser probe ownership

## Runtime and contract
One agent in a 2-CPU sandbox; Node 22, Next production build/server, PostgreSQL disposable database, Playwright Chromium 143, curl, ESLint, the repository harness and web search were used. No independent agent, simulator, theorem prover, independent reviewer, or hosted CI was used. Real requests went through the product's probe endpoint; the `.invalid` tests deliberately use DNS failure, not mocked responses. System CA trust was enabled on the production server for this environment; this trusts the system store and does not disable certificate checking.

For a mounted Browser and valid tabs with distinct IDs, each active iframe-mode tab lacking a verdict should have its own request started, even when another tab has the same URL. For any such request, at most one is in flight per tab; on completion it can update only a surviving tab with the same ID and requested URL. An explicit retry can make a new request. Observation is limited to the mounted instance and eventual network responses. There is no guarantee of a finite response time from a stalled client connection, no guarantee of framing success or of unchanged remote policy, and no persistence of probe results. No arbitrary-browser universal correctness claim is made. The regression test allows 5 seconds for the local real DNS-negative probe, not a product-wide latency SLA.

H+: per-tab completion is achievable for completed requests. H−: a probe cannot prove a remote page will later frame under different request, policy, network, or browser conditions. H∂: the answer depends on valid independent tab IDs, active selection, proxy mode, endpoint completion and trustworthy TLS configuration. Threshold for this narrow claim: old build must fail a concrete real-browser counterexample; patched build must pass it and a fresh retry attack; compile and affected regression suites must run. Full product Class A and merge require much broader evidence.

## Evidence and boundaries
Old build: first `.invalid` tab received `unknown` but opening the identical URL again produced no probe response in 5s; 0/1. New build: a real request is observed for each tab and for a retry in each tab, all returning `unknown`; 1/1. TT220 identity 2/2. Production build and Browser lint passed. With the server started using `NODE_OPTIONS=--use-system-ca`, an actual GitHub probe returned 200 and X-Frame-Options deny, and TT134 review passed 8/8 including genuine invalid DNS checks in both widths. As prior design notes already documented, this is sandbox trust configuration, not an application change or evidence for every deployment. Never use disabled TLS verification as a substitute.

The patch retains only per-tab in-flight IDs and checks both ID and original URL before applying a response. It prevents URL-based deduplication from suppressing an independent tab and prevents an old result from updating a changed URL. It does not cancel a request on tab close, enforce a browser-side timeout, test close-while-pending, verify all response fields, or prove proxy mode and remount behavior. Probe results can become stale. Existing embed-probe classification is simplistic: for example it treats any `*` in frame-ancestors as unrestricted, including a wildcard subdomain; that remains an untested-by-this-patch separate issue. The separate `embed-policy.ts` also says obsolete ALLOW-FROM is blocking; current MDN says modern browsers ignore it. This turn does not fix those separate parsers or assert their correctness.

External constraints: [MDN X-Frame-Options](https://github.com/mdn/content/blob/main/files/en-us/web/http/reference/headers/x-frame-options/index.md?plain=1) specifies DENY blocks all framing and SAMEORIGIN requires all ancestors to match, while modern engines ignore obsolete ALLOW-FROM. [OWASP clickjacking guidance](https://cheatsheetseries.owasp.org/cheatsheets/Clickjacking_Defense_Cheat_Sheet.html) notes enforced CSP frame-ancestors overrides XFO in modern conforming implementations, with legacy browser exceptions. Those header rules do not establish a particular live origin's future response or prove this app's parser.

## Candidate mechanisms and falsifiers
1. URL-only set (old code): artifact is the prepatch real-browser counterexample; cheapest attack is a second tab with identical URL. Gap is local and demonstrated.
2. Per-tab in-flight set (implemented): artifact is `Browser.tsx` and `e2e-tt221-browser-probe.mts`; demonstrated only for two sequential unknown results and retry. Attack: close or change a tab while the request is held. Gap is local and not yet exercised.
3. Shared URL promise with subscriber fan-out: construction shares one network result across tab IDs. Attack: close one subscriber or retry while another remains; stale policy and request generations make correct fan-out nontrivial. No implementation or verification; local gap.
4. Cache completed results by URL with expiry: one network read can serve many tabs. Attack: policy changes inside TTL or request-sensitive responses; requires explicit freshness semantics, so its gap reaches the remote-truth requirement.
5. Always re-probe on activation: avoids persistent URL cache but causes extra traffic and may race or loop after failure. Attack: switch repeatedly while a request is pending. Local gap; no performance claim.
6. Abort per-tab on close and unmount: would reduce unnecessary work. Attack: completion races with abort and response already committed; cancellation cannot retroactively establish remote state. Local lifecycle gap, not implemented.

Fifteen misleading result shapes: (1) badge only; (2) first tab succeeds; (3) second tab reuses a URL key but has no result; (4) synthetic fulfilled response called a real probe; (5) DNS failure called a denial; (6) certificate failure called remote policy; (7) disabled TLS validation called a fix; (8) one URL's policy asserted for all paths; (9) stale result called current; (10) header probe called guaranteed browser render; (11) failed response treated as unrestricted; (12) retry button that does not send a request; (13) result applied to a different tab; (14) default content measured as intended app; (15) changed caps or hidden data called a density improvement; (16) a modal dialog alone described as proof an action completed. In the modal shortcut, acceptance of a prompt is merely user input: it does not prove an asynchronous request was sent, acknowledged or committed. The regression's response waiter and returned verdict are required independently of UI state; a prompt/badge without a matching actual response fails the test.

No ten Class-A promotions, comprehensive visual review, new artwork, or measured Pareto improvement is claimed. Broader specs and accumulated-data density gates remain open. The next high-information test for this patch holds a real probe request while switching/closing tabs, then releases it and verifies ownership and retry; it must not be replaced by a fabricated success response.
